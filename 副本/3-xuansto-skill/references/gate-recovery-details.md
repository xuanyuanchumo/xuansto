# 3-Strike Protocol 门禁恢复详细文档

## 3-Strike Protocol 完整描述

3-Strike Protocol 是门禁检查失败后的渐进式恢复机制，通过三次递进式尝试解决阻塞问题，避免无限循环和重复无效修复。

### Strike 1: 自动修复尝试

- **触发条件**: 门禁检查首次失败
- **执行动作**:
  1. 分析失败原因，定位具体错误点
  2. 基于失败信息自动修正代码或配置
  3. 重新运行门禁检查，验证修复是否生效
- **适用场景**: 编码错误、配置缺失、依赖版本不匹配、语法问题等可直接定位和修复的情况
- **预期耗时**: 短，通常为单次修改+重新检查的时间
- **记录要求**: 将失败原因及修复动作记录到 Decision Log

### Strike 2: 换策略修复

- **触发条件**: Strike 1 修复后门禁检查仍然失败
- **执行动作**:
  1. 停止使用 Strike 1 的修复方法
  2. 深入分析根因而非表面症状
  3. 换一种修复方法，包括但不限于:
     - 换算法（如排序算法、搜索策略）
     - 换实现方式（如同步改异步、递归改迭代）
     - 换依赖库（如换用其他同等功能的第三方包）
     - 换架构模式（如换用不同的设计模式）
  4. 重新运行门禁检查，验证修复是否生效
- **适用场景**: 架构设计问题、性能瓶颈、算法选择不当、实现方式不合理等需要从根本思路改变的情况
- **预期耗时**: 中等，需要重新理解和调整实现
- **记录要求**: 将 Strike 1 失败原因、根因分析及新策略记录到 Decision Log

### Strike 3: 升级处理

- **触发条件**: Strike 2 换策略后门禁检查仍然失败
- **执行动作**:
  1. 停止当前 Phase 的执行
  2. 将问题升级给用户（escalation_target: user），提供完整的失败上下文:
     - 三次 Strike 的失败原因
     - 已尝试的修复方法及结果
     - 根因分析
     - 建议的后续方向
  3. 等待人工介入决策
  4. 可选路径:
     - 用户提供指导后继续执行
     - 分析反模式后经用户确认重启该 Phase
- **适用场景**: 安全漏洞、需求理解偏差、外部依赖不可用、超出当前能力范围的问题
- **预期耗时**: 不确定，取决于用户响应时间
- **记录要求**: 将三次 Strike 的完整失败记录、升级原因及用户决策记录到 Decision Log

### 失败经验沉淀

- **触发条件**: 3次 Strike 全部失败后
- **执行动作**: 将失败经验沉淀到经验知识库，confidence=0.40
- **沉淀内容**:
  - 问题描述及上下文
  - 尝试过的修复方法及结果
  - 根因分析
  - 最终解决方案（如有）
- **confidence 说明**: 0.40 表示该经验为失败经验，可信度较低，仅供参考，不可直接作为决策依据

### Decision Log 记录规范

每次 Strike 都必须记录以下信息到 Decision Log:

| 字段 | 说明 |
|------|------|
| strike_number | 当前 Strike 编号（1/2/3） |
| gate_name | 失败的门禁名称 |
| failure_category | 失败分类（BLOCK/WARN） |
| failure_reason | 失败原因描述 |
| fix_action | 采取的修复动作 |
| fix_result | 修复结果（成功/失败） |
| root_cause | 根因分析（Strike 2 起必填） |
| timestamp | 记录时间 |

## 门禁失败分类

### BLOCK

- **含义**: 必须修复才能继续
- **特征**: 存在阻塞性问题，当前 Phase 无法推进到下一阶段
- **处理方式**: 必须触发 3-Strike Protocol 进行修复
- **示例场景**:
  - 编译失败
  - 测试用例全部失败
  - 安全漏洞检测发现高危问题
  - 核心功能不可用

### WARN

- **含义**: 建议修复但可继续
- **特征**: 存在非阻塞性问题，不影响当前 Phase 推进，但可能影响质量或后续阶段
- **处理方式**: 记录到 Decision Log，可选择修复或标记为已知问题继续推进
- **示例场景**:
  - 部分测试用例失败（非核心功能）
  - 代码风格不符合规范
  - 性能未达最优但可接受
  - 低危安全问题

### PASS

- **含义**: 通过
- **特征**: 门禁检查全部通过，无任何问题
- **处理方式**: 正常推进到下一阶段
- **示例场景**:
  - 所有测试用例通过
  - 安全检查无问题
  - 性能指标达标
  - 代码质量评分合格

## 恢复策略选择逻辑

根据门禁失败的类型和原因，自动选择最合适的恢复策略:

### 编码问题 → 自动修复

- **识别特征**: 语法错误、类型错误、逻辑错误、配置缺失、依赖版本问题
- **选择理由**: 编码问题通常有明确的错误信息，可直接定位和修复
- **对应 Strike**: Strike 1
- **修复方式**: 基于错误信息直接修改代码或配置
- **示例**:
  - TypeScript 类型错误 → 修正类型定义
  - 缺少依赖包 → 安装对应依赖
  - 配置项缺失 → 补充配置

### 架构问题 → 换策略

- **识别特征**: 设计模式不当、模块耦合过紧、扩展性差、职责划分不清
- **选择理由**: 架构问题无法通过简单修改解决，需要从根本上改变实现方式
- **对应 Strike**: Strike 2
- **修复方式**: 重新设计架构，换用不同的设计模式或实现策略
- **示例**:
  - 回调地狱 → 改用 Promise/async-await
  - 紧耦合模块 → 引入依赖注入或事件驱动
  - 单体架构瓶颈 → 拆分为微服务或模块化

### 安全问题 → 升级处理

- **识别特征**: SQL注入、XSS漏洞、认证绕过、敏感信息泄露、权限控制缺失
- **选择理由**: 安全问题需要专业判断，自动修复可能引入新的安全风险
- **对应 Strike**: Strike 3
- **修复方式**: 升级给用户，由专业人员评估和决策
- **示例**:
  - SQL注入风险 → 需要安全专家审查修复方案
  - 认证机制缺陷 → 需要重新设计认证流程
  - 敏感数据暴露 → 需要评估数据分类和保护策略

### 性能问题 → 换策略

- **识别特征**: 响应时间超标、内存泄漏、CPU占用过高、吞吐量不足
- **选择理由**: 性能问题通常不是简单代码修改能解决的，需要换用更优的算法或实现
- **对应 Strike**: Strike 2
- **修复方式**: 分析性能瓶颈，换用更高效的算法、数据结构或实现方式
- **示例**:
  - O(n²)排序 → 换用O(n log n)算法
  - 同步阻塞IO → 换用异步非阻塞IO
  - 内存泄漏 → 换用更合理的资源管理策略

### 策略选择决策表

| 失败类型 | 优先策略 | 对应Strike | 是否可跳过 | 升级条件 |
|----------|----------|------------|------------|----------|
| 编码问题 | 自动修复 | Strike 1 | 否 | Strike 1失败后进入Strike 2 |
| 架构问题 | 换策略 | Strike 2 | 否 | Strike 2失败后进入Strike 3 |
| 安全问题 | 升级处理 | Strike 3 | 否 | 直接升级给用户 |
| 性能问题 | 换策略 | Strike 2 | WARN时可跳过 | 连续2次换策略失败后升级 |

### 特殊规则

1. 安全问题中的 BLOCK 类别直接跳至 Strike 3 升级处理，不进行自动修复尝试
2. 性能问题中的 WARN 类别可记录后继续推进，不强制触发 3-Strike Protocol
3. 同一门禁连续3次触发 3-Strike Protocol 且均失败时，应考虑调整门禁阈值或规则
4. 升级处理时必须提供完整的上下文信息，包括三次 Strike 的详细记录
