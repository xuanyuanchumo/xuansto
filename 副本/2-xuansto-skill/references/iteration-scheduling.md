# 智能迭代调度

## 1. 修复优先级矩阵

迭代过程中产生的缺陷按以下优先级从高到低排序：

### 1.1 阻塞性门禁失败（BLOCKING_GATE_FAILURE）— 最高优先级

**定义**：质量门禁（Quality Gate）失败且阻塞整个流水线继续执行的缺陷。此类缺陷导致后续所有Phase或Agent无法正常推进，必须在本轮迭代中立即修复。

**判定标准**：
- TEST-PASS门禁失败：所有测试无法通过，构建产物不可用
- BUILD-SUCCESS门禁失败：编译/构建失败，无法生成可部署产物
- SECURITY-CRITICAL门禁失败：安全扫描发现高危漏洞，禁止发布

**示例**：
- TEST-PASS门禁失败，测试套件中0个用例通过，整个交付流水线停滞
- 构建阶段产生致命编译错误，所有下游Agent无法获取构建产物
- 安全门禁检测到SQL注入漏洞，按策略必须阻断发布流程

**调度规则**：触发即时中断，当前迭代暂停所有其他任务，集中全部资源修复。

### 1.2 高影响范围（HIGH_IMPACT_SCOPE）

**定义**：缺陷影响多个模块、关键用户旅程或跨平台功能，虽未完全阻塞流水线，但严重影响交付质量与用户体验。

**判定标准**：
- 影响范围跨越2个及以上模块
- 破坏关键用户旅程（如登录、支付、数据提交）
- 同时影响Web和Desktop等多个平台
- 导致核心业务逻辑输出错误

**示例**：
- Bug同时影响Web和Desktop两个平台，用户无法完成关键操作
- 认证模块缺陷导致登录流程在Chrome和Firefox上均失败
- API接口变更未同步更新，导致前端和后端模块同时异常
- 数据持久化层缺陷影响所有依赖该层的业务模块

**调度规则**：在当前迭代窗口内必须完成修复，优先排入修复队列。

### 1.3 低影响范围（LOW_IMPACT_SCOPE）

**定义**：缺陷仅影响单一组件或边界场景，且存在可用的临时规避方案（workaround），不影响核心功能正常运行。

**判定标准**：
- 影响范围限于单一模块或组件
- 仅在特定边界条件下触发
- 存在用户可执行的规避方案
- 不影响核心业务流程

**示例**：
- 仅在特定浏览器版本下出现的样式偏移，可通过刷新页面规避
- 非核心表单字段的校验提示信息不准确，不影响数据提交
- 日志输出格式异常，不影响功能逻辑
- 某一边界输入导致非关键UI组件渲染异常

**调度规则**：可安排在后续迭代中修复；累积不超过5个，超过则提升为HIGH_IMPACT批量处理。

### 1.4 低修复置信度（LOW_FIX_CONFIDENCE）

**定义**：Agent对修复方案的正确性不确定，需要人工干预或更多验证。通常发生在Agent多次尝试修复失败，或修复涉及安全敏感代码的场景。

**判定标准**：
- Agent连续3次尝试修复均未通过验证
- 修复涉及安全敏感代码（认证、加密、权限控制）
- 修复方案存在多种可能路径，Agent无法自主选择最优解
- 修复可能引入新的副作用，风险不可控

**示例**：
- Agent尝试修复认证Token刷新逻辑3次均失败，需要人工审查安全逻辑
- 涉及加密密钥轮换的缺陷，Agent无法自主判断密钥管理策略
- 并发竞态条件修复，Agent的修复方案在压力测试下仍出现偶发失败
- 涉及用户权限升级的缺陷，修复方案需要安全团队评审

**调度规则**：分配额外的验证迭代，不占用主修复资源；触发人机协作断点等待人工决策。

### 1.5 优先级调度总览

| 优先级 | 触发条件 | 响应时间 | 资源分配 |
|--------|----------|----------|----------|
| BLOCKING_GATE_FAILURE | 质量门禁失败阻塞流水线 | 即时（0延迟） | 100%资源集中 |
| HIGH_IMPACT_SCOPE | 多模块/跨平台/关键旅程受影响 | 当前迭代窗口内 | 优先分配 |
| LOW_IMPACT_SCOPE | 单组件/边界场景/有规避方案 | 后续迭代 | 按队列处理 |
| LOW_FIX_CONFIDENCE | 3次修复失败/安全敏感/需人工 | 额外验证迭代 | 独立资源池 |

## 2. 修复价值评分公式

### 2.1 公式定义

```
修复价值（Fix Value） = 阻塞等级 × 影响范围系数 + 修复置信度
```

### 2.2 参数定义

#### 阻塞等级（Blocking Level）

| 等级 | 编码 | 分值 | 说明 |
|------|------|------|------|
| 阻塞 | BLOCK | 10 | 质量门禁失败，流水线完全停滞 |
| 警告 | WARN | 5 | 核心功能受损，但流水线可部分运行 |
| 信息 | INFO | 1 | 非核心问题，不影响流水线运行 |

#### 影响范围系数（Impact Scope Coefficient）

| 范围 | 系数 | 说明 |
|------|------|------|
| 跨平台 | 3.0 | 同时影响Web、Desktop等多个平台 |
| 多模块 | 2.0 | 影响2个及以上功能模块 |
| 单模块 | 1.0 | 仅影响单一模块 |
| 边界场景 | 0.5 | 仅在特定边界条件下触发 |

#### 修复置信度（Fix Confidence）

| 置信度 | 分值 | 判定依据 |
|--------|------|----------|
| 高（high） | 0.9 | Agent有成功修复同类问题的历史记录，方案经过静态验证 |
| 中（medium） | 0.6 | Agent有部分相关经验，方案逻辑合理但未充分验证 |
| 低（low） | 0.3 | Agent无相关经验，方案为探索性尝试，或已失败1-2次 |

### 2.3 评分计算示例

**示例1：跨平台BLOCK门禁失败**
- 阻塞等级：BLOCK = 10
- 影响范围：跨平台 = 3.0
- 修复置信度：high = 0.9
- 修复价值 = 10 × 3.0 + 0.9 = **30.9**

**示例2：多模块WARN缺陷**
- 阻塞等级：WARN = 5
- 影响范围：多模块 = 2.0
- 修复置信度：medium = 0.6
- 修复价值 = 5 × 2.0 + 0.6 = **10.6**

**示例3：单模块INFO缺陷**
- 阻塞等级：INFO = 1
- 影响范围：单模块 = 1.0
- 修复置信度：high = 0.9
- 修复价值 = 1 × 1.0 + 0.9 = **1.9**

**示例4：边界场景WARN缺陷，低置信度**
- 阻塞等级：WARN = 5
- 影响范围：边界场景 = 0.5
- 修复置信度：low = 0.3
- 修复价值 = 5 × 0.5 + 0.3 = **2.8**

### 2.4 排序与执行规则

- **排序规则**：按修复价值评分降序排列，分值高的优先执行
- **同分处理**：阻塞等级高的优先；阻塞等级相同则影响范围系数大的优先
- **评分阈值**：

| 评分区间 | 决策 | 执行策略 |
|----------|------|----------|
| > 15 | 立即修复 | 中断当前低优先级任务，分配资源即时处理 |
| 5 - 15 | 排队修复 | 加入当前迭代修复队列，按评分降序依次处理 |
| < 5 | 记录但不修复 | 记录至缺陷知识库，待后续迭代评估 |

## 3. 增量验证策略

### 3.1 核心原则

智能选择受影响测试子集，基于代码变更的依赖分析，避免每次迭代运行全量测试，目标是将迭代周期缩短50%以上。

### 3.2 受影响测试子集选择算法

增量验证的核心是精确识别代码变更影响的测试范围，具体算法步骤如下：

**步骤1：解析代码差异（Parse Code Diff）**
- 对比当前迭代与上一迭代的代码差异
- 识别变更的文件列表和变更类型（新增/修改/删除）
- 提取变更文件中具体修改的函数、类、接口名称
- 记录变更的导出符号（exported symbols）

**步骤2：构建依赖图（Build Dependency Graph）**
- 扫描代码库中所有 `import` / `require` 语句，构建模块级依赖图
- 建立测试 → 被测代码的映射关系（test-to-code mapping）
- 基于函数调用链构建细粒度的函数级依赖图
- 标记依赖深度：直接依赖（depth=1）、传递依赖（depth>1）

**步骤3：选择受影响测试（Select Affected Tests）**
- 选择直接依赖变更代码的测试用例（depth=1）
- 递归选择传递依赖变更代码的测试用例（depth>1，默认最大深度为3）
- 合并去重，生成受影响测试子集

**步骤4：强制包含关键测试（Always Include）**
- 冒烟测试（Smoke Tests）：验证系统基本可用性的核心测试集
- 关键路径测试（Critical Path Tests）：覆盖核心用户旅程的端到端测试
- 安全基线测试（Security Baseline Tests）：验证安全门禁的必要测试

### 3.3 依赖图分析实现

依赖图的构建基于代码静态分析，具体规则如下：

| 变更级别 | 分析规则 | 测试范围 |
|----------|----------|----------|
| 函数级变更 | 追踪函数调用链，定位直接和传递调用者 | 运行该函数的直接测试及传递依赖测试 |
| 模块级变更 | 扫描模块内所有导出符号的引用 | 运行该模块的所有测试及依赖模块测试 |
| 接口级变更 | 分析接口契约变更，追踪所有实现方和消费方 | 运行依赖该接口的所有模块测试 |
| 配置级变更 | 配置项可能影响全局行为，无法精确限定范围 | 运行全量测试 |

依赖图构建使用 `import` / `require` 语句解析模块依赖关系，结合AST分析提取函数级调用链。依赖图以有向无环图（DAG）形式存储，支持增量更新。

### 3.4 迭代周期缩短机制

**传统全量验证**：每次迭代运行全量测试套件（如500个测试用例），耗时较长。

**增量验证**：仅运行受影响测试子集（如50-100个测试用例），大幅缩短验证时间。

| 场景 | 全量测试数 | 增量测试数 | 周期缩短比例 |
|------|-----------|-----------|-------------|
| 单函数修改 | 500 | 10-20 | ~96% |
| 单模块修改 | 500 | 50-100 | ~80% |
| 多模块修改 | 500 | 100-200 | ~60% |
| 接口变更 | 500 | 200-300 | ~40% |
| 配置变更 | 500 | 500（全量） | 0% |

**预期效果**：
- 平均缩短迭代周期50%以上
- 减少不必要的测试执行开销
- 保持缺陷检出率不降低
- 配置级变更自动升级为全量测试，确保安全性

### 3.5 回退规则

增量验证存在漏检风险，因此设置回退机制：

1. **正常流程**：增量验证通过 → 标记本轮验证完成 → 进入下一迭代
2. **回退触发**：增量验证通过但后续全量验证失败 → 下一迭代自动回退为全量验证
3. **回退恢复**：连续2次全量验证通过后，恢复为增量验证模式
4. **强制全量**：每5次增量验证后，自动执行1次全量验证作为健康检查

### 3.6 执行流程

1. 代码变更提交后，自动触发依赖分析引擎
2. 解析代码差异，识别变更文件和函数
3. 构建依赖图，确定受影响测试子集
4. 强制包含冒烟测试和关键路径测试
5. 执行增量测试子集
6. 若增量测试全部通过，标记本轮验证完成
7. 若增量测试存在失败，扩大测试范围至上一级别重新验证
8. 记录验证结果，更新依赖图缓存

## 4. 跨分支经验同步策略

不同类型的知识资产采用不同的同步策略，确保分支间经验传递的完整性与一致性。

### 4.1 三类知识资产的同步方式

#### 4.1.1 Markdown源文件（.knowledge/ 目录下的 .md 文件）

**同步方式**：使用 git merge / cherry-pick 进行同步

**适用场景**：经验文档、设计决策记录、最佳实践等文本类知识

**操作流程**：
1. 在源分支确认Markdown文件已提交
2. 在目标分支执行 `git merge` 或 `git cherry-pick` 同步提交
3. 若出现冲突，进入人工审核流程
4. 冲突解决后提交，完成同步

**冲突处理**：Markdown文件冲突由人工审核，保留双方修改中有价值的部分，合并为完整文档。冲突标记区域需逐段审查，确保语义一致性。

#### 4.1.2 SQLite数据库（knowledge.db）

**同步方式**：使用导出-导入方法（export-import）

**适用场景**：结构化的经验数据、缺陷统计、修复历史记录等

**操作流程**：
1. 在源分支导出数据：`sqlite3 knowledge.db .dump > export.sql`
2. 将 export.sql 传输至目标分支工作区
3. 在目标分支执行合并：解析SQL语句，按主键去重合并
4. 重新导入：`sqlite3 knowledge.db < merged.sql`
5. 验证数据完整性：检查表记录数、索引一致性

**重要约束**：
- **禁止直接 cherry-pick 二进制文件**：SQLite的.db文件为二进制格式，直接cherry-pick可能导致数据损坏
- 必须通过 `.dump` 导出为SQL文本格式后再进行合并操作
- 合并时执行去重与冲突检测，确保数据一致性

**冲突处理**：采用"最新优先"（latest wins）策略——当同一记录在两个分支中存在不同版本时，以时间戳较新的版本为准，旧版本移入历史归档表。

#### 4.1.3 Chroma向量数据

**同步方式**：通过重新嵌入（re-embedding）重建，不跨分支复制

**适用场景**：语义搜索索引、相似度检索向量、知识嵌入等

**操作流程**：
1. 检测源分支知识源文件的数据hash变化
2. 在目标分支触发重新嵌入流程
3. 使用当前分支的嵌入模型对源文件重新生成向量
4. 构建新的向量索引，替换旧索引
5. 验证向量检索的准确性和召回率

**重要约束**：
- **禁止跨分支复制向量数据**：不同分支的嵌入模型版本可能不同，直接复制向量会导致维度不匹配或语义偏移
- 必须在目标分支本地重新执行嵌入计算
- 重新嵌入后需验证检索质量，确保向量索引与源数据一致

**冲突处理**：对两个分支的源文件分别重新嵌入，生成向量后执行去重——基于余弦相似度阈值（默认0.98）识别重复向量，保留较新版本。

### 4.2 同步策略总览

| 知识类型 | 同步方式 | 冲突处理 | 禁止操作 |
|----------|----------|----------|----------|
| Markdown知识 | git merge / cherry-pick | 人工审核，保留双方修改 | 无特殊禁止 |
| SQLite知识库 | 导出→合并→导入（.dump → merge → reimport） | latest wins策略 | 禁止直接cherry-pick .db文件 |
| Chroma向量库 | 重新嵌入（re-embedding） | 重新嵌入双方版本后去重 | 禁止跨分支复制向量数据 |

### 4.3 同步触发机制

**自动触发**：每次Phase 7（智能迭代调度）完成后，Specification Keeper Agent评估经验适用性，将高置信度知识广播至其他活跃的 `feature/*` 分支。

**评估标准**：
- 知识置信度评分 ≥ 0.8（基于历史验证成功率）
- 知识适用范围与目标分支的功能领域匹配
- 知识未标记为分支特定（branch-specific）

**广播流程**：
1. Specification Keeper扫描当前分支Phase 7产出的知识资产
2. 按知识类型分类，评估每项知识的适用性
3. 筛选高置信度知识，生成同步候选列表
4. 向目标分支发送同步通知，包含知识摘要和适用性评估
5. 目标分支接收通知后，按知识类型执行对应同步策略

### 4.4 其他同步时机

| 触发条件 | 说明 |
|----------|------|
| 分支合并前 | 在执行merge操作之前，先同步知识资产，避免合并后数据丢失 |
| Phase切换时 | 从一个Phase进入下一个Phase时，自动同步当前分支的经验知识 |
| 手动触发 | 通过 `/sync-knowledge` 命令主动触发同步，适用于紧急修复或知识更新场景 |

### 4.5 同步完整流程

1. 检测当前分支与目标分支的知识资产差异
2. 按知识类型选择对应同步策略
3. 执行同步操作，记录同步日志
4. 验证同步后知识资产的完整性
5. 若验证失败，回滚同步操作并告警
6. 同步完成后更新知识资产版本号

## 5. 迭代收敛判定

### 5.1 收敛条件

连续2次迭代满足以下全部条件时，判定为收敛：

- 通过所有质量门禁（Quality Gates）
- 无新增缺陷
- 所有BLOCKER和HIGH_IMPACT缺陷已修复
- 修复置信度评分均达到阈值以上

### 5.2 不收敛处理

连续3次迭代未收敛时，触发 `ITERATION_DIVERGENCE` 人机协作断点：

1. 系统自动生成发散分析报告，包含：
   - 未收敛原因分析
   - 缺陷分布热力图
   - 资源消耗统计
2. 暂停自动迭代，等待人工决策
3. 人工可选操作：
   - 调整修复优先级矩阵
   - 降低收敛条件（需审批）
   - 引入外部专家Agent
   - 终止当前迭代，回退至上一稳定状态

### 5.3 收敛后操作

1. 生成迭代报告，包含：
   - 迭代轮次与耗时
   - 缺陷修复统计
