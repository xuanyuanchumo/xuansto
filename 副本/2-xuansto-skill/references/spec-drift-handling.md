# 规格漂移处理（Spec Drift Handling）

> 本文档定义了 Xuansto Skill 多Agent自主开发编排器中规格漂移的完整三级处理流程，
> 涵盖漂移等级定义、各级处理流程、SPEC-CONSISTENCY质量门禁机制及标记规范。

---

## 1. 概述

在SDD（规格驱动开发）流程中，Agent在实现阶段可能遇到实际情况与规格文档不一致的场景，
此类偏差称为**规格漂移（Spec Drift）**。本流程确保漂移被识别、标记、评估和妥善处理，
防止未经授权的规格偏离累积为系统性风险。

核心原则：
- 所有漂移必须被显式标记，禁止隐式偏离规格
- 漂移影响等级决定处理流程的严格程度
- 高影响漂移必须触发人工介入，Agent不得自主决策
- 所有漂移记录必须可追溯、可审计

---

## 2. 漂移等级定义

### 2.1 低影响漂移（Low Impact Drift）

**定义**：仅影响单个函数或组件内部实现细节的漂移，不改变外部可观测行为。

**典型场景**：
- 变量命名与规格建议不一致，但语义等价
- 内部算法实现方式与规格描述不同，但输入输出契约一致
- 代码风格、注释格式等非功能性差异
- 内部辅助函数的拆分或合并，不影响公开接口
- 错误消息措辞微调，不影响错误码和语义

**判断标准**：
- 不引入规格未覆盖的新行为
- 不改变模块间接口契约
- 不影响数据格式兼容性
- 不影响安全性模型

### 2.2 中影响漂移（Medium Impact Drift）

**定义**：影响模块间接口或数据格式的漂移，可能波及多个组件但风险可控。

**典型场景**：
- 模块间调用接口参数顺序或类型变更
- 数据结构字段增减（非破坏性变更）
- 配置项默认值变更
- 错误码体系扩展
- 内部模块间通信协议微调
- 缓存策略或性能优化导致的可观测行为变化

**判断标准**：
- 影响跨模块交互但可通过适配层兼容
- 数据格式变更但保持向后兼容
- 测试用例需要相应调整但核心逻辑不变
- 不涉及外部API契约或安全模型

### 2.3 高影响漂移（High Impact Drift）

**定义**：影响外部API契约、安全模型、关键业务逻辑或跨平台共享层的漂移。

**典型场景**：
- 外部API端点增删或请求/响应格式破坏性变更
- 认证授权模型或权限体系变更
- 核心业务流程逻辑根本性偏离
- 跨平台共享层（如IPC契约）接口变更
- 数据持久化格式破坏性变更
- 第三方集成契约变更
- 合规性或隐私保护相关逻辑变更

**判断标准**：
- 任何外部可观测契约的破坏性变更
- 安全性模型的任何变更
- 关键业务逻辑与规格定义存在根本性偏差
- 影响跨平台兼容性的变更

## 3. 低影响漂移处理流程

```
Agent发现漂移 → 判定为低影响 → 自行补全实现 → 标记Spec-Drift → 继续执行
                                                           ↓
                                              PR描述中说明变更原因
                                                           ↓
                                              Specification Keeper事后审核
```

**详细步骤**：

1. **Agent自行补全实现**：Agent根据上下文和最佳实践自行补全差异部分，
   无需暂停等待授权

2. **提交标记**：在commit message中标记
   ```
   Spec-Drift: [low] <简要描述>
   ```
   示例：`Spec-Drift: [low] 使用快速排序替代归并排序，性能更优且接口不变`

3. **PR描述说明**：在PR描述中解释变更原因，包含以下要素：
   - 原规格要求是什么
   - 实际实现为何偏离
   - 偏离后的行为是否等价

4. **Specification Keeper事后审核**：
   - 审核规则：检查漂移是否引入了规格未覆盖的新行为
   - 如果引入了新行为 → 更新规格文档，将漂移正式纳入规格
   - 如果未引入新行为 → 确认即可，无需更新规格
   - 审核结果记录在知识库中

## 4. 中影响漂移处理流程

```
Agent发现漂移 → 判定为中影响 → 立即暂停 → 上报Orchestrator
                                                    ↓
                                    Orchestrator + System Architect快速评估
                                         ↓                    ↓
                                   方案明确且风险可控       存在不确定因素
                                   授权修改并通知           升级为高影响处理
                                   Specification Keeper
                                   更新规格
```

**详细步骤**：

1. **立即暂停当前子任务**：Agent不得继续执行可能扩大漂移范围的操作

2. **上报Orchestrator**：附带漂移分析报告，包含：
   - 漂移的具体描述和影响范围
   - 受影响的模块和接口列表
   - 建议的处理方案
   - 风险评估初步结论

3. **Orchestrator与System Architect快速评估**（允许自动决策，无需人工介入）：
   - 评估维度：
     - **接口兼容性**：变更是否破坏现有接口契约
     - **数据格式向后兼容性**：变更是否导致旧数据无法解析
     - **测试覆盖影响**：现有测试是否需要大幅修改
   - 评估结论：
     - 方案明确且风险可控 → 授权修改
     - 存在不确定因素 → 升级为高影响漂移处理

4. **授权修改后**：
   - Agent按授权方案实施修改
   - 通知Specification Keeper更新规格文档
   - 在commit message中标记 `Spec-Drift: [medium] <变更描述>`
   - 受影响的测试用例必须同步更新

## 5. 高影响漂移处理流程

```
Agent发现漂移 → 判定为高影响 → 触发人机协作断点 → 等待人工确认
                                                        ↓
                                            Product Manager / 人工负责人
                                                 ↓              ↓
                                           确认规格演进       要求回归规格
                                           更新spec.md       创建回退分支
                                           标记为有意演进     重新实现
                                                ↓
                                    Agent实施授权变更
                                                ↓
                                    Specification Keeper更新规格
                                                ↓
                                    重跑所有受影响测试
```

**详细步骤**：

1. **触发人机协作断点**：
   - 断点类型：`ARCHITECTURE_DECISION` 或 `SPEC_DRIFT`
   - Agent必须暂停，不得自主决策
   - 向人工负责人提交完整的漂移影响分析报告

2. **等待Product Manager或对应人工负责人确认**：
   - 人工确认选项：
     - **确认规格演进**：漂移是合理的，更新规格文档，标记为有意的规格演进
     - **要求回归规格**：漂移不可接受，创建回退分支，Agent重新按规格实现
   - 此级别漂移强制人工介入，Agent无权自主决策

3. **恢复流程**（人工确认后）：
   - Agent按授权方案实施变更
   - Specification Keeper更新规格文档
   - 所有受影响的测试必须重新运行并全部通过
   - 变更记录存入 `.knowledge/experience/decisions/` 目录

## 6. SPEC-CONSISTENCY 质量门禁复核机制

### 6.1 门禁触发时机

- 每个Phase结束时自动触发
- PR合并前强制触发
- Sprint结束时汇总触发

### 6.2 漂移标记聚合

所有Spec-Drift标记在SPEC-CONSISTENCY质量门禁中汇总，按影响等级分类复核。

### 6.3 分级复核流程

| 影响等级 | 复核方式 | 复核人 | 通过条件 |
|---------|---------|--------|---------|
| 低影响 | 批量审核 | Specification Keeper | 无累积风险，未引入规格外新行为 |
| 中影响 | 逐项审核 | Orchestrator | 每项均有授权记录，方案合理 |
| 高影响 | 强制人工签收 | Product Manager | 人工确认已完成，测试全部通过 |

### 6.4 门禁阻断规则

- **任何未解决的高影响漂移** → **BLOCK**：门禁不通过，禁止进入下一阶段
- **任何中影响漂移缺少Orchestrator授权** → **BLOCK**：门禁不通过，需补办授权
- 低影响漂移累积超过阈值（默认5项） → **WARN**：警告但不阻断，建议Specification Keeper集中审核

### 6.5 门禁通过条件

- 所有关键指标达标：
  - 高影响漂移：100%人工确认完成
  - 中影响漂移：100%获得Orchestrator授权
  - 低影响漂移：无累积风险告警
  - 受影响测试：全部通过

## 7. Spec-Drift 标记规范

### 7.1 Commit Message 格式

```
<常规commit信息>

Spec-Drift: [low|medium|high] <简要描述>
```

示例：
```
feat: 优化用户查询接口响应速度

Spec-Drift: [medium] 用户查询接口返回格式从数组变更为分页对象，保持向后兼容
```

### 7.2 PR 标签规范

- 添加 `spec-drift` 标签
- 附加影响等级标签：`spec-drift:low`、`spec-drift:medium`、`spec-drift:high`
- 高影响漂移PR必须标记为 `blocked:awaiting-human-review`

### 7.3 知识库记录格式

存储路径：`.knowledge/experience/decisions/`

文件命名：`spec-drift-<YYYYMMDD>-<序号>.md`

条目结构：

```yaml
drift_id: "SD-20260502-001"
impact_level: "medium"
description: "用户查询接口返回格式变更"
original_spec: "接口返回用户数组"
actual_implementation: "接口返回分页对象，包含users/total/page字段"
resolution: "授权修改，规格已更新"
authorizer: "Orchestrator"
authorized_at: "2026-05-02T14:30:00Z"
spec_updated: true
tests_rerun: true
tests_passed: true
related_commits:
  - "abc1234"
  - "def5678"
```

## 8. 漂移等级升级规则

漂移等级可在评估过程中升级，但不可降级：

- **低 → 中**：Specification Keeper审核时发现漂移实际影响超出预期
- **中 → 高**：Orchestrator评估时发现存在不确定因素或风险不可控
- **禁止降级**：一旦标记为某等级，不得因后续评估而降低等级

升级时必须：
1. 重新按新等级流程处理
2. 更新所有已有标记（commit message、PR标签、知识库记录）
3. 通知所有相关角色

## 9. 特殊场景处理

### 9.1 紧急修复中的漂移

生产环境紧急修复允许临时跳过中影响漂移的暂停流程，但必须：
- 在修复后24小时内补办完整评估流程
- commit message中额外标记 `hotfix`
- 紧急修复不适用于高影响漂移，仍需人工确认

### 9.2 规格文档本身的错误

若Agent发现规格文档存在明显错误（如逻辑矛盾、技术不可行）：
- 按中影响漂移流程处理
- 额外在报告中标注 `spec-error` 标签
- Specification Keeper优先处理此类漂移

### 9.3 跨Agent协作中的漂移

当一个Agent的漂移影响其他Agent的工作范围时：
- Orchestrator负责协调受影响Agent的同步调整
- 在漂移分析报告中列出所有受影响Agent
- 受影响Agent暂停相关工作直到漂移处理完成

```
                    Agent发现实现与规格不一致
                              │
                    ┌─────────┴─────────┐
                    │   影响等级判定      │
                    └─────────┬─────────┘
                              │
           ┌──────────────────┼──────────────────┐
           │                  │                  │
     低影响漂移          中影响漂移          高影响漂移
           │                  │                  │
    Agent自行补全       暂停→上报Orchestrator   触发人机协作断点
           │                  │                  │
    标记[low]           Orchestrator+Architect   等待PM确认
    PR描述说明           快速评估                │
           │              │       │         确认演进/回归规格
           │         方案明确   不确定          │
           │         授权修改   升级为高    Agent实施授权变更
           │              │                  │
    Spec Keeper        通知Spec Keeper     Spec Keeper更新规格
    事后审核            更新规格            重跑受影响测试
           │              │                  │
           └──────────────────┼──────────────────┘
                              │
                    SPEC-CONSISTENCY门禁复核
                              │
                     ┌────────┴────────┐
                     │ 通过             │ 阻断
                     │ 进入下一阶段     │ 修复后重新复核
                     └─────────────────┘
```
