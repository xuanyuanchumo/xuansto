# API 错误码规范

## 错误码格式

错误码采用 6 位编码，格式为 `XXYYZZ`：

```
XX  - 模块编码（2位）
YY  - 错误类别（2位）
ZZ  - 具体错误序号（2位）
```

### 模块编码

| 编码 | 模块 | 编码 | 模块 |
|------|------|------|------|
| 10 | 通用 | 20 | 用户 |
| 30 | 商品 | 40 | 订单 |
| 50 | 支付 | 60 | 消息 |
| 70 | 文件 | 90 | 系统 |

### 错误类别

| 编码 | 类别 | 说明 |
|------|------|------|
| 01 | 参数错误 | 请求参数校验失败 |
| 02 | 认证错误 | 身份认证失败 |
| 03 | 权限错误 | 无操作权限 |
| 04 | 资源不存在 | 请求的资源未找到 |
| 05 | 业务逻辑错误 | 违反业务规则 |
| 06 | 并发冲突 | 数据版本冲突或锁竞争 |
| 07 | 外部服务错误 | 第三方服务调用失败 |
| 08 | 限流熔断 | 请求被限流或服务熔断 |

## 错误处理最佳实践

### 客户端处理

1. **优先判断 HTTP 状态码**，4xx 为客户端错误，5xx 为服务端错误
2. **解析 error.code** 进行精确的错误分支处理，避免依赖 message 文本匹配
3. **401 错误**自动触发 Token 刷新或跳转登录页
4. **429 错误**读取 `Retry-After` 头，按指定时间退避
5. **5xx 错误**采用指数退避重试，最多 3 次
6. **展示用户友好信息**，将 error.message 翻译为用户可读文本

### 服务端处理

1. **统一异常中间件**捕获所有未处理异常并转换为标准错误响应
2. **不暴露内部实现**，5xx 错误不返回堆栈信息或 SQL 语句
3. **记录 traceId**，便于通过日志追踪完整请求链路
4. **区分业务异常与系统异常**，业务异常不触发告警，系统异常触发 PagerDuty
5. **幂等设计**，支付等关键操作通过 idempotency key 防止重复处理
