## 1. 性能需求

### 1.1 Skill加载与响应

| 指标 | 目标值 | 可接受值 | 测量方法 |
|------|--------|----------|----------|
| Skill加载时间 | < 2秒 | < 3秒 | 从触发到Skill提示词注入完成 |
| 模式学习延迟 | < 5秒 | < 8秒 | 从模式输入到学习结果可用 |

Skill加载时间直接影响开发者体验。加载过程包括：Skill元数据解析 → 提示词模板渲染 → 依赖资源预加载 → 上下文注入。任何阶段超时均应记录告警日志。

模式学习延迟指系统从用户行为中提取模式并更新知识库的端到端时间，包含：行为采集 → 特征提取 → 模式匹配 → 知识库写入。

### 1.2 Agent并行与编排

| 指标 | 目标值 | 说明 |
|------|--------|------|
| Agent并行数 | ≥ 10 | 同时运行的独立Agent数量 |
| Agent调度延迟 | < 500ms | 从编排器发出指令到Agent开始执行 |

并行编排应支持以下模式：
- **完全并行**：无依赖关系的Agent同时启动
- **阶段并行**：同一阶段内的Agent并行，阶段间串行
- **流水线并行**：上游Agent产出部分结果后下游即可启动

### 1.3 上下文与知识库

| 指标 | 目标值 | 可接受值 | 测量方法 |
|------|--------|----------|----------|
| 上下文压缩比 | > 90% | > 85% | 压缩后Token数 / 原始Token数 |
| 压缩精度损失 | < 2% | < 5% | 压缩前后语义相似度对比 |
| 知识库检索响应 | < 500ms | < 1秒 | 混合检索（向量+关键词）端到端延迟 |

上下文压缩采用分层策略：
1. **无损压缩**：去除冗余空白、合并重复引用
2. **语义压缩**：摘要长文本、保留关键决策节点
3. **选择性丢弃**：低相关性历史对话、已完成的中间状态

知识库混合检索流程：用户查询 → 向量检索（Top-20） → 关键词检索（Top-20） → 融合排序（RRF） → 返回Top-K。

### 1.4 测试与验证

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 单元测试执行时间 | < 30秒 | 单个模块全部单元测试 |
| 视觉回归对比时间 | < 30秒 | 100张截图的像素级对比 |

单元测试应遵循快速反馈原则，禁止在单元测试中引入网络调用、文件IO等慢速操作。视觉回归对比采用多线程并行像素差异计算，支持忽略区域配置。

### 1.5 桌面应用性能

| 指标 | 目标值 | 可接受值 | 说明 |
|------|--------|----------|------|
| 冷启动时间 | < 2秒 | < 3秒 | 从双击图标到主界面可交互 |
| 热启动时间 | < 0.5秒 | < 1秒 | 从系统托盘恢复到主界面可交互 |
| 空闲内存占用 | < 200MB | < 300MB | 无活跃任务时的内存占用 |
| 活跃内存占用 | < 400MB | < 600MB | 执行Agent编排任务时的内存占用 |
| 安装包大小 | < 100MB | < 150MB | 压缩后安装包体积 |
| 差量更新大小 | < 10MB | < 20MB | 增量更新包体积 |

冷启动优化策略：
- 延迟加载非核心模块（设置页、插件市场等）
- 预编译渲染层资源缓存
- 主进程与渲染进程并行初始化

内存优化策略：
- WebView实例按需创建与销毁
- 大文件采用流式处理，避免全量加载到内存
- 定期执行GC提示，回收未引用资源

## 2. 可靠性需求

### 2.1 Agent故障恢复

- Agent执行异常时自动捕获错误上下文（调用栈、输入参数、中间状态）
- 故障Agent标记为不可用，从调度池中移除
- 恢复策略：自动重试 → 替换Agent → 静默降级，全程不中断用户工作流
- 故障事件写入Decision Log，包含时间戳、Agent ID、错误类型、恢复动作

### 2.2 任务重试策略

| 参数 | 值 | 说明 |
|------|-----|------|
| 最大重试次数 | 3 | 超过后标记任务失败 |
| 退避策略 | 指数退避 | 间隔 = 基础间隔 × 2^重试次数 |
| 基础间隔 | 1秒 | 首次重试等待时间 |
| 最大间隔 | 30秒 | 退避上限 |
| 可重试错误 | 网络超时、模型限流、资源暂不可用 | 不重试：参数校验失败、权限拒绝 |

重试过程应保持幂等性，即重复执行不产生副作用。每次重试前应验证前置条件是否仍然满足。

### 2.3 降级与容错

- **部分Agent失败**：使用可用结果继续执行，在最终输出中标注缺失部分
- **模型服务不可用**：自动切换到备用模型，记录切换事件
- **知识库不可用**：降级为纯提示词模式，跳过知识增强步骤
- **外部服务不可用**：使用本地缓存数据，标注数据时效性

降级决策遵循优先级：数据完整性 > 功能完整性 > 性能最优。任何降级事件均需在Decision Log中记录。

### 2.4 会话与工作流持久化

- **断点续传**：会话中断后可从最近检查点恢复，丢失工作量 < 1个Agent执行周期
- **工作流检查点**：每个阶段完成后自动保存检查点（输入、输出、状态快照）
- **检查点存储**：本地文件系统 + 可选远程同步
- **恢复验证**：恢复后自动验证上下文完整性，缺失部分需重新生成

### 2.5 桌面应用可靠性

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 安装成功率 | > 99% | Windows代码签名后 |
| 安装成功率 | > 98% | macOS公证（Notarized）后 |
| 自动更新成功率 | > 99% | 含回滚机制 |
| 崩溃恢复率 | > 95% | 崩溃后自动恢复会话 |

安装失败应对：
- 预检环境依赖（运行时、系统版本、磁盘空间）
- 提供离线安装包作为备选
- 安装日志自动收集，失败时引导用户上报

自动更新策略：
- 更新前自动创建还原点
- 更新失败自动回滚到上一版本
- 差量更新校验SHA256完整性

| 平台 | 适配级别 | 说明 |
|------|----------|------|
| Claude Code | 原生支持 | 一等公民，全功能可用 |

适配层应抽象IDE差异，核心逻辑不依赖特定IDE API。平台差异通过适配器模式隔离在独立模块中。

协议实现应保持向后兼容，新版本协议特性采用特性检测而非版本判断。

### 3.3 桌面操作系统兼容

| 操作系统 | 最低版本 | 推荐版本 | 架构 |

| macOS | 13 (Ventura) | 14 (Sonoma) | x64, ARM64 |
| Ubuntu | 22.04 LTS | 24.04 LTS | x64 |

跨平台注意事项：
- 文件路径使用平台感知的路径处理库
- 系统调用通过抽象层隔离平台差异
- UI渲染使用跨平台框架原生组件

### 3.4 桌面框架兼容

| 框架 | 版本要求 | 优先级 | 说明 |
|------|----------|--------|------|

框架选择决策树：需要丰富Node生态 → Electron；追求包体与内存极小 → Tauri；需移动端统一 → Flutter。

## 4. 安全性需求

### 4.1 敏感数据保护

- **分类分级**：将数据分为公开、内部、机密、绝密四级
- **传输加密**：所有网络通信使用TLS 1.3+
- **存储加密**：机密及以上数据使用AES-256-GCM加密存储
- **内存安全**：敏感数据使用后立即清零，避免内存残留
- **日志脱敏**：日志中禁止输出密钥、Token、密码等敏感字段，替换为`***REDACTED***`

### 4.2 权限控制

- **最小权限原则**：Agent仅获取完成任务所需的最小权限集
- **权限声明**：每个Agent在注册时声明所需权限，运行时动态校验
- **权限分级**：读取（默认） → 写入（需确认） → 执行（需审批） → 管理（需二次认证）
- **权限审计**：权限授予与使用记录写入审计日志

### 4.3 审计追踪

- **Decision Log**：记录所有关键决策，包含决策时间、决策者、输入、输出、理由
- **操作日志**：记录文件修改、命令执行、网络请求等操作
- **不可篡改**：审计日志采用追加写入，禁止修改和删除
- **可追溯**：每条日志包含唯一Trace ID，支持端到端链路追踪

### 4.4 Agentic安全

遵循OWASP Agentic Top 10安全规范：

| 风险项 | 缓解措施 |
|--------|----------|
| 提示注入 | 输入消毒、指令与数据分离、多轮验证 |
| 敏感数据泄露 | 输出过滤、数据分级、访问控制 |
| 供应链攻击 | 依赖锁定、完整性校验、来源验证 |
| 未授权操作 | 权限边界、操作确认、沙箱执行 |
| 模型拒绝服务 | 请求限流、资源配额、超时熔断 |
| 不安全输出处理 | 输出编码、类型校验、安全渲染 |
| Agent间通信劫持 | 通道加密、身份认证、消息签名 |
| 权限提升 | 最小权限、权限隔离、定期审计 |
| 模型窃取 | 访问控制、使用监控、水印追踪 |
| 责任归因缺失 | 操作签名、审计链、不可抵赖 |

### 4.5 桌面应用安全

- **本地存储加密**：用户凭证、Token等敏感数据使用操作系统密钥链（Keychain/Credential Manager/libsecret）存储
- **IPC安全隔离**：主进程与渲染进程间通信使用白名单校验，禁止任意消息传递
- **代码签名**：所有发布包必须经过代码签名（Windows: Authenticode, macOS: Developer ID）
- **沙箱执行**：Agent代码在受限沙箱中执行，禁止直接访问文件系统和网络
- **自动更新安全**：更新包SHA256校验 + HTTPS传输 + 签名验证

### 4.6 应用商店合规

| 商店 | 要求 | 状态 |
|------|------|------|
| Microsoft Store | MSIX打包、沙箱合规、隐私声明 | 待提交 |
| Mac App Store | 沙箱合规、Hardened Runtime、公证 | 待提交 |
| Snap Store | Snap打包、接口声明 | 评估中 |

## 5. 可观测性需求

### 5.1 核心指标

| 指标 | 目标值 | 采集方式 | 告警阈值 |
|------|--------|----------|----------|
| 首次通过率 | ≥ 80% | 质量门禁通过率统计 | < 70% |
| MTTR（平均修复时间） | < 30min | Bug修复闭环时间统计 | > 60min |
| Agent调用成功率 | ≥ 95% | Agent执行日志统计 | < 90% |
| Token消耗效率 | 有效输出/总Token > 0.6 | Token使用量与有效输出比 | < 0.4 |
| 知识库命中率 | ≥ 70% | 知识检索使用率统计 | < 50% |
| Karpathy准则合规率 | ≥ 90% | 代码审查自动检测 | < 80% |

指标采集架构：
- **采集层**：各模块埋点输出结构化事件
- **聚合层**：实时流式聚合，1分钟粒度
- **存储层**：时序数据库存储，保留90天
- **展示层**：仪表盘 + 趋势图 + 异常标注

### 5.2 桌面应用监控

| 指标 | 目标值 | 采集方式 |
|------|--------|----------|
| 崩溃率 | < 0.1% | 崩溃报告自动上报 |
| 安装成功率 | > 99% | 安装流程埋点统计 |
| 自动更新漏斗 | 检出→下载→安装各阶段转化率 > 95% | 更新流程各阶段埋点 |
| ANR率（应用无响应） | < 0.5% | 主线程阻塞检测 |
| 用户留存率（7日） | > 60% | 匿名使用统计 |

崩溃报告应包含：异常类型、调用栈、操作系统版本、应用版本、内存状态。用户可选择是否上报，默认匿名化处理。

## 6. 成本优化需求

### 6.1 模型选择策略

| 任务复杂度 | 推荐模型 | 典型场景 | 预估Token消耗 |
|-----------|----------|----------|--------------|
| 简单 | 轻量模型 | 代码格式化、简单查询、文档更新 | < 1K |
| 中等 | 标准模型 | 功能实现、测试编写、代码审查 | 1K-10K |
| 复杂 | 重量模型 | 架构设计、安全审计、复杂Bug修复 | 10K-50K |
| 专家 | 旗舰模型 | 跨系统重构、性能调优、安全漏洞挖掘 | 50K+ |

模型选择决策流程：
1. 编排器根据任务描述评估复杂度等级
2. 查询模型可用性与当前负载
3. 选择满足质量要求且成本最低的模型
4. 执行过程中若检测到复杂度升级，动态切换模型

### 6.2 上下文裁剪

- **知识库检索裁剪**：按相关性排序，仅注入Top-K条目（K≤5），避免冗余上下文
- **文件按需读取**：长文件按需分页读取，避免一次性加载整个文件到上下文
- **历史对话压缩**：超过阈值时自动摘要压缩，保留关键决策节点
- **依赖分析裁剪**：仅加载直接依赖的模块定义，间接依赖按需展开

裁剪优先级：当前任务直接相关 > 近期决策上下文 > 历史模式参考 > 通用知识背景。

### 6.3 并行编排成本预算

- **单次任务Token上限**：根据任务复杂度设定，简单1K、中等10K、复杂50K
- **并行预算公式**：总Token预算 = 单Agent预算 × min(并发数, 3)
- **超预算降级**：超出预算时自动降级为串行执行，减少并行Token消耗
- **预算预警**：消耗达80%时发出预警，达95%时强制降级

预算控制应在编排层实现，而非依赖模型端限流，确保成本可控性。

## 7. 系统复杂度管理

### 7.1 精简模式

- **轻量启动**：仅加载核心Agent（规划器、执行器、验证器），其余按需激活
- **配置预设**：提供"极简/标准/完整"三档预设，控制Agent激活数量
- **按需扩展**：当任务复杂度超出当前模式能力时，自动激活额外Agent
- **资源回收**：空闲超过5分钟的Agent自动休眠，释放上下文资源

| 模式 | 激活Agent数 | 适用场景 |
|------|------------|----------|
| 极简 | 3 | 快速原型、单文件修改 |
| 标准 | 10 | 功能开发、测试编写 |
| 完整 | 41 | 架构重构、安全审计、全流程编排 |

### 7.2 文档分层

- **L0-摘要层**：一句话描述模块职责，面向快速浏览
- **L1-接口层**：公共API与配置项说明，面向集成使用
- **L2-设计层**：架构决策与实现原理，面向深度理解
- **L3-细节层**：内部实现与边界情况，面向维护开发

文档分层原则：
- 默认只展示L0和L1，减少认知负担
- L2和L3按需展开，通过折叠或链接方式访问
- 每层文档独立版本管理，L0变更频率最低

### 7.3 负载监控

- **Agent负载仪表盘**：实时显示各Agent的CPU、内存、Token消耗
- **编排队列监控**：显示待执行、执行中、已完成任务数量与分布
- **瓶颈检测**：自动识别执行时间最长的Agent和阶段
- **自动扩缩**：根据队列深度和平均等待时间，动态调整Agent池大小

| 监控项 | 采集频率 | 保留周期 | 告警条件 |
|--------|----------|----------|----------|
| Agent CPU/内存 | 10秒 | 7天 | 持续>80%达5分钟 |
| Token消耗速率 | 1分钟 | 30天 | 超预算120% |
| 队列深度 | 10秒 | 7天 | 持续>20达3分钟 |
| 平均等待时间 | 1分钟 | 7天 | >30秒 |

## 性能降级3级策略

当系统资源不足或响应延迟超标时，按以下3级策略逐步降级。

### L1: 减少并行（Reduce Parallelism）

| 项目 | 内容 |
|------|------|
| 触发条件 | 平均响应延迟>10秒 或 Token消耗率>预算100% |
| 降级动作 | max_concurrent_agents从3降至2；暂停非关键Agent |
| 恢复条件 | 平均响应延迟<5秒 且 Token消耗率<预算80% 持续5分钟 |
| 用户通知 | `[L1-DEGRADE] 系统负载较高，已减少并行Agent数量` |

### L2: 精简模式（Lean Mode）

| 项目 | 内容 |
|------|------|
| 触发条件 | L1持续10分钟未恢复 或 平均响应延迟>30秒 |
| 降级动作 | 仅激活核心Agent（Orchestrator+FE/BE Dev+Unit Tester+Security Auditor）；禁用设计层、文档层、运维层 |
| 恢复条件 | 平均响应延迟<5秒 且 Token消耗率<预算70% 持续10分钟 |
| 用户通知 | `[L2-DEGRADE] 系统进入精简模式，仅核心Agent运行` |

### L3: 最小串行（Minimal Serial）

| 项目 | 内容 |
|------|------|
| 触发条件 | L2持续15分钟未恢复 或 Token消耗率>预算150% |
| 降级动作 | 所有Agent串行执行；仅Orchestrator+1个执行Agent运行 |
| 恢复条件 | 人工确认恢复 |
| 用户通知 | `[L3-DEGRADE] 系统进入最小串行模式，需人工确认恢复` |

### 降级事件记录

所有降级事件记录至 `.skill-logs/degradation-events.jsonl`：

```json
{
    "timestamp": "2026-05-02T10:30:00Z",
    "level": "L1",
    "trigger_reason": "avg_response_delay_12s",
    "action_taken": "max_concurrent_agents_3_to_2",
    "previous_level": "NORMAL",
    "recovery_condition": "avg_delay<5s AND token_rate<80% FOR 5min"
}
```

### 降级不可逆规则
- 降级只能逐级恢复（L3→L2→L1→NORMAL），不可跳级
- 每级恢复需满足对应恢复条件并持续指定时间
- L3恢复必须人工确认
