# Xuansto-Skill v3.0 整合需求规格说明

## 一、项目概览与升级矩阵

### 1.1 项目定位

**Xuansto Skill** 是一个多Agent自主开发编排器，核心理念为 **SDD（规格驱动开发）+ TDD（测试驱动开发）融合**，支持 Web + Desktop（Electron/Tauri/Flutter）全生命周期开发。

核心入口文件为 [SKILL.md](file:///d:/Projects/TraeProjects/skiller/.trae/skills/xuansto-skill/SKILL.md)。

### 1.2 v3.0 升级目标

将7个经过验证的开源Claude Code Skill的核心能力 + v1.8需求规格中的知识库服务层、Token优化体系、安全框架集成、工程规范增强等整合进xuansto-skill，使其从**41 Agent / 9 Phase / 37 Gate**升级为**48 Agent / 9 Phase / 53 Gate / 23 Command**的超级编排器，实现从"交互式开发助手"到"自主化开发引擎"的跃迁。

### 模块1：Superpowers 可组合技能引擎

**来源**: [github.com/obra/superpowers](https://github.com/obra/superpowers) | 作者: Jesse Vincent | 476K安装

#### 核心能力提取

| 能力 | 原始实现 | xuansto集成方式 |
|:-----|:---------|:---------------|
| **Brainstorming** | 苏格拉底式6阶段对话(Discovery→Option→Design→Reflect→Commit→Transition) | 增强Phase 1需求澄清，新增Brainstorming Facilitator Agent |
| **TDD强制** | Red-Green-Refactor循环，测试必须先失败 | 增强Phase 4 TDD实现，强化GATE-007 |

**来源**: [github.com/anthropics/claude-code](https://github.com/anthropics/claude-code) (Ralph Wiggum Plugin) | Anthropic官方 + Geoffrey Huntley | 145K安装

#### 核心能力提取

| 能力 | 原始实现 | xuansto集成方式 |
|:-----|:---------|:---------------|
| **Stop Hook机制** | 拦截Agent退出(exit code 2)→重新注入提示 | 增强Orchestrator Agent |
| **Completion Promise** | `<promise>DONE</promise>` 标记任务完成 | 新增LOOP-COMPLETION门禁 |
| **自引用迭代** | Agent看到自己之前的工作(文件+git历史)→自主改进 | 与Module 2(Planning Files)协同 |
| **Max Iterations** | 安全网防止无限循环 | 新增ITERATION-BUDGET门禁 |
| **Cancel机制** | /cancel-ralph随时取消 | 新增/cancel-loop命令 |

#### Agent增强

**Orchestrator** (编排层) → 增加 **Loop Enforcement** 能力

```
新增自主迭代模式:
  触发: /loop命令 或 /sprint --autonomous
  工作流:
    1. 初始化循环:
       - 创建.agent_cache/<task>/loop-state.md
       - 记录原始提示+完成标准+最大迭代数
       - 初始化Planning Files(Module 2)
    2. 迭代执行:
       - Agent执行当前阶段任务
       - Agent尝试"完成"时:
         a. 检查completion promise
         b. 检查Planning Files中的完成标准
         c. 检查质量门禁通过状态
       - 如果未真正完成:
         → 拦截退出
         → 注入迭代上下文:
           "🔄 迭代 N | 完成标准: [列出] | 已完成: [列出] | 待完成: [列出]"
         → Agent继续工作
       - 如果已完成:
         → 允许退出
         → 归档Planning Files到.knowledge/
    3. 安全机制:
       - 最大迭代数(默认50，可配置)
       - 连续3次无进展→暂停+报告
       - Token预算耗尽前→优雅退出
       - /cancel-loop随时取消
    4. 与Planning Files协同:
       - 每次迭代开始→重新读取task_plan.md
       - 每次迭代结束→更新progress.md
       - 发现新信息→更新findings.md
```

#### 新增命令

| 命令 | 说明 | 参数 |
|:-----|:-----|:-----|
| `/loop` | 启动自主迭代循环 | `[prompt]` --max-iterations 50 --completion-promise "DONE" |
| `/cancel-loop` | 取消当前迭代循环 | 无 |

#### 新增脚本

| 脚本 | 语言 | 功能 |
|:-----|:-----|:-----|
| `loop-guard.py` | Python | 循环状态管理+迭代计数+进度检测 |
| `completion-verifier.py` | Python | 验证completion promise+质量门禁+完成标准 |

#### 新增质量门禁

| 门禁 | 阶段 | 检查项 | 阻塞级别 |
|:-----|:-----|:-------|:---------|
| LOOP-COMPLETION | 跨阶段 | Completion promise已输出+所有完成标准已满足+质量门禁通过 | BLOCK |
| ITERATION-BUDGET | 跨阶段 | 迭代数<=最大值+连续无进展<=3次+Token预算未耗尽 | WARN+BLOCK |

### 5.1 双引擎架构

| 引擎 | 职责 | 技术选型 |
|:-----|:-----|:---------|
| **SQLite** | 结构化数据存储 + FTS5全文检索 + 版本追踪 | knowledge.db单文件，零部署 |
| **ChromaDB** | 向量嵌入存储 + HNSW语义检索 | chroma_data/目录，HNSW索引 |

### 5.2 服务接口

| 接口类型 | 实现 | 说明 |
|:---------|:-----|:-----|
| **REST API** | knowledge_server/main.py + api.py | GET/POST/PUT/DELETE标准CRUD |
| **MCP Tool** | knowledge_server/mcp_server.py | 5个Tool函数供AI模型直接调用 |
| **混合检索** | knowledge_server/hybrid_search.py | RRF(Reciprocal Rank Fusion)融合FTS5+Chroma结果 |

### 5.3 核心功能

| 功能 | 说明 | 性能目标 |
|:-----|:-----|:---------|
| **关键词检索** | FTS5 + BM25排序 | <500ms |
| **语义检索** | Chroma HNSW向量检索 | <200ms |
| **混合检索** | RRF融合关键词+语义 | <200ms |
| **单条写入** | 含去重检查 | <100ms |
| **知识去重** | 内容哈希+语义相似度双重检测 | 准确率>=95% |
| **版本追踪** | 每条知识version字段，支持回滚 | 原子操作 |
| **首次导入** | 扫描.knowledge/下Markdown文件自动导入 | 断点续传 |
| **一致性保障** | SQLite与Chroma双向同步，差异自动修复 | 差异数=0 |

### 5.4 一致性保障

- **写入路径**：Markdown源文件 → SQLite索引 → Chroma嵌入（同步写入）
- **读取路径**：Chroma语义检索 + SQLite FTS5关键词检索 → RRF融合
- **降级策略**：Chroma不可用时降级为纯FTS5；SQLite不可用时降级为v1.6文件检索

#### 脚本语言选型矩阵

| 使用场景 | 首选语言 | 扩展名 | 运行时 |
|:---------|:---------|:-------|:-------|
| **通用文件修改** | Python 3.10+ | `.py` | python/python3 |
| **Web项目前端操作** | Node.js | `.js` | node |
| **系统级操作** | PowerShell 7+ | `.ps1` | pwsh |
| **构建打包** | PowerShell 7+ | `.ps1` | pwsh |

**强制约束**：
- Shell脚本(.sh) **仅限CI/CD流水线和容器内操作**，Agent本地不得创建 [强制]
- 任何可跨平台实现的文件修改操作，**优先使用Python脚本** [强制]

#### 5步闭环生命周期

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 1.创建   │───▶│ 2.审查   │───▶│ 3.执行   │───▶│ 4.验证   │───▶│ 5.清理   │
│ 脚本     │    │ 脚本     │    │ 脚本     │    │ 修改结果  │    │ 脚本文件  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

- **创建**：写入`.knowledge/temp-scripts/`，文件名格式`{agent-name}-{task-hash}-{timestamp}.{ext}`
- **审查**：自我审查+安全沙箱约束校验，安全敏感路径提交Code Reviewer审查
- **执行**：Python/JS脚本120秒超时，PowerShell脚本300秒超时
- **验证**：文件存在性+编码+内容完整性+语法+测试
- **清理**：验证通过后**必须删除临时脚本** [强制]

#### 安全沙箱约束

| 约束项 | 规则 | 级别 |
|:-------|:-----|:-----|
| 文件系统写入白名单 | 仅允许写入任务指定目标文件，禁止系统目录 | BLOCK |
| 文件系统读取范围 | 仅允许读取项目目录+标准库 | BLOCK |
| 进程调用 | 禁止subprocess.run/os.system/child_process.exec | BLOCK |
| 网络访问 | 禁止requests.get/fetch/urllib/Invoke-WebRequest | BLOCK |
| 动态代码执行 | 禁止eval/exec/Function构造器 | BLOCK |
| 文件删除范围 | 禁止shutil.rmtree/os.unlink删除非临时文件 | BLOCK |

### 8.2 并发任务执行

#### Token预算分配策略

| 策略 | 说明 | 适用场景 |
|:-----|:-----|:---------|
| **均分策略** | Token预算平均分配 | 同优先级、同类型任务并发 |
| **优先级加权** | P0:3.0/P1:2.0/P2:1.0权重 | 关键路径任务与辅助任务并发 |
| **主从策略** | 主任务70%，从任务30% | 主功能开发+辅助文档/测试 |
| **动态调整** | 运行时监控消耗速率，压缩过快任务 | 长时间复杂并发场景 |

#### 上下文隔离机制

| 隔离维度 | 隔离规则 | 实现方式 |
|:---------|:---------|:---------|
| **会话上下文** | 每个并发Agent独立会话历史 | Orchestrator分配独立上下文槽 |
| **文件访问** | 不得同时修改同一文件 | 文件锁+Orchestrator写队列 |
| **知识库读取** | 可同时读取，各自缓存 | 读取快照+本地缓存 |
| **Spec引用** | 共享只读Spec快照 | Spec版本号+变更广播 |

#### 知识库写入乐观锁

```
1. Agent A 读取知识条目（获得 version=N）
2. Agent B 读取同一知识条目（获得 version=N）
3. Agent A 写入（携带 version=N）→ 匹配 → 成功，version=N+1
4. Agent B 写入（携带 version=N）→ 不匹配 → 拒绝 → 触发冲突解决
```

**冲突解决优先级**：自动合并 > 时间戳优先 > Orchestrator裁决 > 人工介入

### 8.3 编码与注释规范

| 规范项 | 强制要求 | 验证方式 |
|:-------|:---------|:---------|
| **编码格式** | UTF-8 without BOM | CI中file命令或编码检测脚本 |
| **行尾序列** | LF(`\n`) | Git core.autocrlf配置+CI检查 |
| **Python编码声明** | 禁止`# -*- coding: utf-8 -*-` | CI脚本扫描+Python AST解析 |
| **注释语言** | 业务注释必须使用简体中文 | 注释语言检测脚本 |
| **Git提交信息** | 约定式提交，主体内容中文描述 | Code Reviewer审查 |

## 九、质量保障增强

> 来源：v1.8需求第十二、九章 | 根因分析 + 自测试 + 文档规范

### 9.1 根因分析(RCA)框架

当发生测试失败、安全漏洞或运行时异常时，负责修复的Agent必须遵循RCA模板：

```markdown
## 根因分析报告

- **症状**：[可观察到的错误现象，精确到日志/堆栈]
- **直接原因**：[导致症状的直接代码缺陷或配置错误]
- **根本原因**：[为什么会存在这个直接原因？流程/设计/假设的哪个环节出错？]
- **修复措施**：[解决根本原因的具体代码变更]
- **预防措施**：[如何防止同类问题再次发生？]
- **影响范围评估**：[此根本原因可能影响的其它模块/服务]
```

此报告自动存储为经验知识库条目（`experience/errors/`），供未来Code Reviewer和开发者检索。

### 9.2 安全修复闭环

```
AI Penetration Tester 发现漏洞 → 自动创建安全工单
  → Security Auditor 验证并确认 → 指派Developer Agent
  → Developer 实施修复 → Test Architect生成回归测试
  → AI Penetration Tester 复测 → 闭环完成，经验沉淀
```

## 十、非功能性需求

> 来源：v1.8需求第十三章

### 10.1 性能需求

| 指标 | 目标值 | 测试方法 |
|:-----|:-------|:---------|
| Skill加载时间 | <2秒 | 冷启动计时 |
| Agent并行数（系统级） | >=10个同时运行 | 压力测试 |
| 上下文压缩比 | >90%（精度损失<2%） | 长对话测试 |
| 知识库FTS5检索 | <500ms | 压测 |
| 知识库混合检索 | <200ms | API端到端延迟 |
| 知识库单条写入 | <100ms（含去重<300ms） | API端到端延迟 |
| 桌面应用冷启动 | <2秒（目标），<3秒（可接受） | 桌面性能测试 |
| 桌面应用内存 | <200MB（空闲），<400MB（活跃） | 桌面性能测试 |
| 安装包大小 | <100MB（压缩后），差量更新<10MB | 构建产物检查 |

### 10.2 三级性能降级策略

| 降级级别 | 触发条件 | 降级动作 | 恢复条件 |
|:---------|:---------|:---------|:---------|
| **L1: 减少并行** | Agent并行<10或内存>400MB | 并行Agent数从10降至5，非关键Agent串行 | 内存<300MB持续5分钟 |
| **L2: 精简模式** | L1持续5分钟或加载>5秒 | 仅保留编排+工程+测试+安全核心Agent(~15个) | 系统资源恢复+用户确认 |
| **L3: 最小串行** | L2持续10分钟或Token耗尽 | 仅Orchestrator+1工程+1测试，串行执行 | 用户手动重置或新会话 |

**降级原则**：降级不可跳级(L1→L2→L3)，恢复可跳级(L3→L1)；每次降级必须通知用户。

### 10.3 可靠性需求

| 指标 | 目标值 |
|:-----|:-------|

| 工作流检查点/恢复 | 支持持久化状态，故障后从检查点恢复 |
| Orchestrator故障 | Specification Keeper临时接管（串行降级），30秒内恢复 |
