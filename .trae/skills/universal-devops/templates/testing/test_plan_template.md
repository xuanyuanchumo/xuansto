## 4. 测试策略

### 4.1 各类型详细策略

#### 单元测试策略

| 维度 | 策略 |
|------|------|
| **覆盖率目标** | 行覆盖率 ≥ 80%，分支覆盖率 ≥ 70% |
| **框架选择** | 前端(Jest + Testing Library), 后端(JUnit 5 + Mockito) |
| **测试原则** | FAST: Fast(快), Independent(独立), Self-validating(自验证), Timely(及时) |
| **Mock原则** | 只Mock外部依赖(DB/HTTP/API)，不Mock被测单元内部逻辑 |
| **CI集成** | 每次PR触发，失败则阻止合并 |

#### API接口测试策略

| 维度 | 策略 |
|------|------|
| **测试层级** | 契约测试(请求/响应结构) + 业务逻辑测试 + 异常场景测试 |
| **数据准备** | 每个用例独立的数据Setup/Teardown，不依赖执行顺序 |
| **断言方式** | HTTP状态码 + Response Body结构 + Business字段值 |
| **认证处理** | 通过前置步骤获取有效Token，测试未认证场景使用过期Token |
| **自动化程度** | P0接口100%自动化，P1接口≥80%自动化 |

#### E2E测试策略

| 维度 | 策略 |
|------|------|
| **核心路径** | 注册→登录→下单→支付→查看订单（主Happy Path） |
| **关键分支** | 登录失败→找回密码→重置密码→重新登录 |
| **跨页面** | 首页→商品列表→商品详情→加入购物车→结算页 |
| **执行频率** | ST阶段每日执行，上线前全量执行 |
| **环境** | Staging环境，使用接近生产的数据量 |

#### 性能测试策略

| 场景 | 并发数 | 持续时间 | 目标指标 | 加压方式 |
|------|--------|----------|----------|----------|
| 基准负载 | 500并发 | 10min | P99<200ms, CPU<60% | 阶梯递增 |
| 正常负载 | 2000并发 | 30min | P99<500ms, 无错误 | 稳定负载 |
| 峰值负载 | 5000并发 | 10min | P99<1000ms, 错误率<1% | 突发流量 |
| 耐久测试 | 1000并发 | 2h | 无内存泄漏 | 持续加压 |
| 破坏性测试 | 10000并发 | 5min | 系统不崩溃 | 极限压力 |

#### 安全测试策略

| 测试类别 | 检查项 | 工具 | 严重级别 |
|----------|--------|------|----------|
| **注入攻击** | SQL注入/XSS/命令注入 | OWASP ZAP + DAST扫描 | 🔴 Critical |
| **认证安全** | Token暴力破解/Session固定化 | Burp Suite Intruder | 🔴 Critical |
| **数据泄露** | 敏感信息明文传输/存储 | Wireshark + 日志审计 | 🔴 Critical |
| **访问控制** | 越权访问(IDOR)/水平越权 | 手工测试 | 🟠 High |
| **CSRF防护** | 跨站请求伪造 | Burp Suite | 🟠 High |
| **依赖漏洞** | 第三方库已知CVE | Snyk / Dependabot | 🟡 Medium |

| **S4** | 建议(Suggestion) | UI/UX改进、体验优化 | 下个迭代 | 排期考虑 | 按钮颜色不够醒目 |

```
                                    ├──→ WONTFIX(不予修复) → CLOSED
                                    ├──→ DUPLICATE(重复) → CLOSED
                                    └──→ CANNOT_REPRODUCE(无法复现) → NEED_INFO → ... ( reopen if needed )
```
