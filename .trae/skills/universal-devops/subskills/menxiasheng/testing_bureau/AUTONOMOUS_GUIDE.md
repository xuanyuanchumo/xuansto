# 测试验证局 自主操作指南 (Autonomous Operation Guide)

## 概述
本指南定位为测试验证局的自主操作规范，指导AI在没有显式脚本调用的情况下，自主执行测试策略制定、测试用例生成、测试优先级排序和测试结果分析的核心职责。测试验证局是门下省质量保障体系的核心执行机构，负责确保每次代码变更都经过充分且高效的验证，在有限资源下最大化测试覆盖率和缺陷发现率。

## 核心原则
- **风险驱动原则**：测试投入与变更风险成正比，高风险区域获得更多测试资源
- **分层递进原则**：从单元到集成再到E2E，逐层验证，不越级跳步
- **自动化优先原则**：所有可重复的测试场景必须实现自动化，减少人工介入
- **反馈速度原则**：快速失败的测试优先执行，缩短问题发现周期
- **可追溯性原则**：每个测试用例都能追溯到需求/变更/Bug编号
- **持续优化原则**：根据测试通过率、执行时间和缺陷发现效率持续调整策略

## 自主操作流程

### 阶段一：感知（Perceive）

**变更信息收集：**

1. **Git Diff深度分析**
   - 解析commit/PR的完整diff内容
   - 识别变更类型分布：
     - 新增文件 / 新增函数 / 新增类
     - 修改函数体 / 修改签名 / 修改配置
     - 删除代码 / 重命名 / 移动文件
   - 统计变更规模指标：文件数、函数数、行数、复杂度变化

2. **依赖图追踪**
   - 构建被修改模块的直接依赖关系图
   - 追踪间接依赖链（2-3层深度）
   - 识别被修改接口的实现者和调用者
   - 标记共享数据结构的使用者

3. **API变更影响面评估**
   - 检测公开API的签名变更（破坏性变更标记）
   - 检测返回值结构变更
   - 检测异常行为变更（新增抛出异常类型）
   - 检测配置项默认值变更
   - 评估下游消费者的兼容性影响

4. **现有测试资产盘点**
   - 扫描已有测试文件的覆盖范围
   - 识别与变更相关的既有测试用例
   - 评估现有测试的充分性和时效性
   - 定位需要更新或废弃的过期测试

5. **项目上下文理解**
   - 确认使用的测试框架和工具链（Jest/pytest/go-test等）
   - 了解项目的测试目录结构和命名约定
   - 识别Mock/Fixture/Factory等测试基础设施的可复用性
   - 了解CI/CD流水线中的测试阶段配置

### 阶段二：决策（Decide）

**测试策略自主制定框架：**

```
输入：变更分析结果 + 项目上下文
    │
    ▼
┌─────────────────────────────────────┐
│         测试策略决策引擎             │
├─────────────────────────────────────┤
│                                     │
│  变更类型 ──→ 测试层级选择           │
│  ├─ 纯逻辑变更 → 单元测试为主        │
│  ├─ 接口变更 → 单元+集成测试        │
│  ├─ 数据模型变更 → 单元+集成+E2E    │
│  ├─ 基础设施变更 → 集成+E2E测试     │
│  └─ UI交互变更 → E2E测试为主       │
│                                     │
│  影响范围 ──→ 测试广度决策          │
│  ├─ 单文件变更 → 精准测试           │
│  ├─ 模块级变更 → 模块内全量测试     │
│  ├─ 跨模块变更 → 关联路径全量测试   │
│  └─ 全局变更 → 回归测试套件        │
│                                     │
│  风险等级 ──→ 测试强度调节          │
│  ├─ 高风险 → 边界值+异常路径全覆盖  │
│  ├─ 中风险 → 正常路径+关键边界      │
│  └─ 低风险 → 快速冒烟即可          │
│                                     │
└─────────────────────────────────────┘
    │
    ▼
输出：定制化测试计划（含优先级和时间估算）
```

**各测试层级的自主判定标准：**

| 层级 | 覆盖目标 | 自主触发条件 | 执行方式 | 典型耗时 |
|------|----------|--------------|----------|----------|
| 单元测试 | 变更函数的所有分支路径 | 函数逻辑变更 | Mock外部依赖 | 秒级 |
| 集成测试 | 跨模块交互的正确性 | 接口/数据流变更 | 部分真实依赖 | 分钟级 |
| E2E测试 | 完整用户操作流程 | UI/API端点变更 | 全栈环境 | 分钟-小时级 |
| 性能测试 | 关键路径基准回归 | 算法/查询/缓存变更 | 基准对比 | 分钟-十分钟级 |
| 安全测试 | 输入验证和权限控制 | 认证/输入处理变更 | 攻击向量模拟 | 分钟级 |

**测试优先级自主排序算法：**

```
P0 - 必须全量测试（阻塞合并条件）:
  ├── 直接变更的函数/方法
  ├── 公开API的契约测试
  ├── 数据持久化操作的完整性
  ├── 认证和授权相关逻辑
  └── 支付/订单等核心业务流程

P1 - 抽样+重点测试（强烈建议）:
  ├── 间接影响的调用方（上游消费者）
  ├── 共享数据结构的读写一致性
  ├── 配置变更的影响范围
  ├── 错误处理和降级逻辑
  └── 日志和监控埋点正确性

P2 - 冒烟测试即可（可选增强）:
  ├── 未受影响的相邻模块
  ├── 静态资源和样式文件
  ├── 文档和注释变更
  └── 开发工具和脚本更新
```

**TDD自主节奏控制策略：**

| 代码复杂度特征 | TDD粒度建议 | 步骤节奏 |
|---------------|-------------|----------|
| 圈复杂度 ≤5 | 函数级TDD | 红→绿→重构，每个函数一个周期 |
| 圈复杂度 6-10 | 功能点级TDD | 按功能点分批编写测试，每批3-5个用例 |
| 圈复杂度 >10 | 行为级TDD | 先写行为规格（BDD），再拆分为单元测试 |
| 涉及异步/并发 | 场景级TDD | 按时序场景组织测试，包含竞态条件用例 |
| 涉及外部服务 | 契约级TDD | 先定义服务契约（Pact），再实现和验证 |

### 阶段三：执行（Execute）

#### 测试用例自主生成规范

**单元测试生成规则：**

```python
# 对于每个被测函数，自动生成以下测试维度：

def generate_unit_tests(function_info):
    tests = []
    
    # 1. 正常路径测试（Happy Path）
    for valid_input in get_valid_inputs(function_info):
        tests.append(create_test_case(
            name=f"test_{function_name}_with_valid_{input_desc}",
            input=valid_input,
            expected=calculate_expected(valid_input),
            category="happy_path"
        ))
    
    # 2. 边界值测试（Boundary Values）
    for boundary in get_boundary_values(function_info):
        tests.append(create_test_case(
            name=f"test_{function_name}_at_boundary_{boundary_desc}",
            input=boundary,
            expected=handle_boundary(boundary),
            category="boundary"
        ))
    
    # 3. 异常路径测试（Error Paths）
    for error_scenario in get_error_scenarios(function_info):
        tests.append(create_test_case(
            name=f"test_{function_name}_{error_scenario}",
            input=error_scenario.input,
            expected_exception=error_scenario.exception_type,
            category="error_handling"
        ))
    
    # 4. 特殊值测试（Edge Cases）
    for special in get_special_values(function_info):
        tests.append(create_test_case(
            name=f"test_{function_name}_special_{special_desc}",
            input=special,
            expected=handle_special(special),
            category="edge_case"
        ))
    
    return tests
```

**集成测试生成规则：**
- 识别跨模块的数据流：从入口到出口的完整路径
- 对每个数据流路径生成正向和反向测试
- 包含中间状态的一致性检查
- Mock不可控的外部依赖（第三方API、消息队列等）

**E2E测试生成规则：**
- 从用户故事或需求描述中提取用户旅程
- 将用户旅程拆分为可执行的步骤序列
- 为每个步骤定义前置条件和断言
- 生成正向流程、异常流程、回退流程三个变体

**性能测试基线管理：**
- 首次运行时建立性能基线（记录响应时间P50/P95/P99）
- 后续运行与基线对比，偏差超过阈值则告警
- 自动识别性能退化点并关联到具体变更

**安全测试攻击向量库：**

| 攻击类别 | 测试方法 | 目标组件 |
|----------|----------|----------|
| SQL注入 | 参数化SQL bypass尝试 | 数据访问层 |
| XSS攻击 | 脚本注入payload | 前端渲染层 |
| CSRF攻击 | 跨站请求伪造 | 表单提交/API调用 |
| 认证绕过 | Token篡改/Session劫持 | 认证中间件 |
| �限提升 | 角色切换/IDOR | 授权检查点 |
| DDoS模拟 | 高频请求压测 | 限流/熔断机制 |

#### Mock策略自主决策

```
何时使用Mock？
├── 外部服务依赖（数据库/缓存/消息队列/API）→ Mock
├── 不可确定的行为（时间/随机数/UUID）→ Stub
├── 昂贵或慢速操作（网络IO/文件系统）→ Fake/Spy
└── 需要验证交互行为（是否调用了某方法）→ Spy

何时不使用Mock？
├── 被测对象本身就是集成点 → 使用真实依赖
├── Mock会隐藏真实Bug → 使用集成测试替代
├── 测试对象是数据转换逻辑 → 直接传参测试
└── 验证的是最终行为而非过程 → E2E测试
```

### 阶段四：Verify（Verify）

**测试执行结果自主分析方法：**

1. **通过率分析**
   - 全量通过：标记为绿色，允许合并
   - 部分失败：按失败原因分类（代码缺陷/测试缺陷/环境问题/数据问题）
   - 全量失败：立即阻断，启动根因分析流程

2. **失败分类与归因：**
   ```
   失败测试用例
     │
     ├─ 断言错误 → 代码Bug（需修复代码）
     │   ├─ 实际值与预期不符 → 逻辑缺陷
     │   └─ 抛出未预期的异常 → 异常处理缺失
     │
     ├─ 超时错误 → 性能问题或环境瓶颈
     │   ├─ 单个用例超时 → 该路径性能退化
     │   └─ 批量超时 → 环境/基础设施问题
     │
     ├─ Setup/Teardown错误 → 测试环境问题
     │   ├─ 数据初始化失败 → Fixture/Seed数据损坏
     │   └─ 清理失败 → 资源泄漏导致状态污染
     │
     └─ Import/编译错误 → 依赖或配置问题
         ├─ 缺少依赖包 → 需要安装或更新lockfile
         └─ 类型不匹配 → 接口变更后测试未同步更新
   ```

3. **覆盖率有效性评估：**
   - 行覆盖率 >80% 且 分支覆盖率 >70%：合格
   - 行覆盖率 >80% 但 分支覆盖率 <70%：补充边界测试
   - 行覆盖率 <80%：识别未覆盖区域并补充测试
   - 特别关注：新增代码的覆盖率必须达到阈值

4. **测试稳定性检测：**
   - 识别Flaky Test（间歇性失败的测试）
   - 分析Flaky根因：竞态条件/时序依赖/共享状态污染
   - 对Flaky Test标记警告，建议隔离或修复

5. **测试执行效率评估：**
   - 总执行时间是否在可接受范围内（通常<10分钟为理想）
   - 识别执行时间最长的Top 5测试用例
   - 建议优化方向：并行化/减少Setup开销/精简断言

## 典型自主场景

### 场景1：PR提交后的自主测试编排
**触发条件**：检测到新的Pull Request创建或代码推送
**自主执行步骤**：
1. 解析PR diff，提取变更文件列表和变更类型
2. 运行依赖图分析，构建影响范围映射
3. 应用测试优先级算法，将受影响测试用例分级为P0/P1/P2
4. 执行P0级别全量测试（阻塞条件）
5. P0全部通过后，并行执行P1抽样测试和P2冒烟测试
6. 汇总测试结果，生成结构化报告
7. 如有失败，进行智能归因分析，区分代码缺陷vs测试缺陷
8. 在PR评论区发布测试结果摘要，附带详细报告链接
9. 根据测试结果设置PR标签（`tests-passing` / `tests-failing` / `tests-skipped`）

**预期输出**：
- PR上的测试结果状态标签
- 结构化的测试执行报告
- 失败用例的根因分析和修复建议
- 覆盖率变化趋势和缺口提示

### 场景2：夜间回归测试自主执行
**触发条件**：每日定时任务（如凌晨2:00）
**自主执行步骤**：
1. 拉取最新main分支代码
2. 执行完整的回归测试套件（全量P0+P1）
3. 收集性能基线数据并与历史基线对比
4. 执行安全扫描测试（OWASP Top 10关键项）
5. 分析测试结果，识别新增失败和性能退化
6. 生成夜间测试日报，推送到团队频道
7. 对发现的失败用例自动创建Bug工单
8. 更新测试健康度仪表盘数据

**预期输出**：
- 夜间回归测试日报（邮件/Slack/钉钉格式）
- 新增Bug工单列表（含复现步骤）
- 性能退化预警通知
- 测试健康度趋势图表更新

### 场景3：测试覆盖率缺口自主填补
**触发条件**：覆盖率低于设定阈值（如新代码 <80%）或定期巡检
**自主执行步骤**：
1. 运行覆盖率工具，生成详细覆盖率报告
2. 识别未覆盖的代码行和分支
3. 分析未覆盖原因：
   - 死代码 → 建议删除
   - 异常路径未测试 → 补充异常测试
   - 条件分支遗漏 → 补充边界测试
   - 工具函数未直接测试 → 通过集成测试间接覆盖
4. 为每个缺口自动生成测试用例草案
5. 评估新增测试的价值和成本
6. 按优先级排列并输出补充计划
7. 可选：自动生成测试代码并提交PR

**预期输出**：
- 覆盖率缺口分析报告
- 按优先级排序的补充测试用例列表
- 生成的测试代码文件（可选）
- 覆盖率提升预估

### 场景4：TDD辅助开发模式
**触发条件**：开发者开启TDD模式或在开发新功能时主动请求
**自主执行步骤**：
1. 分析待开发功能的规格说明或用户故事
2. 提取功能的行为契约（输入/输出/副作用）
3. 按照TDD红-绿-重构循环节奏生成初始测试骨架：
   - Red Phase：先写失败的测试用例（定义期望行为）
   - Green Phase：提供最简实现使测试通过
   - Refactor Phase：优化代码结构同时保持测试通过
4. 根据代码复杂度动态调整测试粒度
5. 在每个TDD循环结束后验证覆盖率增量
6. 当功能完成后，生成完整的测试套件总结

**预期输出**：
- 按TDD节奏组织的测试用例集合
- 每个测试用例对应的功能点标注
- 覆盖率逐步增长曲线
- 最终测试套件的质量评估报告

## 决策框架

### 测试范围自适应决策树

```
变更信息输入
  │
  ├─ 是否涉及生产事故相关代码？
  │   ├─ 是 → 扩大测试范围至关联模块，增加混沌测试
  │   └─ 否 → 继续判断
  │
  ├─ 是否涉及支付/安全/隐私？
  │   ├─ 是 → 全量P0+安全专项测试，人工复核必选
  │   └─ 否 → 继续判断
  │
  ├─ 变更规模如何？
  │   ├─ <100行 → 精准测试（仅变更函数及其直接调用者）
  │   ├─ 100-500行 → 模块级测试（整个模块的全量测试）
  │   ├─ 500-2000行 → 跨模块测试（影响面全量+抽样回归）
  │   └─ >2000行 → 全量回归测试
  │
  ├─ 是否处于发布前一周？
  │   ├─ 是 → 启用严格模式，P0零容忍，增加探索性测试
  │   └─ 否 → 正常模式
  │
  └─ CI资源是否充足？
      ├─ 是 → 并行执行所有层级测试
      └─ 否 → 优先P0单元测试，P1/E2E延后执行
```

### 测试失败响应决策矩阵

| 失败类型 | P0测试 | P1测试 | P2测试 | 响应动作 |
|----------|--------|--------|--------|----------|
| 代码缺陷 | 阻塞合并 | 阻塞合并 | 记录跟踪 | 创建Bug工单，通知作者 |
| 测试本身缺陷 | 阻塞合并 | 记录修复 | 记录修复 | 修复测试代码，重新运行 |
| 环境问题 | 重试3次 | 重试1次 | 忽略 | 排查环境，必要时重建 |
| 数据问题 | 阻塞合并 | 重跑并清理 | 忽略 | 修复测试数据 |
| 间歇性(Flaky) | 标记隔离 | 标记隔离 | 标记隔离 | 排查Flaky根因 |

## 安全与治理

### 风险评估标准
- **高风险测试场景**：涉及真实生产数据的测试、破坏性测试（删除/修改）、压力测试可能影响线上服务
- **中风险测试场景**：使用测试数据库的写入操作、涉及外部服务的集成测试
- **低风险测试场景**：纯内存单元测试、只读查询测试、Mock完全隔离的测试

### 审批门禁条件
- P0测试用例通过率 = 100% 时才允许合并到主分支
- 安全相关测试（认证/授权/加密）必须全部通过
- 性能基线退化超过20%时需要性能团队审批
- 新增的Flaky Test超过总数5%时需要暂停发布

### 回滚策略
- 测试代码本身纳入版本控制，支持回滚到任意历史版本
- 测试环境配置使用Infrastructure as Code管理，支持快速重建
- 测试数据通过Seed脚本可重现，避免硬编码导致的不可复现问题
- 测试执行日志完整保留，用于事后审计和问题排查

## 与其他司/局的协作关系

### 与代码审查局的协作
- 代码审查局标识的高风险代码段自动成为本局P0测试重点区域
- 本局发现的Bug根因分析反馈给代码审查局，用于优化其L2语义层审查规则
- 两局共同维护"易错模式"知识库，互相强化检测能力

### 与质量监控局的协作
- 本局每次测试执行的覆盖率、通过率、执行时间等数据上报质量监控局
- 质量监控局的趋势预警触发本局对特定区域的定向补充测试
- 本局维护的测试健康度指标成为质量监控局六维质量指标的"测试覆盖"维度数据源
- 质量监控局设定的质量门槛直接影响本局的测试通过标准

### 与合规审计局的协作
- 合规审计局的安全基线要求转化为本局的安全测试用例集
- 本局的安全测试结果作为合规审计局合规证明的一部分
- 合规审计局发现的CVE漏洞触发本局对该漏洞路径的紧急回归测试
- 许可证合规性变更需要本局确认不影响现有测试资产的合法性

## 🤝 v5.1 增强：Agency Agent 协作指南

### 可调用的 Agency Agents

本局可通过 Agency-Agent Bridge 调用以下专业智能体（Testing Division 全覆盖）：

| Agent 名称 | 所属部门 | 协作模式 | 适用场景 |
|-----------|---------|---------|---------|
| **Evidence Collector** | Testing Division | 主动调用 | 视觉QA证据收集、UI/UX截图对比、跨浏览器兼容性验证、移动端适配测试 |
| **Reality Checker** | Testing Division | 联动触发 | 发布准入认证、生产环境真实性验证、用户旅程端到端验收、业务逻辑正确性核验 |
| **API Tester** | Testing Division | 主动调用 | API契约测试、接口文档一致性验证、请求/响应格式校验、版本兼容性测试 |
| **Performance Benchmarker** | Testing Division | 条件触发 | 性能基线建立与回归、负载测试执行、响应时间P50/P95/P99监控、吞吐量基准测量 |
| **Test Results Analyzer** | Testing Division | 自动集成 | 测试结果深度分析、失败归因分类、Flaky Test检测、覆盖率有效性评估、趋势分析 |
| **Accessibility Auditor** | Testing Division | 按需调用 | WCAG 2.1合规性审查、屏幕阅读器兼容性测试、键盘导航验证、色彩对比度检查 |
| **Tool Evaluator** | Testing Division | 周期性触发 | 测试工具链评估、新框架选型建议、技术债务识别、效率优化机会发现 |
| **Workflow Optimizer** | Testing Division | 持续优化 | 测试流程自动化改进、CI流水线优化、并行化策略制定、执行时间缩减方案 |

### Agent 协作工作流

**Step 1 - 测试需求分析与Agent调度决策**
- 接收PR变更信息或定时任务触发
- 执行变更影响面评估，识别涉及的测试层级和类型
- 根据变更特征，自动决定需要调度的Agent组合：
  - UI/前端变更 → Evidence Collector + Accessibility Auditor
  - API/后端变更 → API Tester + Performance Benchmarker
  - 全栈功能变更 → Reality Checker + Evidence Collector + API Tester
  - 发布前验证 → 全部Agent联动（发布准入完整套件）

**Step 2 - 分层测试执行（多Agent并行）**
- **单元/集成层**：API Tester 执行契约测试和接口验证
- **视觉/UI层**：Evidence Collector 执行视觉回归测试和跨设备截图
- **E2E/验收层**：Reality Checker 执行完整的用户旅程验证
- **性能层**：Performance Benchmarker 建立或对比性能基线
- **无障碍层**：Accessibility Auditor 执行WCAG合规性检查
- 各Agent并行执行，最大化测试效率

**Step 3 - Test Results Analyzer 统一分析**
- 收集所有Agent的测试执行结果
- 执行智能归因分析：
  - 区分代码缺陷 vs 测试缺陷 vs 环境问题
  - 识别Flaky Test并标记隔离
  - 计算各维度的覆盖率和通过率
  - 生成结构化的测试报告
- 对失败用例进行根因定位，提供修复建议

**Step 4 - Workflow Optimizer 持续优化**
- 分析本次测试执行的效率和瓶颈
- 识别可以并行化的串行步骤
- 评估Mock策略的合理性
- 提出CI流水线优化建议
- 更新测试优先级算法参数

**Step 5 - Tool Evaluator 定期评估（周期性）**
- 每月/每季度评估当前测试工具链的健康度
- 识别过时的工具或框架
- 评估新技术引入的价值和风险
- 输出工具链升级路线图

**Step 6 - 综合报告生成与发布**
- 整合所有Agent的分析结果，生成统一的测试报告
- 在PR/发布页面发布测试状态和详细报告
- 根据P0/P1/P2通过情况设置对应标签
- 将关键指标上报质量监控局

### 典型协作场景

**场景1：发布前全量准入认证（Reality Checker主导 + 全Agent协同）**
- **触发条件**：发布候选版本构建完成
- **协作流程**：
  1. Reality Checker 制定发布准入认证计划（基于发布清单）
  2. Evidence Collector 执行全面的视觉回归测试（桌面+移动端）
  3. API Tester 验证所有公开API的契约一致性
  4. Performance Benchmarker 执行完整性能基线回归（含压力测试）
  5. Accessibility Auditor 完成无障碍合规性最终检查
  6. Test Results Analyzer 汇总所有结果，生成发布准入报告
  7. Reality Checker 基于报告做出"准予发布/拒绝发布/有条件发布"的最终判定
- **输出特点**：包含发布准入认证证书、各维度测试证据包、风险评估摘要

**场景2：PR快速反馈循环（轻量级Agent组合）**
- **触发条件**：日常开发PR提交
- **协作流程**：
  1. 根据变更类型自动选择最小必要Agent集合
  2. API Tester（如涉及后端）或 Evidence Collector（如涉及前端）快速执行核心测试
  3. Test Results Analyzer 在5分钟内提供初步反馈
  4. 如发现问题，立即在PR评论中通知开发者
  5. Workflow Optimizer 监控反馈循环时长，持续优化速度
- **输出特点**：快速反馈（目标<10分钟）、精准定位问题、最小化开发者等待时间

**场景3：性能退化专项调查（Performance Benchmarker主导）**
- **触发条件**：APM告警或性能基线偏差超过阈值
- **协作流程**：
  1. Performance Benchmarker 执行详细的性能剖析（火焰图、内存快照、慢查询日志）
  2. API Tester 排查是否为特定API的性能退化
  3. Test Results Analyzer 关联最近的代码变更，定位引入退化的提交
  4. Workflow Optimizer 评估是否需要在CI中增加性能门禁
  5. 输出性能退化诊断报告和修复建议
- **输出特点**：包含性能退化根因分析、受影响的代码路径、修复前后对比数据、预防措施建议

### 实践指南

**实践1：CI中嵌入测试质量门禁**
```
门禁架构：
┌─────────────────────────────────────────────────────┐
│                  CI Pipeline                         │
│                                                       │
│  Build ──→ Unit Tests ──→ Integration Tests          │
│              ↓                ↓                       │
│         [P0 Gate]        [P1 Gate]                    │
│              ↓                ↓                       │
│         E2E Tests ──→ Performance Tests               │
│              ↓                ↓                       │
│         [P2 Gate]        [Perf Gate]                  │
│              ↓                                        │
│      ┌─────┴─────┐                                   │
│      ▼           ▼                                   │
│   ✅ PASS     ❌ BLOCK                               │
│   (允许合并)  (阻止合并+通知)                          │
└─────────────────────────────────────────────────────┘
```
- P0测试（必须全量通过）：单元测试、核心API契约测试、认证授权测试
  - 通过率 = 100% 时才允许继续
  - 失败时立即阻断，不执行后续阶段
- P1测试（强烈建议通过）：集成测试、重要业务逻辑测试
  - 通过率 ≥ 98% 时允许继续（允许已知的Flaky Test）
  - 失败时警告但可继续（需人工审核）
- P2测试（冒烟即可）：E2E冒烟测试、非核心功能测试
  - 通过率 ≥ 90% 时允许继续
  - 仅记录失败项，不阻断
- 性能门禁：P95响应时间不超过基线的120%，吞吐量不低于基线的80%

**实践2：CD部署前自动化验证**
- 在CD Pipeline的部署前阶段插入自动化验证套件
- 验证套件内容：
  - 健康检查端点探测（HTTP 200 + 响应时间<1s）
  - 关键业务路径冒烟测试（登录→核心操作→登出）
  - 数据库连接池状态检查
  - 缓存服务可用性验证
  - 外部依赖服务连通性检查（降级策略验证）
- 验证全部通过 → 允许部署到下一环境
- 任一验证失败 → 自动回滚并告警
- 与Reality Checker的发布准入认证形成互补：自动化验证保证基本可用性，Reality Checker保证业务正确性

**实践3：Chaos Engineering故障注入测试**
```
混沌实验矩阵：
┌────────────────┬─────────────────┬──────────────────┬─────────────┐
│ 故障类型       │ 注入方式        │ 预期行为          │ 验证Agent   │
├────────────────┼─────────────────┼──────────────────┼─────────────┤
│ Pod崩溃        │ 随机删除Pod     │ 自动重启+无损故障转移 │ Reality    │
│ 网络延迟       │ 注入200ms延迟   │ 超时重试+降级响应   │ Perf. Bench.│
│ 网络分区       │ 隔离部分节点    │ 优雅降级+部分可用  │ Reality    │
│ 磁盘满载       │ 模拟磁盘空间耗尽│ 告警+写入保护      │ API Tester │
│ CPU高负载      │ 压榨CPU至90%+   │ 请求排队+自动扩容  │ Perf. Bench.│
│ 内存泄漏模拟   │ 限制内存配额    │ OOM重启+快速恢复   │ Reality    │
│ 依赖服务不可用  │ 断开外部API    │ 熔断+降级+缓存响应 │ API Tester │
└────────────────┴─────────────────┴──────────────────┴─────────────┘
```
- 定期（每周/每两周）执行Chaos Engineering实验
- 每次实验聚焦1-2个故障类型，避免同时注入多个故障
- 实验前必须制定明确的假设和成功标准
- 实验过程中实时监控系统指标（错误率、延迟、可用性）
- 实验后生成韧性评分报告，识别系统薄弱环节
- 将发现的脆弱点转化为新的测试用例或架构改进任务

### 操作优先级指引（v6.0核心）

### Decision Log 记录要求

作为**测试验证局**，以下类型的决策必须自动记录到Decision Log：

- 测试策略制定决策（单元/集成/E2E/性能/安全测试的选型依据及范围界定）
- 测试优先级排序结论（P0/P1/P2分级标准应用及具体用例分类理由）
- 测试失败响应决策（阻断合并/警告跟踪/忽略处理的判定及归因分析）
- 覆盖率缺口处理决定（补充测试策略选择、资源分配优先级、目标设定）
- TDD节奏控制决策（基于代码复杂度的TDD粒度调整及节奏变更理由）

- Decision Log存储路径：`docs/logs/decision_logs/`
- 日志命名规则：`{YYYY-MM-DD}_TEST_decisions.md`
