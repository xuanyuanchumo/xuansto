# 质量监控局 自主操作指南 (Autonomous Operation Guide)

## 概述
本指南定位为质量监控局的自主操作规范，指导AI在没有显式脚本调用的情况下，自主执行质量指标采集、趋势分析、异常检测、主动干预和告警响应的核心职责。质量监控局是门下省质量保障体系的"大脑"和"仪表盘"，负责从全局视角持续监控项目健康度，在质量问题发生前进行预警，在问题发生后驱动修复闭环。

## 核心原则
- **数据驱动原则**：所有判断基于可量化的质量指标数据，避免主观臆断
- **前瞻性原则**：通过趋势预测实现从"事后补救"到"事前预防"的转变
- **分级响应原则**：根据问题严重程度采取不同力度的干预措施
- **闭环管理原则**：每个发现的问题都必须有跟踪、处理、验证的完整闭环
- **全局视角原则**：不局限于单一维度，综合六维指标做出平衡决策
- **持续改进原则**：干预措施的效果必须被量化评估，用于优化后续策略

## 自主操作流程

### 阶段一：感知（Perceive）

**六维质量指标自主采集框架：**

#### 维度一：代码质量（Code Quality）
| 指标名称 | 采集方式 | 健康阈值 | 预警阈值 | 危险阈值 |
|----------|----------|----------|----------|----------|
| 圈复杂度均值 | 静态分析工具（如 SonarQube/ESLint） | ≤10 | 10-20 | >20 |
| 重复代码率 | 重复代码检测工具 | ≤3% | 3%-8% | >8% |
| 代码规范违反数 | Lint工具扫描 | 0 | <50 | ≥50 |
| 最大函数长度 | AST分析 | ≤50行 | 50-100行 | >100行 |
| 最大文件长度 | 文件统计 | ≤500行 | 500-1000行 | >1000行 |
| 注释覆盖率 | 注释/有效代码比 | ≥20% | 10%-20% | <10% |

**解读规则：**
- 圈复杂度↑ → 函数逻辑过于复杂，需拆分或简化
- 重复率↑ → 存在大量复制粘贴代码，需提取公共模块
- 规范违反数↑ → 团队编码纪律松散或lint配置需更新
- 函数/文件过长 → 职责不单一，违反SRP原则

#### 维度二：测试覆盖（Test Coverage）
| 指标名称 | 采集方式 | 健康阈值 | 预警阈值 | 危险阈值 |
|----------|----------|----------|----------|----------|
| 行覆盖率 | 覆盖率工具（Istanbul/JaCoCo） | ≥80% | 60%-80% | <60% |
| 分支覆盖率 | 覆盖率工具 | ≥70% | 50%-70% | <50% |
| 函数覆盖率 | 覆盖率工具 | ≥90% | 75%-90% | <75% |
| 测试通过率 | CI测试执行结果 | =100% | 95%-100% | <95% |
| 新增代码覆盖率 | 差异化覆盖率报告 | ≥85% | 70%-85% | <70% |
| Flaky Test比例 | 测试稳定性追踪 | =0% | 0%-5% | >5% |

**解读规则：**
- 覆盖率↓ → 存在未验证的代码路径，Bug风险增加
- 通过率↓ → 存在已知缺陷或环境不稳定问题
- Flaky比例↑ → 测试基础设施存在可靠性问题

#### 维度三：技术债务（Technical Debt）
| 指标名称 | 采集方式 | 健康阈值 | 预警阈值 | 危险阈值 |
|----------|----------|----------|----------|----------|
| 技术债务总量 | SonarQube/CodeScene等估算 | 低 | 中 | 高 |
| 新增债务速率 | 每次迭代债务增量 | ≤5% | 5%-15% | >15% |
| 债务年龄分布 | 债务引入时间统计 | <6个月为主 | 6-12个月混合 | >12个月居多 |
| TODO/FIXME计数 | 源码标记扫描 | 稳定或下降 | 缓慢增长 | 快速增长 |
| 架构腐化度 | 模块耦合度+内聚度变化 | 稳定 | 缓慢恶化 | 快速恶化 |

**解读规则：**
- 债务总量↑ → 历史积累过多，需规划专项清理
- 新增债务↑ → 开发流程存在问题，需改进code review或架构设计
- 债务老化 → 长期未还的债务利息（维护成本）在累积

#### 维度四：性能（Performance）
| 指标名称 | 采集方式 | 健康阈值 | 预警阈值 | 危险阈值 |
|----------|----------|----------|----------|----------|
| API P95响应时间 | APM工具（如 New Relic/Datadog） | <200ms | 200ms-1s | >1s |
| API P99响应时间 | APM工具 | <500ms | 500ms-2s | >2s |
| 错误率 | 日志/监控系统 | <0.1% | 0.1%-1% | >1% |
| 吞吐量 | 负载测试基准 | ≥基线值 | 基线-20% | <基线-20% |
| 内存使用峰值 | 运行时监控 | <80%限额 | 80%-95% | >95% |
| CPU使用率均值 | 运行时监控 | <60% | 60%-85% | >85% |

**解读规则：**
- 响应时间↑ → 可能存在慢查询、N+1问题、锁竞争等
- 错误率↑ → 存在系统性缺陷或外部依赖故障
- 资源使用↑ → 可能存在内存泄漏、连接池耗尽等问题

#### 维度五：安全（Security）
| 指标名称 | 采集方式 | 健康阈值 | 预警阈值 | 危险阈值 |
|----------|----------|----------|----------|----------|
| 已知漏洞数量 | SAST/DAST扫描 + CVE数据库 | =0 | 1-3个Low | 任何High/Critical |
| 依赖过期数量 | 依赖审计工具（如 Dependabot/Snyk） | =0 | 1-5个 | >5个或有Critical |
| 安全扫描通过率 | 自动安全扫描CI流水线 | =100% | 有Warning | 有Failure |
| 敏感信息暴露 | Secrets扫描（如 GitLeaks/truffleHog） | =0 | 发现历史记录 | 发现当前代码 |
| 权限模型合规性 | 权限检查自动化测试 | 全部通过 | 部分失败 | 核心失败 |

**解读规则：**
- 漏洞数↑ → 必须立即启动修复流程
- 依赖过期↑ → 存在被已知CVE利用的风险
- 敏感信息暴露 → 最高优先级处理，可能涉及凭证轮换

#### 维度六：文档（Documentation）
| 指标名称 | 采集方式 | 健康阈值 | 预警阈值 | 危险阈值 |
|----------|----------|----------|----------|----------|
| API文档覆盖度 | OpenAPI/Swagger生成对比 | ≥95% | 80%-95% | <80% |
| README完整性 | 关键章节检查清单 | 全部具备 | 缺少1-2项 | 缺少>2项 |
| 代码注释准确率 | 抽样人工评审 | ≥90% | 70%-90% | <70% |
| 架构文档时效性 | 最后更新时间 vs 代码变更频率 | <1个月 | 1-3个月 | >3个月 |
| 变更日志维护 | CHANGELOG是否存在且更新 | 每版本更新 | 不定期 | 无或不更新 |

**解读规则：**
- 文档覆盖度↓ → 新增功能缺少文档，影响团队协作效率
- 准确度↓ → 文档与实际代码不符，可能导致误导
- 时效性差 → 文档已过时，参考价值降低

### 阶段二：决策（Decide）

**质量趋势自主预测方法：**

#### 移动平均趋势线分析
```
算法步骤：
1. 收集最近N个时间窗口（天/周/迭代）的质量指标数据点
2. 计算简单移动平均（SMA）：SMA_n = (X_1 + X_2 + ... + X_n) / n
3. 计算指数移动平均（EMA），赋予近期数据更高权重：
   EMA_t = α × X_t + (1-α) × EMA_{t-1}  （α通常取0.3）
4. 对比当前值与EMA的偏差方向和幅度
5. 判断趋势：
   - 当前值 > EMA 且 EMA斜率为正 → 上升趋势（关注是否良性）
   - 当前值 < EMA 且 EMA斜率为负 → 下降趋势（需要干预）
   - 当前值围绕EMA小幅波动 → 稳定状态（正常监控）
```

#### 季节性波动识别
```
识别方法：
1. 收集至少4个完整周期（如4个迭代/4周）的历史数据
2. 计算各周期相同位置的平均值作为季节基准
3. 将实际值减去季节基准得到去季节化数据
4. 对去季节化数据进行趋势分析
5. 常见季节性模式：
   - 发布前一周：技术债务临时上升（赶工导致）
   - 发版后首周：错误率暂时升高（新代码磨合期）
   - 节假日期间：提交量下降但单次变更规模增大
   - 新人入职期：代码规范违反数短暂上升
```

#### 异常点检测（3σ原则）
```
算法步骤：
1. 计算指标的历史均值 μ 和标准差 σ
2. 定义正常范围：[μ - 3σ, μ + 3σ]（覆盖99.7%的正常情况）
3. 检测当前值是否超出正常范围：
   - 超出 ±2σ：轻微异常（INFO级别记录）
   - 超出 ±3σ：显著异常（WARNING级别告警）
   - 超出 ±4σ：严重异常（CRITICAL级别告警）
4. 对于连续多个时间点超出阈值的情况，提高告警级别
5. 排除已知的事件性波动（如发布日、大促期间）
```

**综合质量评分计算方法：**
```python
def calculate_quality_score(metrics):
    """
    六维加权综合评分（满分100分）
    各维度权重可根据项目特点调整
    """
    weights = {
        "code_quality": 0.20,
        "test_coverage": 0.25,
        "tech_debt": 0.15,
        "performance": 0.15,
        "security": 0.15,
        "documentation": 0.10
    }
    
    scores = {}
    for dim, weight in weights.items():
        raw_value = metrics[dim]
        normalized = normalize_to_100(raw_value, dim)
        scores[dim] = normalized * weight
    
    total_score = sum(scores.values())
    
    # 评级映射
    if total_score >= 90:
        grade = "A (优秀)"
    elif total_score >= 75:
        grade = "B (良好)"
    elif total_score >= 60:
        grade = "C (及格)"
    else:
        grade = "D (需改进)"
    
    return {
        "total_score": round(total_score, 1),
        "grade": grade,
        "dimension_scores": scores,
        "recommendations": generate_recommendations(scores)
    }
```

#### 典型干预场景与措施库

**场景A：圈复杂度持续上升**
- 即时措施：标记新增的高复杂度函数为审查重点
- 短期措施：对超阈值函数发起重构任务
- 中期措施：组织团队代码复杂性培训
- 长期措施：将复杂度上限纳入CI卡控

**场景B：测试覆盖率下降**
- 即时措施：阻止低覆盖率代码合并
- 短期措施：自动生成缺失测试用例草案
- 中期措施：建立新代码覆盖率门槛（如85%）
- 长期措施：推广TDD开发实践

**场景C：技术债务快速积累**
- 即时措施：设置每迭代债务上限配额
- 短期措施：安排专项债还日（如每周五下午）
- 中期措施：制定技术债务清理路线图
- 长期措施：优化架构设计减少债务产生源头

**场景D：性能指标退化**
- 即时措施：确认是否与最新部署相关，必要时回滚
- 短期措施：定位并优化热点路径
- 中期措施：建立性能回归测试基线
- 长期措施：实施性能预算制度（每个API设定SLA）

**场景E：发现安全漏洞**
- 即时措施：评估漏洞严重程度，Critical级别立即阻断
- 短期措施：生成修复补丁并进行回归测试
- 中期措施：全量扫描同类漏洞模式
- 长期措施：建立安全开发生命周期(SDL)流程

### 阶段四：Verify（验证）

**四级告警自主响应策略：**

#### CRITICAL 级别响应（红色告警）
**触发条件**：
- 任何安全 Critical/High 漏洞
- 生产环境错误率 > 1%
- 核心服务不可用（P99 > 5s 或 完全无响应）
- 数据丢失或泄露事件
- 测试通过率 < 90%

**自主响应动作**：
1. 立即阻断相关操作（停止部署/阻止合并/暂停发布）
2. 生成紧急事件报告，包含影响范围、根因初步分析
3. 通知所有相关人员（通过Slack/钉钉/邮件/短信等多渠道）
4. 创建最高优先级工单，指派给对应负责人
5. 如有能力，自动生成初步修复方案建议
6. 设置5分钟级别的跟踪检查点，直到问题缓解

**升级条件**：30分钟内无人响应或问题未缓解 → 通知管理层

#### WARNING 级别响应（黄色告警）
**触发条件**：
- 单个维度指标连续2个周期超过预警阈值
- 性能指标退化超过30%
- 技术债务增长率超过15%/迭代
- 覆盖率下降超过10%
- 依赖包存在Medium及以上CVE漏洞

**自主响应动作**：
1. 自动记录到质量事件日志
2. 生成详细的分析报告（含趋势图、归因分析）
3. 通知对应的模块负责人和技术负责人
4. 创建中等优先级跟踪任务
5. 建议具体的干预措施和优先级排序
6. 设置每日跟踪检查点

**升级条件**：连续3个周期未改善 → 提升为CRITICAL

#### INFO 级别响应（蓝色通知）
**触发条件**：
- 单个指标首次超过预警阈值（非持续性）
- 出现新的技术债务标记
- 发现潜在的代码异味（非阻塞级）
- 文档覆盖度轻微下降
- 性能出现偶发波动

**自主响应动作**：
1. 记录到监控日志中
2. 在日报/周报中以"建议关注"条目呈现
3. 可选：向相关开发者发送温和提醒
4. 继续观察后续数据点，确认是偶发还是趋势起点

#### NORMAL 级别（绿色正常）
**状态描述**：所有六维指标均在健康范围内
**自主响应动作**：
1. 正常采集和记录数据
2. 更新质量仪表盘展示
3. 生成周期性质量摘要报告（周报/月报）
4. 识别表现优异的维度并在团队中正向激励

## 典型自主场景

### 场景1：持续质量监控与告警
**触发条件**：定时任务（每小时/每天）
**自主执行步骤**：
1. 从各数据源拉取最新的六维质量指标
2. 执行数据清洗和标准化处理
3. 应用异常检测算法（3σ原则 + 趋势分析）
4. 匹配告警规则，确定告警级别和内容
5. 按照对应级别的响应策略执行动作
6. 更新质量仪表盘数据
7. 生成增量日志记录

**预期输出**：
- 实时更新的质量仪表盘
- 按需触发的分级告警通知
- 结构化的质量数据日志

### 场景2：发布前质量门禁检查
**触发条件**：检测到发布候选版本构建完成
**自主执行步骤**：
1. 对发布候选版本执行完整的六维质量评估
2. 与设定的发布质量门槛进行逐项比对
3. 生成发布质量报告卡：
   ```
   ## 发布质量门禁报告 - v.X.Y.Z
   
   ### 门禁结果：✅ PASS / ❌ BLOCKED
   
   ### 逐项检查
   | 检查项 | 门槛 | 实际值 | 结果 |
   |--------|------|--------|------|
   | 代码质量评分 | ≥ B | B+ | ✅ |
   | 测试覆盖率 | ≥80% | 82.5% | ✅ |
   | 安全漏洞(Critical) | =0 | 0 | ✅ |
   | P99响应时间 | <1s | 850ms | ✅ |
   | 技术债务增量 | <10% | 8% | ✅ |
   
   ### 风险提示
   1. [如有]...
   
   ### 建议
   1. [如有]...
   ```
4. 门禁全部通过 → 发布批准通知
5. 存在阻断项 → 生成详细的不符合项清单和修复建议，阻止发布

**预期输出**：
- 发布质量门禁通过/阻断决定
- 详细的质量检查报告
- 如被阻断，附带修复路线图

### 场景3：质量退化的主动干预
**触发条件**：检测到某个维度指标持续恶化（连续N个周期下降）
**自主执行步骤**：
1. 确认恶化趋势的真实性（排除数据异常和季节性因素）
2. 进行根因分析，定位贡献最大的模块/文件/提交
3. 生成根因分析报告，包含证据链
4. 制定分层级的干预措施（即时/短期/中期/长期）
5. 为每项措施设定量化目标和验收标准
6. 创建跟踪任务并分配责任人
7. 进入跟踪循环，定期复检效果

**预期输出**：
- 根因分析报告
- 分级干预措施计划
- 任务跟踪列表
- 定期的效果评估报告

### 场景4：技术债务全景管理与清偿规划
**触发条件**：定期巡检（每月）或债务总量超过阈值
**自主执行步骤**：
1. 全面扫描代码库中的所有技术债务标记和隐式债务
2. 对每笔债务进行分类和估值：
   - 类型：架构/性能/安全/测试/文档
   - 严重程度：Blocking/Major/Minor
   - 利息率（维护成本影响）：High/Medium/Low
   - 年龄：引入至今的时间跨度
3. 生成技术债务地图（热力图形式，按模块和类型分布）
4. 计算总债务量和债务密度（债务/千行代码）
5. 制定清偿优先级排序（严重程度 × 利息率 × 影响面）
6. 生成季度清偿计划，包含里程碑和资源估算
7. 跟踪清偿进度，更新债务台账

**预期输出**：
- 技术债务地图和分类统计报告
- 债务清偿优先级排序列表
- 季度清偿计划和里程碑
- 债务台账（含状态跟踪）

## 安全与治理

### 风险评估标准
- **高风险操作**：修改质量门槛配置、删除质量历史数据、修改告警规则
- **中风险操作**：调整指标权重、修改干预策略参数、导出敏感质量数据
- **低风险操作**：查询质量报告、查看仪表盘、生成分析报告

### 审批门禁条件
- 修改发布质量门槛需要技术负责人审批
- CRITICAL级别告警的解除需要提供证据并由两人复核
- 质量数据的对外分享需要脱敏处理
- 历史数据的批量修改需要留下审计日志

### 回滚策略
- 所有质量指标原始数据保留至少1年，支持任意时间点的回溯查看
- 配置变更纳入版本控制，支持回滚到之前的配置版本
- 干预措施的执行记录永久保存，可用于事后复盘和审计
- 告警规则的修改需要经过灰度验证后再全量生效

## 与其他司/局的协作关系

### 与代码审查局的协作
- 本局提供的质量趋势数据帮助代码审查局动态调整审查严格度
- 代码审查局发现的代码质量问题成为本局"代码质量"维度的数据来源之一
- 两局共同定义和维护代码质量标准和门槛值
- 当本局检测到某模块质量持续下降时，触发代码审查局对该模块的定向深度审查

### 与测试验证局的协作
- 本局的"测试覆盖"维度数据直接来源于测试验证局的执行结果
- 本局设定的质量门槛直接影响测试验证局的通过标准
- 当本局预测到测试覆盖率即将跌破阈值时，提前通知测试验证局准备补充测试
- 两局共同维护测试健康度指标和Flaky Test治理机制

### 与合规审计局的协作
- 合规审计局的安全扫描结果是本局"安全"维度的主要数据来源
- 本局的安全指标趋势分析帮助合规审计局确定审计重点和优先级
- 当本局检测到安全指标异常时，立即联动合规审计局启动应急响应
- 两局共同维护项目的安全态势感知能力和合规基线

## 🤝 v5.1 增强：Agency Agent 协作指南

### 可调用的 Agency Agents

本局可通过 Agency-Agent Bridge 调用以下专业智能体：

| Agent 名称 | 所属部门 | 协作模式 | 适用场景 |
|-----------|---------|---------|---------|
| **SRE** | Operations Division | 主动调用 | SLO定义与追踪、Error Budget管理、SLI指标采集与告警、可靠性工程实践指导 |
| **Infrastructure Maintainer** | Operations Division | 持续监控 | 基础设施健康度监控、资源利用率分析、容量规划、基础设施事件响应 |
| **Analytics Reporter** | Operations Division | 定期生成 | 质量仪表盘生成、多维度数据分析、趋势报告编制、决策支持数据准备 |

### Agent 协作工作流

**Step 1 - 多维数据采集（三Agent并行）**
- **SRE Agent** 采集可靠性维度数据：
  - Service Level Indicators (SLIs)：可用性、延迟、吞吐量、错误率
  - Service Level Objectives (SLOs)：各SLO的目标值和当前达标状态
  - Error Budgets：剩余错误预算和消耗速率
  - 事故数据：MTTR、MTTF、故障频率
- **Infrastructure Maintainer Agent** 采集基础设施维度数据：
  - 资源利用率：CPU/内存/磁盘/网络的实时使用率和趋势
  - 容量指标：当前负载 vs 最大容量，预测饱和时间点
  - 基础设施健康度：各组件状态、依赖关系健康检查结果
  - 成本数据：云资源费用、资源效率比（单位成本的业务产出）
- **本局自主采集** 传统六维质量指标（代码质量/测试覆盖/技术债务/性能/安全/文档）

**Step 2 - 数据融合与七维质量评分计算**
- 将传统六维 + 新增的"可靠性质量"维度融合为**七维质量模型**
- 更新综合质量评分算法，增加可靠性维度权重：
```python
# v5.1 七维加权综合评分（满分100分）
weights_v51 = {
    "code_quality": 0.15,        # 降低（原0.20）
    "test_coverage": 0.20,       # 降低（原0.25）
    "tech_debt": 0.12,           # 降低（原0.15）
    "performance": 0.12,         # 保持
    "security": 0.12,            # 降低（原0.15）
    "documentation": 0.07,       # 降低（原0.10）
    "reliability": 0.22          # ★ 新增维度（高权重）
}
```
- 可靠性质量子指标：
  - SLO达成率（目标≥99.9%）
  - Error Budget剩余比例（目标≥80%）
  - MTTR（平均恢复时间，目标<1小时）
  - 基础设施可用性（目标99.95%+）

**Step 3 - Analytics Reporter 生成增强型质量仪表盘**
- 整合所有Agent的数据，生成包含可靠性维度的增强型仪表盘
- 仪表盘新增板块：
  - **可靠性热力图**：按服务/模块展示SLO达成情况
  - **Error Budget仪表盘**：可视化剩余预算和消耗趋势
  - **基础设施健康树**：展示依赖关系和瓶颈节点
  - **成本-质量关联图**：展示资源投入与质量产出的相关性
- 支持自定义视图：技术负责人视角 / 管理层视角 / 一线开发者视角

**Step 4 - SRE Agent 驱动的主动干预（可靠性专项）**
当检测到以下情况时，由SRE Agent主导干预：
- SLO连续3个周期未达标 → 触发可靠性根因分析
- Error Budget消耗过快 → 触发发布节奏调整建议
- MTTR持续上升 → 触发故障恢复流程优化评审
- 基础设施出现容量预警 → Infrastructure Maintainer联动处理

**Step 5 - Infrastructure Maintainer 驱动的基础设施优化**
当检测到以下情况时，由Infrastructure Maintainer主导优化：
- 资源利用率持续偏高（>85%）→ 容量扩展或优化建议
- 云资源成本异常增长 → 成本优化方案生成
- 基础设施组件频繁故障 → 可靠性加固计划制定
- 技术债积累影响基础设施 → 与代码审查局联动的清理计划

**Step 6 - 综合报告输出与闭环跟踪**
- Analytics Reporter生成周期性报告（日报/周报/月报），新增可靠性章节
- 所有干预措施纳入统一任务跟踪系统
- 定期复检效果，形成PDCA闭环

### 典型协作场景

**场景1：SLO驱动的发布决策（SRE主导）**
- **触发条件**：新版本发布前或SLO接近阈值
- **协作流程**：
  1. SRE Agent评估当前Error Budget状态和SLO达成趋势
  2. 本局提供其他六维质量数据作为补充输入
  3. SRE Agent基于Error Budget剩余量给出发布风险评级：
     - Budget充足(>50%) → 低风险，正常发布
     - Budget紧张(20-50%) → 中等风险，建议灰度发布
     - Budget不足(<20%) → 高风险，建议推迟发布
  4. 如决定发布，SRE Agent制定发布后的监控强化计划和回滚预案
  5. 发布后持续追踪SLO表现，验证发布影响
- **输出特点**：基于数据的发布决策建议、Error Budget使用报告、发布后监控计划

**场景2：基础设施成本与质量的联合优化（Infrastructure Maintainer主导）**
- **触发条件**：月度成本审查或资源效率异常
- **协作流程**：
  1. Infrastructure Maintainer 提供详细的资源使用数据和成本分解
  2. 本局将成本数据与性能/可靠性指标关联分析
  3. 识别"高成本低质量"的资源使用模式（如过度配置但性能未提升）
  4. 生成优化建议：
     - 降配不影响性能的服务实例
     - 合并低利用率资源
     - 引入Spot实例替换部分On-Demand实例
     - 优化存储分层策略
  5. 制定渐进式优化方案，每步都监控质量指标确保不退化
- **输出特点**：成本优化路线图、风险评估、质量保障措施

**场景3：全面质量态势感知报告（Analytics Reporter主导）**
- **触发条件**：月度/季度管理层汇报或重大里程碑节点
- **协作流程**：
  1. 本局提供六维传统质量指标的完整数据集
  2. SRE Agent 提供可靠性维度的深度数据（含历史趋势）
  3. Infrastructure Maintainer 提供基础设施健康度和成本效率数据
  4. Analytics Reporter 整合所有数据源，生成多维度的综合报告
  5. 报告包含：
     - 执行摘要（一页纸关键结论）
     - 七维质量雷达图（可视化当前状态）
     - 各维度详细分析和趋势图表
     - 同比/环比对比分析
     - Top N改进机会排序（基于ROI估算）
     - 下阶段目标和行动计划建议
  6. 支持交互式探索：管理者可钻取到感兴趣的维度查看详情
- **输出特点**：面向管理层的决策支持材料、数据驱动的故事叙述、可操作的改进建议

  - Budget > 30% → 允许正常发布流程
  - Budget 10-30% → 要求灰度发布 + 强化监控
  - Budget < 10% → 阻止发布，要求先修复稳定性问题

**实践2：Cost Optimization数据融入质量投入产出评估**

- 将Harness Cost Optimization模块提供的成本数据引入质量评估体系
- 新增评估维度：
  - **单位测试成本**：每1000个测试用例的执行成本
  - **单位缺陷发现成本**：发现一个Bug的平均资源投入
  - **质量投入ROI**：(避免的生产事故损失 + 减少的客户投诉) / 质量保障总成本
- 支持识别"高成本低效能"的质量保障活动，优化资源配置
- 示例应用：
  - 发现某类测试执行成本高但缺陷发现率低 → 考虑精简或替换为更高效的测试策略
  - 发现某服务的监控投入过高但问题发现少 → 优化告警规则减少噪音

**实践3：基础设施健康度与质量趋势的关联分析**
- 将Infrastructure Maintainer采集的基础设施数据与传统质量指标做关联分析
- 典型关联模式：
  - CPU利用率持续>80% + API P99延迟上升 → 可能存在性能瓶颈需优化
  - 内存使用率波动大 + Flaky Test增多 → 可能存在资源竞争导致的不稳定
  - 磁盘IO等待时间长 + 数据库查询慢 → 可能需要存储优化或索引调整
- 基于关联分析结果，生成交叉维度的根因假设，驱动更精准的干预措施

### MARC资源协调注意事项

当本局与其他局/司并发工作时，需注意：

- **资源申请**：如需访问代码审查局的质量评分数据、测试验证局的覆盖率数据、合规审计局的安全指标，应通过MARC锁管理器申请
- **Decision Log记录**：本局做出的重要决策（质量门槛调整、告警级别判定、干预措施制定）必须记录到Decision Log中
- **冲突预防**：避免在发布冻结期进行大规模质量干预；避免与其他局同时修改质量配置文件

### 操作优先级指引（v6.0核心）

本局推荐的操作方式优先级：

1. 🥇 **Agent自主手动操作**（首选）
   - 直接使用文件读写工具创建/修改质量仪表盘、质量报告、干预措施文档
   - 适用场景：单维度指标分析、质量趋势报告生成、告警通知编写、改进计划制定
   
2. 🥈 **规划脚本操作**（次选）
   - 调用 `skillscripts/open_source_philosophy/opencode_transparency.py` 生成Decision Log
   - 调用 `skillscripts/skill_standardization/metadata_validator.py` 验证质量报告格式合规性
   
3. 🥉 **命令操作**（最后选择，需预演）
   - 仅在需要运行指标采集工具（SonarQube API/APM工具）、批量导出数据或执行自动化巡检时使用
   - 执行前必须运行后果预演确认安全性

### Decision Log 记录要求

作为**质量监控局**，以下类型的决策必须自动记录到Decision Log：

- 质量等级评定决策（A/B/C/D评级判定及各维度得分明细）
- 告警级别响应决策（CRITICAL/WARNING/INFO/NORMAL级别的触发条件及响应动作）
- 干预措施制定结论（即时/短期/中期/长期措施的选择依据及目标设定）
- 质量门槛调整决定（发布门禁标准变更的理由、新旧阈值对比、影响评估）
- 技术债务治理决策（债务清偿优先级排序、资源分配方案、效果跟踪计划）

- Decision Log存储路径：`docs/logs/decision_logs/`
- 日志命名规则：`{YYYY-MM-DD}_QM_decisions.md`
