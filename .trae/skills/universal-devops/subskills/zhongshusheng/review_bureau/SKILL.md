# 方案审议局 (Review Bureau)

> 中书省 · 决策层 · Universal DevOps v4.0

**状态**: 占位符 - 具体内容由后续任务填充

## 🤖 自主化操作指南 (v7.0)

### 推荐操作模式
| 操作场景 | 推荐模式 | 置信度 | 说明 |
|---------|---------|--------|------|
| 方案评审 | AUTONOMOUS_MANUAL | 80% | 需要综合评估技术可行性、成本、风险 |
| 设计文档审核 | HYBRID_ASSISTED | 85% | 自动检查完整性 + 人工评审合理性 |
| RFC（Request for Comments）处理 | AUTONOMOUS_MANUAL | 75% | 涉及多方利益协调和共识达成 |
| 决策记录归档 | SCRIPTED_BATCH | 95% | 结构化存储，模板化输出 |

### 常用工具组合
- **读操作**: Read, SearchCodebase, Grep（查阅相关RFC、历史决策）
- **写操作**: Write, SearchReplace（撰写评审意见、决议文档）
- **批量操作**: RFC模板生成器、评审意见汇总脚本
- **验证操作**: 评审闭环检查工具（确认所有意见已响应）

### 注意事项
- ⚠️ 评审应聚焦于方案本身，避免针对个人的批评
- ⚠️ 评审意见必须具体可执行，禁止模糊的"需要优化"类反馈
- ✅ 采用"三明治法则"：肯定优点 → 提出改进 → 再次鼓励
- ✅ 设置明确的评审SLA（如24小时内给出初审意见），避免阻塞流程

## 🔗 资源协调要点 (v7.0)

### 常访问资源
| 资源类型 | 典型路径 | 锁策略建议 |
|---------|---------|-----------|
| FILE | /docs/rfc/ | SHARED (读) / EXCLUSIVE (写) |
| FILE | /docs/review-records/ | APPEND_ONLY (评审记录不可篡改) |
| CODEBASE | 待评审的特性分支 | SHARED (读) |
| API | 评审工作流系统 | STATEFUL (状态机管理) |

### 竞争规避策略
1. **评审队列机制**: RFC按提交时间排队，避免插队导致的资源争夺
2. **并行评审隔离**: 不同领域的评审可并行进行（安全评审+性能评审互不干扰）
3. **申诉升级通道**: 评审结果有异议时，可升级至更高层级复审，避免僵局

## 💡 开源哲学应用 (v7.0)

### OpenCode 透明化
- 评审标准和尺度公开：所有评审者遵循统一的checklist，评分标准透明可查
- 决策理由完整记录：每个通过的/驳回的方案都附详细理由，可供后续复盘
- 评审者资质公示：评审者的专业背景和评审历史对被评审方可见，增强公信力

### OpenClaude 编排
- 智能评审员分配：根据方案的技术领域自动匹配合适的专家评审者
- 评审意见自动分类：将反馈归类为Must-have/Should-have/Nice-to-have，辅助优先级决策
- 共识度实时监测：在评审讨论中实时分析各方观点分歧点，主动调解争议

### Claw-Code 契约驱动
- 评审准入契约：提交评审前必须满足最低文档要求（设计文档+测试计划），否则自动退回
- 评审闭环追踪：每条评审意见对应唯一的issue/tracker，关闭后才允许合入
- 质量度量标准化：建立评审质量KPI（如评审意见采纳率、漏审率），持续改进评审效能
