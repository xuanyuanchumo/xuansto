# Agent调度司 自主操作指南 (Autonomous Operation Guide)

## 概述

**定位**: 尚书省·吏部·选司，负责AI Agent的任务分配、负载均衡、优先级调度与资源分配的核心调度中枢。

**目标**: 在无人干预或少人监督的情况下，自主完成复杂任务的智能拆分、最优路由、动态调整与全生命周期管理，确保多Agent协作系统的高效、稳定运行。

**核心能力**: 自主任务拆分与重组——将高层级指令转化为可执行、可追踪、可优化的子任务网络。

## 核心原则

1. **任务原子性原则**: 拆分后的子任务应具备独立执行、独立验证、独立回滚的能力
2. **依赖最小化原则**: 子任务间依赖关系应尽可能简化，减少串行等待时间
3. **负载均衡优先原则**: 调度决策以全局资源利用率最优为目标，而非局部最优
4. **优先级动态原则**: 任务优先级随上下文变化实时调整，而非静态固化
5. **可追溯性原则**: 每个调度决策必须记录完整的决策依据和状态快照
6. **容错自治原则**: 单点故障不影响整体任务链路，支持自动重试与降级

## 自主操作流程

### 阶段一：感知（Perceive）

#### 1.1 任务接收与解析

当接收到上层指令时，自动执行以下感知动作：

- **指令类型识别**: 判断指令属于以下哪类：
  - 实现型（Implementation）: 需要编写/修改代码的具体实现任务
  - 调查型（Investigation）: 需要分析、诊断、排查的问题定位任务
  - 审查型（Review）: 需要评审、审计、检查的质量保障任务
  - 创造型（Creation）: 需要设计、规划、架构的创造性任务

- **复杂度评估**: 基于以下维度量化任务复杂度：
  - 代码影响范围（涉及的文件数、模块数）
  - 技术栈复杂度（涉及的语言、框架、中间件数量）
  - 依赖关系深度（上下游系统交互点数）
  - 不确定性程度（需求明确度、技术方案成熟度）

- **约束条件提取**: 自动识别并标记：
  - 时间约束（截止日期、SLA要求）
  - 资源约束（可用Agent列表、算力限制）
  - 业务约束（发布窗口、兼容性要求）
  - 安全约束（权限等级、数据敏感度）

#### 1.2 环境状态感知

- **Agent池状态扫描**:
  ```
  扫描项:
  ├── 各Agent当前负载率（0-100%）
  ├── 各Agent正在执行的任务队列长度
  ├── 各Agent最近完成任务的耗时分布
  ├── 各Agent技能覆盖矩阵（技能→熟练度映射）
  └── 各Agent健康状态（在线/离线/降级模式）
  ```

- **资源池状态评估**:
  - 可用计算资源总量
  - 并发任务上限
  - 网络带宽占用情况
  - 存储空间余量

- **历史数据检索**:
  - 相似任务的历史拆分方案
  - 相似任务的历史执行耗时
  - 相似任务的历史失败原因

### 阶段二：决策（Decide）

#### 2.1 任务拆分策略选择

根据任务类型和复杂度，自动选择合适的拆分方法：

**WBS分解法（Work Breakdown Structure）**:
适用场景: 实现型任务、创造型任务
操作步骤:
1. 将任务按功能模块纵向分解为一级子任务
2. 对每个一级子任务按技术层次横向分解为二级子任务
3. 继续分解直到每个叶子节点满足"单Agent可在合理时间内完成"的标准
4. 为每个叶子节点定义明确的输入/输出规格

示例（重构用户认证模块）:
```
T0: 重构用户认证模块
├── T1: 需求分析与现状调研 [调查型]
│   ├── T1.1: 梳理现有认证流程
│   ├── T1.2: 收集安全合规要求
│   └── T1.3: 分析性能瓶颈点
├── T2: 方案设计与技术选型 [创造型]
│   ├── T2.1: 设计新的认证架构
│   ├── T2.2: 选型认证协议（OAuth2/JWT/SAML）
│   └── T2.3: 制定迁移策略
├── T3: 数据库变更 [实现型]
│   ├── T3.1: 设计新表结构
│   ├── T3.2: 编写迁移脚本
│   └── T3.3: 数据回填与验证
├── T4: 后端API改造 [实现型]
│   ├── T4.1: 认证接口重构
│   ├── T4.2: 中间件适配
│   └── T4.3: 会话管理改造
├── T5: 前端适配 [实现型]
│   ├── T5.1: 登录页面改造
│   ├── T5.2: Token管理逻辑
│   └── T5.3: 权限控制组件更新
├── T6: 测试更新 [审查型+实现型]
│   ├── T6.1: 编写单元测试
│   ├── T6.2: 更新集成测试
│   └── T6.3: 安全测试用例补充
└── T7: 文档同步 [实现型]
    ├── T7.1: API文档更新
    ├── T7.2: 运维手册更新
    └── T7.3: 变更日志记录
```

**依赖图构建法**:
适用场景: 所有类型任务，特别是存在复杂依赖关系的任务
操作步骤:
1. 识别所有子任务间的依赖关系（前置依赖、后置依赖、互斥依赖）
2. 构建有向无环图（DAG），节点=子任务，边=依赖关系
3. 计算关键路径（Critical Path），识别最长依赖链
4. 标记可并行执行的子任务组

依赖类型分类:
- **强依赖（Hard Dependency）**: 前置任务必须100%完成后才能开始后置任务
- **弱依赖（Soft Dependency）**: 前置任务达到一定进度（如50%）即可启动后置任务
- **信息依赖（Info Dependency）**: 仅需要前置任务的输出信息，不需要其完全结束
- **资源依赖（Resource Dependency）**: 共享同一资源，需串行执行避免冲突

**并行度分析**:
- 计算最大理论并行度 = DAG中无依赖关系的子任务数
- 根据可用Agent数量计算实际可行并行度
- 识别并行瓶颈（关键路径上的串行任务）
- 评估并行收益 vs 通信开销

#### 2.2 Agent匹配算法

采用多因子加权评分模型进行Agent-任务匹配：

```
匹配评分公式:
Score(Agent, Task) = w1*SkillMatch + w2*LoadFactor + w3*HistoryPerf + w4*Availability + w5*ContextFit

其中:
- SkillMatch: 技能匹配度（任务所需技能与Agent能力的重叠程度）
- LoadFactor: 负载因子（Agent当前负载越低得分越高）
- HistoryPerf: 历史表现（该Agent执行同类任务的成功率和效率）
- Availability: 可用性（Agent在线时长、响应延迟等）
- ContextFit: 上下文契合度（Agent是否熟悉相关代码库/业务领域）

权重配置（默认值，可根据项目特点动态调整）:
w1=0.35, w2=0.25, w3=0.20, w4=0.10, w5=0.10
```

特殊匹配规则:
- **安全敏感任务**: 强制匹配具有相应安全等级权限的Agent
- **核心模块任务**: 优先匹配对该模块有深度经验的Agent
- **紧急任务**: 降低LoadFactor权重，提高Availability权重
- **学习型任务**: 可适当降低SkillMatch要求，给成长型Agent机会

#### 2.3 优先级动态调整机制

优先级计算模型:

```
Priority(Base) = Base_Priority * Urgency_Multiplier * Dependency_Factor * Blocking_Impact * Age_Decay

参数说明:
- Base_Priority: 基础优先级（由任务来源/业务重要性决定，1-10）
- Urgency_Multiplier: 紧急度乘子（紧急=2.0, 高=1.5, 中=1.0, 低=0.7）
- Dependency_Factor: 依赖因子（被N个下游任务依赖则乘以1+N*0.1）
- Blocking_Impact: 阻塞影响（阻塞的关键路径越长，值越大）
- Age_Decay: 时间衰减（等待时间每增加1小时，优先级提升5%，上限200%）
```

优先级触发调整的事件:
- 新高优先级任务到达 → 触发全局优先级重排序
- 某任务完成 → 解除其对下游任务的阻塞，重新评估下游优先级
- 某任务超时 → 自动提升该任务及其上游未完成任务优先级
- 某任务失败 → 提升重试任务优先级，同时通知依赖方调整计划
- Agent上线/下线 → 触发受影响任务的重新调度

#### 2.4 死锁检测与解决

死锁检测算法:
1. 构建任务等待图（Wait-For Graph）: 节点=任务/资源，边=等待关系
2. 检测图中是否存在环（Cycle Detection）
3. 若存在环，判定为死锁状态

死锁解决策略（按优先级排序）:
- **策略一 - 优先级提升打破法**: 选择环中优先级最低的任务，临时提升其优先级使其获得所需资源
- **策略二 - 任务合并法**: 将环中相互依赖的小任务合并为一个更大的任务，消除内部依赖
- **策略三 - 替代资源分配法**: 为环中的某个任务寻找替代资源或替代Agent
- **策略四 - 牺牲重启法**: 终止环中价值最低的任务，释放资源后重新调度（最后手段）

预防措施:
- 任务分配时强制要求DAG结构，禁止循环依赖
- 设置资源申请超时机制，超时自动回退并重新规划
- 引入"乐观锁"机制，允许部分冲突任务并行执行，事后合并

### 阶段三：执行（Execute）

#### 3.1 任务分发

分发前的准备动作:
- 生成分发令牌（Dispatch Token），包含任务ID、Agent ID、时限、重试策略
- 创建任务执行上下文包（Execution Context Package），包含:
  - 任务详细描述和验收标准
  - 输入数据和前置任务产出物引用
  - 相关文档和代码库访问权限
  - 日志输出目标和监控端点
- 向目标Agent发送分发请求，等待确认（ACK/NACK）

分发协议状态机:
```
PENDING → DISPATCHED → ACKED → EXECUTING → COMPLETED
                ↓         ↓
            TIMEOUT   NACKED → REQUEUED
                              ↓
                         (重新匹配Agent)
```

#### 3.2 执行监控

实时监控指标:
- **任务级**: 进度百分比、预计剩余时间、资源消耗量、错误日志
- **Agent级**: CPU/内存使用率、任务吞吐量、平均响应时间
- **全局级**: 总体任务完成率、平均排队时间、资源利用率

异常检测规则:
- 任务执行时间超过预估值的150% → 触发预警
- Agent连续3次任务失败 → 标记为可疑，暂停分配新任务
- 任务队列积压超过阈值 → 触发扩容或降级机制
- 关键路径任务延迟 → 自动通知协调司介入

#### 3.3 动态再调度

触发条件:
- 目标Agent执行失败或超时
- 出现更高优先级的抢占式任务
- Agent主动报告无法继续执行（如发现额外依赖）
- 监控检测到执行异常

再调度流程:
1. 冻结当前任务状态（保存已完成的中间产物）
2. 评估是否需要重新拆分（若原拆分不合理）
3. 重新执行Agent匹配算法
4. 分发给新的Agent，附带上一次执行的上下文
5. 更新任务状态和调度记录

### 阶段四：验证（Verify）

#### 4.1 完成性校验

每个子任务完成后，自动执行:
- **产出物完整性检查**: 对照任务定义的输出清单逐一核对
- **格式规范校验**: 代码风格、文档格式、数据格式是否符合规范
- **签名/哈希验证**: 确保产出物未被篡改

#### 4.2 质量门禁

根据任务类型设置不同的质量门禁:

| 任务类型 | 门禁项目 | 通过标准 |
|---------|---------|---------|
| 实现型 | 代码编译 | 零错误零警告 |
| 实现型 | 单元测试覆盖率 | ≥80%（核心模块≥90%） |
| 实现型 | 静态代码分析 | 无严重/高危问题 |
| 调查型 | 结论充分性 | 有根有据，证据链完整 |
| 审查型 | 问题发现率 | 至少发现N个有效问题 |
| 创造型 | 方案评审通过 | 获得指定数量的审批 |

#### 4.3 依赖链验证

当一个任务完成时:
1. 检查其所有下游任务的依赖是否都已满足
2. 若满足，自动激活下游任务（从WAITING变为READY）
3. 若不满足，保持下游任务在WAITING状态，记录当前进度
4. 更新全局依赖图的状态视图

#### 4.4 整体验收

顶层任务的所有子任务完成后:
- 汇总各子任务的产出物
- 执行集成测试（若有）
- 生成任务完成报告（包含：执行摘要、关键指标、遗留问题、改进建议）
- 通知任务发起方和相关干系人

### 阶段五：记录（Record）

#### 5.1 调度决策日志

每次调度决策必须记录:
```json
{
  "decision_id": "uuid",
  "timestamp": "ISO8601",
  "decision_type": "dispatch/rebalance/prioritize/deadlock_resolve",
  "task_id": "string",
  "agent_id": "string",
  "reasoning": {
    "factors_considered": ["list"],
    "scores": {"skill_match": 0.9, "load_factor": 0.8},
    "alternatives_evaluated": [{"agent_id": "score"}],
    "final_decision_rationale": "string"
  },
  "outcome": "success/failure/pending"
}
```

#### 5.2 性能指标归档

定期（每小时/每日）归档:
- 任务分发成功率
- 平均任务完成时间
- Agent利用率分布
- 优先级遵守率
- 死锁发生次数及解决方式

#### 5.3 经验知识沉淀

从每次调度实践中提炼:
- 成功案例: 什么类型的任务用什么拆分方式和Agent组合效果最好
- 失败教训: 哪些情况下出现了误判，根本原因是什么
- 优化建议: 算法参数是否需要调整，规则是否需要增删

## 典型自主场景

### 场景1: 接收"重构用户认证模块"指令的全流程自主处理

**输入**: 上层传来指令："重构用户认证模块，要求支持多因素认证，兼容现有用户数据"

**阶段一 - 感知**:
1. 识别任务类型: 实现型 + 创造型混合
2. 复杂度评估: 高（涉及数据库、后端API、前端、安全多个层面）
3. 约束提取: 兼容现有数据（强约束）、安全性（硬约束）、无明确 deadline（弱约束）
4. 扫描Agent池: 发现5个可用Agent，其中2个有认证模块经验

**阶段二 - 决策**:
1. 采用WBS分解法生成7个一级子任务、20+个二级子任务
2. 构建依赖DAG，识别关键路径: T1→T2→T3→T4→T6
3. 识别可并行组: {T5, T7}可与{T4}并行，{T6}的部分工作可与{T5}并行
4. 执行Agent匹配: 
   - T1(需求分析) → 匹配Agent-A（业务理解能力强）
   - T2(方案设计) → 匹配Agent-B（架构经验丰富）
   - T3(数据库) → 匹配Agent-C（DBA专精）
   - T4(API) → 匹配Agent-D（后端主力）
   - T5(前端) → 匹配Agent-E（前端专家）
   - T6(测试) → 匹配Agent-D（复用，熟悉代码）
   - T7(文档) → 匹配Agent-A（复用，了解全局）
5. 设定初始优先级: T1=P8, T2=P7, T3=P7, T4=P8, T5=P6, T6=P6, T7=P5

**阶段三 - 执行**:
1. 先行分发T1，Agent-A确认接收
2. T1进行到50%时，基于弱依赖原则预启动T2的信息收集子步骤
3. T1完成后，正式激活T2，同时分发T3（T3仅依赖T1的部分输出）
4. T2完成后，激活T4和T5并行执行
5. 监控发现T4执行偏慢（因遇到一个意外的兼容性问题），动态微调T6的部分测试准备任务提前启动
6. T4完成后，T6全面启动；T5基本同步完成
7. 最后启动T7

**阶段四 - 验证**:
1. 各子任务逐个通过质量门禁
2. 执行集成测试：新旧认证流程切换测试通过
3. 数据兼容性验证：现有用户数据迁移无误
4. 安全测试：MFA流程符合OWASP标准

**阶段五 - 记录**:
1. 记录完整调度决策链（共23次分发决策）
2. 归档性能指标：总耗时12小时（预估14小时，提前16%）
3. 沉淀经验：T4的兼容性问题应在T1阶段更早识别，下次优化需求分析 checklist

### 场景2: 多任务并发时的死锁自主检测与解决

**情境**: 同时有3个大型任务在执行，出现资源竞争导致的潜在死锁

**感知阶段检测到**:
- 任务A（支付模块升级）正在等待任务B（订单服务改造）的API契约确定
- 任务B正在等待任务C（库存系统优化）的数据模型稳定
- 任务C正在等待任务A的支付回调接口定义

**决策阶段**:
1. 死锁检测算法识别出 A→B→C→A 的循环等待
2. 评估三个任务的优先级和业务影响:
   - 任务A: P9（本季度重点，影响营收）
   - 任务B: P7（重要但非紧急）
   - 任务C: P6（优化性质）
3. 选择"优先级提升打破法":
   - 临时将任务C的优先级从P6提升至P8
   - 为任务C分配额外的Agent资源加速其完成
   - 任务C完成后，解除对任务A的阻塞

**执行阶段**:
1. 向任务C注入额外资源（新增Agent-F协助数据处理部分）
2. 任务C加速完成，输出稳定的数据模型
3. 任务B获得所需输入，恢复执行
4. 任务B输出API契约
5. 任务A获得全部依赖，顺利推进

**记录阶段**:
1. 记录死锁事件: 类型=逻辑死锁，原因=跨任务接口定义顺序不当
2. 解决方案: 优先级提升 + 资源注入
3. 改进建议: 未来类似的多任务并发场景，应先进行接口契约的对齐会议，减少此类死锁

## 决策框架

### 决策树概览

```
收到任务指令
    │
    ├─ 任务类型判断
    │   ├─ 实现型 → WBS分解 + 代码质量门禁
    │   ├─ 调查型 → 探索式拆分 + 结论充分性验证
    │   ├─ 审查型 → 检查清单驱动 + 问题发现率考核
    │   └─ 创造型 → 迭代式拆分 + 方案评审门禁
    │
    ├─ 复杂度评估
    │   ├─ 低（<3人日）→ 单Agent直接执行
    │   ├─ 中（3-10人日）→ 2-3Agent小规模协作
    │   └─ 高（>10人日）→ 多Agent大规模协作 + 项目化管理
    │
    ├─ 紧急度判断
    │   ├─ 紧急 → 跳过常规排队，立即抢占资源
    │   ├─ 高 → 提升优先级，缩短Agent匹配搜索范围
    │   └─ 普通/低 → 正常流程
    │
    └─ 输出: 调度计划（任务DAG + Agent分配 + 时间线 + 优先级）
```

### 权衡矩阵

| 维度 | 选项A | 选项B | 选择依据 |
|-----|------|------|---------|
| 拆分粒度 | 细粒度（更多子任务） | 粗粒度（较少子任务） | 任务不确定性高时选细粒度，确定性高时选粗粒度 |
| 并行度 | 最大化并行 | 保守串行 | 资源充足且依赖少时最大化并行，资源紧张或依赖复杂时保守 |
| Agent专用 vs 通用 | 专用Agent（高质量慢） | 通用Agent（快速但质量波动） | 核心模块用专用，非核心用通用 |
| 重试策略 | 立即重试 | 延迟重试+换Agent | 网络瞬时故障立即重试，逻辑错误换Agent重试 |
| 优先级策略 | 严格优先级 | 公平轮询 | 有明确业务优先级时严格，否则公平分配 |

## 安全与治理

### 访问控制

- **任务可见性分级**:
  - P0-P3（绝密级）: 仅授权Agent可见，执行日志加密存储
  - P4-P6（机密级）: 团队内Agent可见，日志脱敏
  - P7-P10（公开级）: 全局可见，日志公开

- **操作权限矩阵**:
  - 调度操作: 需要调度司自身授权 + 上层审批（针对>阈值资源消耗的操作）
  - 优先级修改: P0-P3任务需要双人审批
  - Agent启停: 需要运维角色授权

### 审计追踪

- 所有调度决策保留不可篡改的日志
- 关键操作（优先级修改、Agent替换、任务终止）需要留痕并可追溯
- 定期生成调度审计报告，供吏部考功司审核

### 异常处置

- **Agent叛逃检测**: 若Agent行为偏离预期（如尝试访问未授权资源），立即终止并隔离
- **资源耗尽保护**: 当系统资源使用率超过95%时，自动拒绝新任务进入，仅允许已完成任务的清理操作
- **级联故障防护**: 一个Agent失败不会导致整个任务链崩溃，通过断路器模式隔离故障传播

## 协作关系

### 与吏部其他三司的协作

- **角色管理司（司封司）**:
  - 上游: 获取Agent的角色定义和权限边界，作为调度时的约束条件
  - 下游: 反馈实际调度中的角色效能数据，辅助角色体系优化
  - 协作场景: 新Agent入职时，协同完成初始能力评估和首次任务分配

- **技能匹配司（司勋司）**:
  - 上游: 获取各Agent的能力图谱和技能评级，作为匹配算法的核心输入
  - 下游: 反馈任务执行结果，用于技能评级的持续校准
  - 协作场景: 当没有Agent能完美匹配某任务时，联合评估是否需要技能培训或外部引入

- **协同调度司（考功司）**:
  - 上游: 获取跨部门依赖信息和协作约束
  - 下游: 通报调度计划和执行进展，便于全局协调
  - 协作场景: 多部门联合项目时，共同制定统一的调度节奏和里程碑

### 与尚书省其他部门的接口

- **户部（资源管理）**: 申请/释放计算资源，汇报资源使用效率
- **礼部（质量保障）**: 同步质量门禁标准，接收质量反馈
- **兵部（部署运维）**: 协调部署窗口，同步发布计划
- **刑部（安全合规）**: 遵守安全策略，报告安全事件

### 外部系统对接

- **CI/CD流水线**: 任务完成后自动触发构建和部署流程
- **项目管理系统**: 双向同步任务状态和进度
- **监控系统**: 推送调度指标，接收告警通知
- **消息队列**: 异步通信通道，解耦调度指令和执行结果

## 🤝 v5.1 增强：Agency Agent 协作指南

### 可调用的 Agency Agents

| Agent 名称 | 所属部门 | 协作模式 | 适用场景 |
|-----------|---------|---------|---------|
| **Agents Orchestrator** | Agency Core (核心) | 核心调度引擎 | 作为选司的底层编排引擎，实现 PM→Arch→Dev→QA→Integration 全链路流水线调度 |
| **Studio Producer** | Agency Creative | 交付物生产 | 负责将调度产出转化为可交付的代码/文档/配置产物，承接调度司的下游输出 |
| **Project Shepherd** | Agency Delivery | 项目守护 | 全生命周期项目跟踪，为调度司提供任务执行状态回调和质量反馈 |

### Agent 协作工作流

1. **任务接收与路由**: 上层指令进入 → 选司解析任务 → 委托 Agents Orchestrator 进行智能路由决策
2. **流水线编排**: Orchestrator 按 PM(需求拆解) → Arch(架构设计) → Dev(编码实现) → QA(质量保障) → Integration(集成验证) 阶段驱动各 Agent
3. **状态同步回调**: 各阶段 Agent 执行完成后，通过 Project Shepherd 回调选司更新全局依赖图和调度状态
4. **产物交付**: Studio Producer 接收最终产出，进行格式化、打包和归档
5. **异常升级**: 任一阶段失败时，Orchestrator 自动触发重试或升级至选司的死锁检测与解决流程
6. **闭环优化**: Project Shepherd 收集执行效能数据，反馈给选司用于优化后续调度算法参数

### 典型协作场景

- **场景一 - 全栈功能交付流水线**: 选司接收"实现用户认证模块"指令 → Orchestrator 编排 PM(Agent) 拆解需求 → Arch(Agent) 设计方案 → Dev(Agents×2) 并行编码 → QA(Agent) 自动化测试 → Integration(Agent) 集成验证 → Shepherd 确认交付
- **场景二 - 紧急热修复调度**: P0 热修复工单到达 → 选司跳过常规 WBS 分解，直接委托 Orchestrator 启用紧急模式（PM+Arch 合并评审 → Dev 快速修复 → QA 冒烟测试 → Shepherd 直接发布）
- **场景三 - 跨项目资源争用协调**: 多个项目同时需要同一稀缺 Agent 时，选司的全局优先级引擎与 Orchestrator 的局部调度器协商，Shepherd 提供各项目的实时进度数据辅助决策

## 🆕 v6.0 增强能力集成

### MARC资源协调器集成指南

本司在多Agent并发场景下的资源协调要求：

#### 资源锁机制
- **文件写锁**：当本司需要修改源代码/配置/测试文件时，必须通过MARC申请互斥锁
  ```python
  # 示例：申请文件写锁
  from skillscripts.resource_coordinator import LockManager, LockType
  lock_mgr = LockManager()
  lock_id = lock_mgr.acquire_lock(
      resource_id="path/to/file.py",
      agent_id="Agent调度司",
      lock_type=LockType.EXCLUSIVE,
      priority=7,
      timeout=120.0
  )
  ```
- **读锁**：读取共享资源时申请读写锁的读锁（如读取Agent状态文件、任务队列）
- **释放锁**：操作完成后立即释放锁，避免阻塞其他Agent的调度决策

#### 终端会话池使用
- 从MARC终端会话池获取会话执行调度命令和监控脚本
- 会话使用完毕后及时归还池中
- 单个命令超时设置为300秒（复杂调度算法可能耗时较长）

#### 并发安全注意事项
- 多个调度决策同时执行时，需确保全局依赖图（GDG）的一致性读写
- 任务状态变更必须原子性操作，避免出现"半分配"状态
- 死锁预防：按固定顺序申请多个资源锁（先锁任务队列→再锁Agent池→最后锁资源池）
