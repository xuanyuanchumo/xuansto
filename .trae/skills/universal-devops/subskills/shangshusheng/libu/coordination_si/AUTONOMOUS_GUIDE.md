# 协同调度司 自主操作指南 (Autonomous Operation Guide)

## 概述

**定位**: 尚书省·吏部·考功司，负责跨部门协作编排、冲突检测与解决、多Agent进度同步、沟通协调与异常恢复的核心协同中枢。

**目标**: 在无人干预或少人监督的情况下，自主构建和维护全局依赖拓扑、智能识别并解决各类协作冲突、确保多Agent/多团队间的状态实时对齐、在异常发生时快速恢复系统协调秩序，保障大型复杂项目的顺畅推进。

**核心能力**: 自主冲突解决——自动识别资源冲突、时序冲突、逻辑冲突、数据冲突，并从解决方案库中匹配最优策略进行化解。

## 核心原则

1. **全局最优原则**: 协调决策以整体项目利益最大化为目标，而非局部团队或单个Agent的利益
2. **透明可见原则**: 所有依赖关系、冲突状态、协调决策对相关方完全透明可查
3. **主动预防原则**: 不仅被动响应已发生的冲突，更要主动预测和预防潜在冲突
4. **快速收敛原则**: 冲突发现到解决的周期尽可能短，避免阻塞效应扩散
5. **公平公正原则**: 冲突解决中各方受到平等对待，基于规则和数据而非偏好做决策
6. **弹性恢复原则**: 系统具备自愈能力，单点故障不会导致协调体系崩溃

## 自主操作流程

### 阶段一：感知（Perceive）

#### 1.1 全局依赖拓扑构建与维护

持续维护一个实时的全局任务依赖图（Global Dependency Graph, GDG）:

**GDG 数据模型**:
```
GlobalDependencyGraph = {
    nodes: [  // 节点 = 任务单元（可以是子任务、里程碑、交付物）
        {
            node_id: "string",
            name: "string",
            type: "task/milestone/deliverable/gate",
            owner: "agent_id or team_id",
            status: "not_started/in_progress/blocked/completed/cancelled",
            progress: float (0-100),
            planned_start: "date",
            planned_end: "date",
            actual_start: "date or null",
            actual_end: "date or null",
            priority: int (1-10),
            criticality: "critical/important/normal/low",
            metadata: {...}
        }
    ],
    edges: [  // 边 = 依赖关系
        {
            from_node_id: "string",
            to_node_id: "string",
            dependency_type: "finish_to_start/start_to_start/finish_to_finish/start_to_finish",
            constraint_type: "hard/soft/info/resource",
            lag: int (days, 可为负数表示提前),
            confidence: float (0-1, 该依赖关系的确定性)
        }
    ],
    layers: [  // 层级划分（按团队/部门/子系统）
        {
            layer_id: "string",
            name: "string",
            nodes: ["node_ids"],
            external_dependencies: [{"from_external": "string", "to_internal": "string"}]
        }
    ],
    critical_path: ["node_ids"],  // 当前关键路径
    last_updated: "ISO8601"
}
```

**依赖关系的四种类型**:

| 类型 | 符号 | 含义 | 示例 |
|-----|------|------|------|
| 完成-开始 (FS) | →→ | 前置任务完成后，后置任务才能开始 | 代码编写完成 → 代码审查开始 |
| 开始-开始 (SS) | ⇉ | 前置任务开始后，后置任务才能开始 | 后端开发开始 → 前端联调开始 |
| 完成-完成 (FF) | ⇒⇒ | 前置任务完成后，后置任务才能完成 | 测试用例编写完成 → 测试执行完成 |
| 开始-完成 (SF) | →⇒ | 前置任务开始后，后置任务才能完成 | 监控部署开始 → 验收测试完成 |

**约束类型详解**:
- **硬约束 (Hard)**: 必须严格遵守，违反将导致功能错误或数据损坏
- **软约束 (Soft)**: 建议遵守但可以灵活处理，违反可能影响效率但不影响正确性
- **信息约束 (Info)**: 仅需要信息传递，不需要严格的时间顺序
- **资源约束 (Resource)**: 因共享有限资源而形成的伪依赖

**拓扑构建流程**:
```
1. 自动采集:
   - 从调度司获取任务拆分结果和Agent分配信息
   - 从各Agent的执行报告中提取实际依赖关系
   - 从项目管理工具同步人工定义的依赖
   
2. 智能补全:
   - 基于历史模式推断隐含依赖（如"API设计"通常依赖"需求分析"）
   - 检测并标记缺失的可能依赖（警告级别）
   
3. 一致性校验:
   - 检测循环依赖（应不存在）
   - 检测悬空节点（无前置依赖的开始节点 / 无后续依赖的结束节点是否合理）
   - 检测关键路径合理性
   
4. 可视化呈现:
   - 生成交互式依赖图（支持缩放、筛选、高亮关键路径）
   - 多维度视图: 按时间线 / 按团队 / 按优先级 / 按风险等级
```

#### 1.2 冲突信号实时监测

建立多维度的冲突监测雷达：

**监测维度一览**:

```
ConflictMonitoringRadar:
│
├── 📊 资源维度 (Resource Conflicts)
│   ├── Agent过载检测: 单Agent同时被分配>阈值(如3)个活跃任务
│   ├── 资源争用检测: 多个任务竞争同一独占资源（如数据库迁移窗口）
│   ├── 环境冲突检测: 多个任务需要在同一环境（如Staging）上操作
│   └── 算力瓶颈检测: 计算资源使用率超过安全阈值
│
├── ⏰ 时序维度 (Timing Conflicts)
│   ├── 截止日期冲突: 多个任务的deadline过于接近导致资源挤兑
│   ├── 里程碑对齐问题: 各子系统里程碑不同步导致集成点错位
│   ├── 等待超时预警: 某任务等待依赖的时间超过正常范围
│   └── 关键路径漂移: 关键路径发生变化未及时通知相关方
│
├── 🧠 逻辑维度 (Logical Conflicts)
│   ├── 接口契约矛盾: 下游期望的接口与上游计划交付的不一致
│   ├── 数据模型冲突: 不同模块对同一数据的定义/格式不一致
│   ├── 技术选型分歧: 相关模块使用了不兼容的技术方案
│   └── 需求理解偏差: 不同执行者对同一需求的理解存在差异
│
├── 💾 数据维度 (Data Conflicts)
│   ├── 并发写入冲突: 多个任务同时修改同一数据源
│   ├── 数据版本不一致: 各方使用的不是同一版本的数据
│   ├── 数据权限冲突: 某任务需要的数据被其他任务锁定
│   └── 数据质量争议: 对数据准确性/完整性有不同判断
│
└── 👥 人际/协作维度 (Collaboration Conflicts)
    ├── 沟通延迟: 信息传递耗时超过预期
    ├── 责任推诿: 边界模糊地带无人认领
    ├── 目标不一致: 各方的局部目标与全局目标偏离
    └── 信任度下降: 反复出现的协调问题导致合作意愿降低
```

**监测机制**:
- **实时监测**: 通过事件流（Event Streaming）实时捕获任务状态变化事件，即时计算潜在冲突
- **定期扫描**: 每15分钟执行一次全量冲突扫描，捕获非事件驱动的潜在问题
- **预测性分析**: 基于当前趋势预测未来24-72小时内可能出现哪些冲突
- **分级告警**:
  - 🔴 P0 - 立即阻塞: 已发生的冲突正在阻碍任务进展 → 立即触发解决流程
  - 🟠 P1 - 即将发生: 未来2小时内必然发生的冲突 → 提前介入预防
  - 🟡 P2 - 可能发生: 未来24小时内有可能发生的冲突 → 发出预警和建议
  - 🟢 P3 - 潜在风险: 更长期的可能性 → 纳入观察列表

### 阶段二：决策（Decide）

#### 2.1 冲突类型识别与分类

当监测到冲突信号时，首先进行精确识别和分类：

**冲突分类决策树**:
```
检测到异常信号
    │
    ├─ 是否涉及共享资源的并发访问?
    │   ├─ 是 → 资源冲突 → 进一步判断:
    │   │   ├─ Agent资源? → Agent过载冲突
    │   │   ├─ 环境/基础设施? → 环境冲突
    │   │   ├─ 数据存储? → 数据写入冲突
    │   │   └─ 计算/网络? → 算力瓶颈冲突
    │   │
    └─ 否 → 是否涉及时间安排?
        ├─ 是 → 时序冲突 → 进一步判断:
        │   ├─ Deadline碰撞? → 截止日期冲突
        │   ├─ 依赖等待超时? → 等待超时冲突
        │   └─ 里程碑不对齐? → 同步点冲突
        │
        └─ 否 → 是否涉及内容/规格?
            ├─ 是 → 逻辑冲突 → 进一步判断:
            │   ├─ 接口/契约? → 接口契约冲突
            │   ├─ 数据结构? → 数据模型冲突
            │   ├─ 技术方案? → 技术选型冲突
            │   └─ 需求理解? → 需求偏差冲突
            │
            └─ 否 → 是否涉及多方配合?
                ├─ 是 → 协作冲突
                └─ 否 → 可能是误报 → 标记待观察
```

**冲突严重程度评估矩阵**:

| 影响维度 | 权重 | 评分标准 (1-5分) |
|---------|------|----------------|
| 阻塞程度 | 30% | 1=无影响, 3=轻微延误, 5=完全停滞 |
| 影响范围 | 25% | 1=单任务, 3=多任务, 5=跨项目 |
| 解决难度 | 20% | 1=简单调整, 3=需协商, 5=需重大变更 |
| 紧迫程度 | 15% | 1=宽松, 3=一般, 5=紧急 |
| 重复风险 | 10% | 1=偶发, 3=周期性, 5=高频 |

`Severity_Score = Σ(dimension_score × weight)`
- ≥4.0: 严重冲突 → 最高优先级解决
- 3.0-3.9: 重要冲突 → 高优先级
- 2.0-2.9: 一般冲突 → 正常优先级
- <2.0: 轻微冲突 → 低优先级或暂缓

#### 2.2 冲突解决方案库

针对每种冲突类型，维护一套标准化的解决方案库：

**资源冲突解决方案**:

| 方案编号 | 方案名称 | 适用场景 | 操作方式 | 副作用 |
|---------|---------|---------|---------|-------|
| R-01 | 时间片轮转 | Agent轻度过载 | 将Agent的时间按比例分配给各任务 | 每个任务获得的注意力减少 |
| R-02 | 任务降级 | 非关键任务过载 | 降低非关键任务的质量要求或范围 | 可能产生技术债务 |
| R-03 | 任务转移 | 有替代Agent可用 | 将部分任务重新分配给其他Agent | 新Agent需要上手时间 |
| R-04 | 资源扩容 | 资源不足 | 申请额外的计算/环境资源 | 成本增加 |
| R-05 | 串行化排期 | 环境冲突 | 为冲突的任务排定互斥的使用时间段 | 总时长增加 |
| R-06 | 环境克隆 | 环境冲突且无法串行 | 创建独立的环境副本 | 资源消耗翻倍 |

**时序冲突解决方案**:

| 方案编号 | 方案名称 | 适用场景 | 操作方式 | 副作用 |
|---------|---------|---------|---------|-------|
| T-01 | 快速跟踪 (Fast Tracking) | 需要压缩工期 | 将原串行的任务改为并行执行 | 增加协调成本和返工风险 |
| T-02 | 赶工 (Crashing) | Deadline不可移动 | 投入更多资源加速关键任务 | 成本急剧上升 |
| T-03 |Deadline重协商 | Deadline不合理 | 与干系人协商延期 | 需要管理层的批准 |
| T-04 | 范围裁剪 | 无法按时完成全部 | 移除非核心功能到后续迭代 | 功能缩减 |
| T-05 | 里程碑重对齐 | 子系统间里程碑错位 | 调整各方里程碑使其同步 | 可能影响某方的内部节奏 |
| T-06 | 缓冲吸收 | 小幅延迟 | 使用项目缓冲时间吸收延迟 | 缓冲耗尽后无退路 |

**逻辑冲突解决方案**:

| 方案编号 | 方案名称 | 适用场景 | 操作方式 | 副作用 |
|---------|---------|---------|---------|-------|
| L-01 | 接口协调会 | 接口契约矛盾 | 召集上下游共同敲定接口规范 | 需要会议时间 |
| L-02 | 上游让步 | 上游改动成本低于下游 | 以上游修改接口来适配下游需求 | 上游工作量增加 |
| L-03 | 下游适配层 | 下游改动成本较低 | 下游增加适配层屏蔽差异 | 引入额外间接层 |
| L-04 | 抽象层统一 | 双方改动都合理 | 定义统一的抽象接口，双方分别实现 | 设计复杂度增加 |
| L-05 | 仲裁裁决 | 双方僵持不下 | 由架构师或技术委员会做出裁决 | 败诉方可能有不满 |
| L-06 | 并行验证 | 技术选型分歧 | 允许双方各自做原型验证后再决定 | 耗时较长 |

**数据冲突解决方案**:

| 方案编号 | 方案名称 | 适用场景 | 操作方式 | 副作用 |
|---------|---------|---------|---------|-------|
| D-01 | 写锁机制 | 并发写入冲突 | 对共享数据实施严格的写锁控制 | 吞吐量下降 |
| D-02 | 版本分支 | 数据格式演变中 | 各方在各自的分支上工作，最后合并 | 合并冲突风险 |
| D-03 | 数据所有权明确 | 权责不清 | 明确每个数据域的唯一所有者 | 需要跨团队协议 |
| D-04 | CQRS模式 | 读写冲突严重 | 分离读写模型，各自优化 | 架构复杂度提升 |
| D-05 | 事件溯源 | 数据一致性要求高 | 以事件日志作为数据真相来源 | 存储和查询复杂度增加 |
| D-06 | 数据仲裁 | 数据质量争议 | 由数据管理员或业务方仲裁 | 需要权威角色参与 |

**解决方案选择算法**:
```
SelectBestSolution(conflict):
    candidates = solution_library.get_solutions(conflict.type)
    
    for sol in candidates:
        score = 0
        # 有效性评估: 该方案能否真正解决此冲突?
        score += evaluate_effectiveness(sol, conflict) * 0.35
        # 成本评估: 实施此方案的成本（时间/人力/金钱）
        score += evaluate_cost(sol, conflict) * 0.25
        # 副作用评估: 此方案的副作用可接受程度
        score += evaluate_side_effects(sol, conflict) * 0.20
        # 历史效果: 此类方案在历史上的成功率
        score += historical_success_rate(sol) * 0.15
        # 干系人接受度: 相关方对此方案的接受可能性
        score += stakeholder_acceptance(sol, conflict) * 0.05
        
        sol.score = score
    
    return sorted(candidates, key=lambda x: x.score, reverse=True)[0]
```

#### 2.3 进度同步机制设计

**多Agent状态对齐协议 (Multi-Agent State Alignment Protocol, MASAP)**:

```
协议层次:
┌─────────────────────────────────────────────┐
│         Layer 4: 战略同步层                   │
│    （项目级目标、里程碑、大方向的对齐）          │
│    同步频率: 每日1次 + 重大变更时即时           │
├─────────────────────────────────────────────┤
│         Layer 3: 战术同步层                   │
│    （迭代/阶段级计划、依赖关系、风险的对齐）      │
│    同步频率: 每4小时1次 + 依赖变化时即时        │
├─────────────────────────────────────────────┤
│         Layer 2: 操作同步层                   │
│    （任务级状态、产出物、阻塞问题的对齐）         │
│    同步频率: 每30分钟1次 + 状态变化时即时       │
├─────────────────────────────────────────────┤
│         Layer 1: 事件同步层                   │
│    （原子操作的实时事件流，毫秒级）              │
│    同步频率: 实时                               │
└─────────────────────────────────────────────┘
```

**Layer 2 详细协议 — 任务状态同步**:

```protobuf
message TaskStateUpdate {
    string task_id = 1;
    string agent_id = 2;
    enum Status {
        UNKNOWN = 0;
        NOT_STARTED = 1;
        IN_PROGRESS = 2;
        BLOCKED = 3;
        WAITING_FOR_INPUT = 4;
        COMPLETED = 5;
        CANCELLED = 6;
    }
    Status status = 3;
    float progress_percent = 4;      // 0-100
    repeated Blocker blockers = 5;   // 当前阻塞因素列表
    repeated Output outputs = 6;     // 已产生的输出物
    int64 estimated_remaining_minutes = 7;
    string notes = 8;                // 自由文本备注
    int64 timestamp = 9;             // 事件时间戳
}

message Blocker {
    enum Type {
        DEPENDENCY_NOT_READY = 0;    // 依赖未就绪
        RESOURCE_UNAVAILABLE = 1;    // 资源不可用
        BLOCKED_BY_ISSUE = 2;        // 被某个问题阻塞
        AWAITING_APPROVAL = 3;       // 等待审批
        EXTERNAL_BLOCKER = 4;        // 外部阻塞
        UNKNOWN = 5;
    }
    Type type = 1;
    string description = 2;
    string related_task_id = 3;      // 若是依赖类阻塞，关联的任务ID
    Severity severity = 4;           // 阻塞严重程度
}
```

**同步会话类型**:

| 会话类型 | 触发条件 | 参与者 | 产出 |
|---------|---------|--------|------|
| 心跳同步 | 定时（每30min） | 全部活跃Agent | 状态汇总报告 |
| 依赖唤醒同步 | 前置任务完成 | 前置任务Owner + 后续任务Owners | 交接确认 |
| 阻塞警报同步 | 检测到BLOCKED状态 | 被阻塞Agent + 协调司 + 相关依赖方 | 阻塞分析和缓解方案 |
| 变更通知同步 | 计划/范围/优先级变更 | 受影响的所有Agent | 变更影响评估和新计划 |
| 里程碑同步 | 到达/临近里程碑 | 里程碑涉及的全部Agent | 里程碑验收检查 |
| 日总结同步 | 每日结束时 | 全部Agent + 项目管理者 | 当日进展总结 + 次日计划 |

#### 2.4 异常恢复策略框架

**异常分类与对应恢复策略**:

```
ExceptionRecoveryFramework:
│
├─ 单点失败 (Single Point Failure)
│   │
│   ├─ Agent执行失败
│   │   ├── 策略A - 自动重试 (Retry): 适用于瞬时故障（网络超时、服务暂时不可用）
│   │   │   └── 最大重试3次，指数退避（1s→2s→4s）
│   │   ├── 策略B - 替换Agent (Replace): 适用于Agent自身问题（能力不足、状态异常）
│   │   │   └── 重新调用调度司进行Agent重分配
│   │   ├── 策略C - 任务拆分 (Split): 适用于任务过大导致失败
│   │   │   └── 将失败任务拆分为更小的子任务重新分发
│   │   └── 策略D - 降级执行 (Degrade): 适用于非关键路径上的失败
│   │       └── 标记为已知限制，继续推进后续任务
│   │
│   ├─ 通信链路中断
│   │   ├── 策略A - 切换通道 (Switch Channel): 主通道故障时切换备用通道
│   │   ├── 策略B - 本地队列缓存 (Local Buffering): 消息暂存本地，恢复后重发
│   │   └── 策略C - 断路器模式 (Circuit Breaker): 连续失败N次后停止尝试，定时探测恢复
│   │
│   └─ 数据损坏/丢失
│       ├── 策略A - 回滚至最近快照 (Rollback): 从最近的完好状态恢复
│       ├── 策略B - 从副本重建 (Reconstruct): 从备份或其他Agent处获取数据重建
│       └── 策略C - 幂等重放 (Idempotent Replay): 重新执行操作（若操作满足幂等性）
│
├─ 级联失败 (Cascading Failure)
│   │
│   ├── 检测: 监控失败传播链，当一个失败引发≥2个下游失败时判定为级联
│   ├── 隔离: 立即将失败区域与其他区域隔离（断路器全开）
│   ├── 稳定: 让隔离区域内的问题自行稳定（不再注入新任务）
│   ├── 评估: 分析根因和影响范围
│   ├── 恢复: 按依赖反序逐步恢复（先恢复最上游的失败点）
│   └── 预防: 在依赖图中添加保护机制防止再次发生
│
└─ 协调中枢故障 (Coordinator Failure)
    ├── 策略A - 热备切换 (Failover): 立即切换到备用协调实例
    ├── 策略B - 降级自治 (Degraded Autonomy): 各Agent进入自主模式，
    │   使用预定义的简单协调规则维持基本运转
    └── 策略C - 人工接管 (Manual Takeover): 发送最高级别告警，
        等待人类管理者接管协调职责
```

### 阶段三：执行（Execute）

#### 3.1 冲突解决执行流程

```
ConflictResolutionExecution:
    
    Step 1 - 冲突宣告 (Declare)
    ├── 生成冲突ID和正式记录
    ├── 向所有受影响的Agent/团队发送冲突通知
    ├── 在全局依赖图上标记冲突区域（红色高亮）
    └── 设定解决时限（根据严重程度: P0=1h, P1=4h, P2=24h, P3=72h）
    
    Step 2 - 方案实施 (Implement)
    ├── 执行选定的解决方案
    ├── 对于需要多方配合的方案，协调各方行动顺序
    ├── 实时跟踪方案执行进度
    └── 记录每一步的操作和中间状态
    
    Step 3 - 效果验证 (Verify)
    ├── 确认冲突症状是否消除
    ├── 检查是否引入了新的冲突（二次冲突）
    ├── 收集相关方的反馈
    └── 若未解决，返回Step 2选择替代方案
    
    Step 4 - 状态更新 (Update)
    ├── 更新全局依赖图（移除冲突标记）
    ├── 向所有相关方发送冲突解决通知
    ├── 更新冲突统计指标
    └── 触发经验沉淀流程
```

#### 3.3 异常恢复执行

**级联失败恢复的具体步骤示例**:

```
场景: Agent-D（后端API开发者）失败 → 导致Agent-E（前端联调者）阻塞 
      → Agent-F（集成测试者）阻塞 → Agent-G（部署准备者）阻塞

恢复执行:
1. 检测 (T+0min):
   - 发现失败传播链长度=4，判定为级联失败
   - 触发P0级告警
   
2. 隔离 (T+2min):
   - 将Agent-D/E/F/G所在的任务区域标记为"隔离区"
   - 暂停向该区域分配新任务
   - 通知隔离区内所有Agent进入"等待协调"状态
   
3. 根因定位 (T+10min):
   - 分析Agent-D失败原因: 数据库连接池耗尽导致的OOM
   - 确认根因: 数据库连接配置不当（max_connections设置过低）
   
4. 修复 (T+25min):
   - 修复数据库连接配置
   - 重启Agent-D
   - Agent-D恢复健康
   
5. 渐进恢复 (T+30min起):
   - Phase 1: Agent-D重新执行其失败的任务 → 完成
   - Phase 2: 解除Agent-E的阻塞，通知其依赖已就绪 → Agent-E恢复
   - Phase 3: Agent-F收到Agent-E的产出 → 恢复执行
   - Phase 4: Agent-G收到Agent-F的产出 → 恢复执行
   
6. 复盘 (T+120min):
   - 生成事故报告
   - 更新预防措施: 在依赖图中增加"DB连接池监控"检查点
   - 通知相关方恢复完成
```

### 阶段四：验证（Verify）

#### 4.1 协调效能度量指标

| 指标类别 | 指标名称 | 计算公式 | 目标值 |
|---------|---------|---------|--------|
| 及时性 | 平均冲突解决时间 | 从检测到解决的平均时长 | P0<1h, P1<4h, P2<24h |
| 及时性 | 进度同步延迟 | 状态变化到同步完成的平均延迟 | <15min |
| 有效性 | 冲突一次解决率 | 第一次尝试即成功解决的冲突占比 | >80% |
| 有效性 | 二次冲突率 | 解决后又复发或产生新冲突的比例 | <10% |
| 完整性 | 依赖覆盖率 | 已纳入GDG的依赖 / 实际存在的总依赖 | >95% |
| 完整性 | 同步参与率 | 应参与同步但缺席的Agent比例 | <5% |
| 满意度 | 协调满意度评分 | 相关Agent对协调结果的满意度(1-5) | >4.0 |
| 稳定性 | 异常恢复成功率 | 异常发生后成功恢复正常的比例 | >95% |

#### 4.2 依赖图健康检查

- **完整性**: 是否有遗漏的依赖关系？
- **准确性**: 已记录的依赖关系是否仍然有效？
- **时效性**: 节点的状态信息是否是最新的？
- **合理性**: 关键路径是否符合预期？是否有意外的关键路径出现？

#### 4.3 冲突模式分析

统计分析冲突的发生模式:
- 哪种类型的冲突最高发？（指导预防重点）
- 哪些Agent/团队最容易卷入冲突？（指导能力建设）
- 哪些时段冲突最密集？（指导资源调度）
- 哪些解决方案的成功率最高？（优化解决方案库排序）

## 典型自主场景

### 场景1: 大型跨团队项目的全周期协调自治

**情境**: "电商平台3.0重构"项目——涉及前端组（3人）、后端组（4人）、数据组（2人）、运维组（2人）、安全组（1人），共12个Agent，历时3个月。

**自主协调全过程**:

**Phase 1 - 项目启动协调（第1周）**:
1. **依赖拓扑初始化**:
   - 收集各团队的WBS，合并为全局依赖图
   - 识别跨团队的关键依赖:
     - 后端API定义 → 前端开发（强依赖）
     - 数据模型设计 → 后端实现 + 前端展示（双强依赖）
     - 安全合规评审 → 集成测试（硬约束）
     - 基础设施搭建 → 所有开发活动（前置依赖）
   - 检测到初始依赖图中存在2处潜在冲突:
     - 冲突①: 前端组和后端组都需要在第2周使用Staging环境做首次联调
     - 冲突②: 安全组的合规评审窗口（第6周）与原计划的首次发布（第5周末）冲突
2. **主动冲突预防**:
   - 冲突①解决方案: 采用R-05（串行化排期），前端组周一三用Staging，后端组周二四用，周五共用
   - 冲突②解决方案: 采用T-03（Deadline重协商），将首次发布推迟到第6周中，与安全评审衔接
3. **同步机制建立**:
   - 设立Layer 2同步: 每30分钟心跳
   - 设立Layer 3同步: 每日晨会 + 每周五跨团队同步会
   - 设立Layer 4同步: 每两周里程碑评审

**Phase 2 - 执行期协调（第2-10周）**:
1. **第3周 — 检测到接口契约冲突**:
   - 信号: 前端组实现的Mock API与后端组最终确定的API规范存在5处不一致
   - 类型: 逻辑冲突（L-01接口契约矛盾）
   - 严重程度: 3.8（重要）
   - 解决: 自动召集前后端接口协调会（15分钟），逐一敲定5处差异的处理方式（3处以后端为准改前端，2处以前端合理需求为准改后端）
   - 结果: 47分钟内解决，未影响整体进度

2. **第5周 — 检测到Agent过载冲突**:
   - 信号: 后端组的Agent-L（Tech Lead）同时承担4个活跃任务，且其中3个在关键路径上
   - 类型: 资源冲突（R-01 Agent过载）
   - 严重程度: 4.1（严重）
   - 解决: 组合方案:
     - R-03（转移）: 将代码审查任务转移给Agent-M
     - R-02（降级）: 将技术文档编写的详细程度要求从"完整"降为"核心要点版"
   - 结果: Agent-L负载降至2.5个任务的健康水平

3. **第7周 — 数据模型冲突爆发**:
   - 信号: 后端组和数据组对"用户画像"的数据结构定义完全不同（后端偏向事务型，数据组偏向分析型）
   - 类型: 逻辑冲突（L-02数据模型冲突）+ 协作冲突（责任推诿）
   - 严重程度: 4.5（严重+）
   - 解决: 采用L-04（抽象层统一）：
     - 定义统一的"用户画像核心实体"（包含双方共同需要的字段）
     - 后端在此基础上扩展"事务扩展属性"
     - 数据组在此基础上扩展"分析扩展属性"
     - 通过事件机制保持两部分的数据最终一致性
   - 附加措施: 召开数据治理专项会，明确未来类似情况的数据所有权规则
   - 结果: 3小时内达成一致，虽然引入了一定的架构复杂度，但彻底解决了根本分歧

4. **第9周 — 发布前级联风险**:
   - 信号: 运维组的一个部署脚本Bug导致预发布环境回滚，阻塞了前端组、后端组、测试组的所有验证活动
   - 类型: 级联失败（单点失败→扩散）
   - 严重程度: 4.8（危急）
   - 恢复执行:
     - 立即隔离: 将预发布环境标记为维护状态，暂停所有依赖它的任务
     - 快速修复: 运维组在45分钟内修复脚本Bug并重新部署
     - 渐进恢复: 按"运维→后端→前端→测试"的顺序依次解除阻塞
     - 补偿措施: 为被延误的团队追加24小时的缓冲时间
   - 结果: 总影响时间约3小时，通过加班追赶回大部分进度

**Phase 3 - 收尾协调（第11-12周）**:
1. **最终集成协调**: 组织全量集成测试的协调，确保所有组件在同一环境下正确协作
2. **上线发布协调**: 协调各组的上线顺序、回滚预案、监控交接
3. **项目复盘协调**: 生成完整的协调效能报告:
   - 总冲突数: 17次
   - 平均解决时间: 2.3小时（目标<4h，✅达标）
   - 一次解决率: 82%（目标>80%，✅达标）
   - 最大单次影响: 3小时（第9周的级联事件）
   - 关键成功因素: 早期的依赖图构建和预防性协调避免了大量潜在冲突

### 场景2: 多项目并发时的资源共享冲突自主调解

**情境**: 同时运行3个项目（Project-A电商重构、Project-B数据中台、Project-C安全加固），共享同一个由5个Agent组成的核心团队。

**检测到的冲突**:
1. **Agent-X（全栈主力）同时被三个项目需要**:
   - Project-A: 需要其在第2周完成支付模块重构（关键路径）
   - Project-B: 需要其在第2周完成API网关对接（关键路径）
   - Project-C: 需要其在第2周进行安全渗透测试（关键路径）
   - 三者的时间窗口完全重叠

2. **Staging环境争用**:
   - Project-A需要在Week 2周三做集成验证
   - Project-B需要在Week 2周四做性能测试
   - Project-C需要在Week 2周五做安全扫描
   - 但Staging环境每次切换需要半天的环境准备和清理

**自主调解过程**:

**冲突1 — Agent-X的三方争夺**:
- 严重程度评估: 4.6（严重，三个都是关键路径）
- 方案评估:
  - R-01（时间片轮转）: 效果差，每个项目只能得到33%的注意力
  - R-03（转移）: 无合适替代Agent（其他人技能不够）
  - R-02（降级）: 三个都是关键任务，难以降级
  - 创新方案 — 错峰执行 + 优先级重排:
    - 与三个项目的管理者协商（提供数据分析支持）:
    - 最终方案:
      - Project-C的安全渗透测试提前到Week 1末（利用Agent-X在该周的空闲时间）→ Project-C同意小幅调整
      - Project-A的支付模块重构保持Week 2上半周（优先级最高，影响营收）
      - Project-B的API网关对接延后半周到Week 2下半周+Week 3初 → Project-B接受（因其还有其他准备工作可先行）
- 执行结果: Agent-X的负载变为连续3周每周约70%（健康水平），三个项目均未被阻塞

**冲突2 — Staging环境争用**:
- 严重程度评估: 2.8（一般）
- 方案选择: R-06（环境克隆）vs R-05（串行化排期）
- 决策: 采用混合方案:
  - 为Project-C的安全扫描创建一个专用的安全测试环境（轻量级克隆，仅用于扫描）
  - Project-A和Project-B仍共用Staging，采用串行排期（周三A，周四B）
- 执行结果: 成功化解，总成本增加可控（安全测试环境资源消耗很小）

**事后改进建议**:
1. 建议扩充核心团队规模（至少增加1名全栈Agent作为弹性资源）
2. 建议建立多环境策略（Dev/Staging-QA/Staging-Perf/Pre-prod），减少环境争用
3. 建议未来的多项目规划中加入"共享资源容量检查"环节

## 决策框架

### 协同调度决策树

```
收到协调需求 / 检测到异常信号
    │
    ├─ 信号类型判断
    │   ├─ 冲突信号 → 进入冲突解决流程
    │   │   ├── 分类: 资源/时序/逻辑/数据/协作
    │   │   ├── 评级: 严重程度打分
    │   │   ├── 匹配: 从解决方案库选择最优方案
    │   │   ├── 执行: 实施解决方案
    │   │   └── 验证: 确认解决效果
    │   │
    │   ├─ 同步需求 → 进入进度同步流程
    │   │   ├── 判断层级: 事件/操作/战术/战略
    │   │   ├── 确定参与者
    │   │   ├── 执行同步协议
    │   │   └── 输出同步报告
    │   │
    │   ├─ 异常信号 → 进入恢复流程
    │   │   ├── 分类: 单点/级联/中枢故障
    │   │   ├── 隔离: 控制影响范围
    │   │   ├── 修复: 解决根因
    │   │   ├── 恢复: 渐进恢复正常运作
    │   │   └── 复盘: 提炼经验教训
    │   │
    │   └─ 规划需求 → 进入协调规划流程
    │       ├── 构建/更新依赖拓扑
    │       ├── 设立同步机制
    │       ├── 制定应急预案
    │       └── 输出协调计划文档
    │
    └─ 输出: 协调决策 + 执行指令 + 状态更新 + 通知消息
```

### 权衡矩阵

| 维度 | 选项A | 选项B | 选择依据 |
|-----|------|------|---------|
| 协调粒度 | 细粒度（每个子任务都协调） | 粗粒度（仅里程碑级协调） | 高风险/高复杂度项目细粒度，低风险项目粗粒度 |
| 冲突解决风格 | 主动干预 | 放任自洽 | 紧急/严重影响的项目主动干预，成熟团队可适度放权 |
| 同步频率 | 高频同步（实时） | 低频同步（每日） | 动态变化大的项目高频同步，稳定项目低频同步 |
| 恢复策略 | 快速恢复优先 | 根因分析优先 | 业务连续性要求高的场景快速恢复，可容忍中断的场景先分析 |
| 决策集中度 | 中央集权协调 | 分布式自治协调 | 跨团队/跨部门项目中央集权，单一团队内分布式 |

## 安全与治理

### 协调数据安全

- 依赖拓扑图中可能包含敏感的项目信息和架构细节，访问需授权
- 冲突记录中涉及的Agent表现数据属于个人绩效相关信息，需妥善保护
- 同步通信内容加密传输，防止信息泄露

### 协调权限管控

- **常规协调操作**: 自主执行，无需审批
- **涉及优先级变更的协调**: 需通知相关项目经理
- **涉及跨部门资源重新分配的协调**: 需要吏部尚书或更高层级的审批
- **涉及外部依赖方承诺变更的协调**: 需要法务/商务角色参与审核

### 协调审计

- 所有P0/P1级别的冲突解决过程必须完整记录并可审计
- 定期生成协调效能审计报告
- 异常恢复事件必须进行事后复盘（Post-mortem）

## 协作关系

### 与吏部其他三司的协作

- **Agent调度司（选司）**:
  - 上游: 调度司的任务分配结果是本司构建依赖拓扑的核心输入
  - 下游: 本司发现的资源冲突和Agent过载问题反馈给调度司，触发重新调度
  - 协作场景: 每日联合审视全局任务分布和Agent负载；级联失败时共同制定恢复方案

- **角色管理司（司封司）**:
  - 获取角色定义中的协作关系和接口人信息
  - 当角色边界不清导致协作冲突时，联动角色管理司进行角色澄清
  - 协作场景: 跨团队项目中共同定义各方的角色接口和协作协议

- **技能匹配司（司勋司）**:
  - 当冲突的根本原因是能力不足时（如无人能解决某技术难题），请求技能匹配司协助寻找具备相应能力的Agent或制定培养计划
  - 协作场景: 团队技能缺口导致的瓶颈冲突的联合解决

### 与尚书省其他部门的接口

- **户部（资源管理）**: 共享资源的容量管理和分配协调
- **礼部（质量保障）**: 质量门禁处的协调（如集成测试的时机安排）
- **兵部（部署运维）**: 部署窗口和环境资源的协调
- **刑部（安全合规）**: 安全评审和安全事件的协调处理

### 外部系统对接

- **项目管理工具（Jira/Linear/Asana等）**: 任务状态双向同步
- **即时通讯工具（Slack/Teams/飞书等）**: 协调通知和沟通渠道
- **日历系统（Google Calendar/Outlook等）**: 会议安排和时间协调
- **可视化工具（Miro/Mermaid等）**: 依赖图和冲突图的可视化展示

## 🤝 v5.1 增强：Agency Agent 协作指南

### 可调用的 Agency Agents

| Agent 名称 | 所属部门 | 协作模式 | 适用场景 |
|-----------|---------|---------|---------|
| **Studio Operations** | Agency Operations | 运营协调中枢 | 作为考功司跨职能协调的执行臂，负责协调日常运营活动、资源调度和沟通管理，增强多团队协同效率 |
| **Project Shepherd** | Agency Delivery | 项目守护者 | 为考功司的全局依赖拓扑提供项目级的状态锚点和异常上报通道，充当"分布式协调传感器" |

### Agent 协作工作流

1. **全局态势感知**: 考功司构建 GDG 全局依赖拓扑 → Studio Operations 从各项目/团队采集实时运营数据（SLA 状态、资源水位、人员可用性）→ 注入 GDG 作为上下文层
2. **冲突前置预防**: Studio Operations 基于运营日历（发布窗口、大促期、冻结期）提前识别潜在的资源/时间冲突 → 推送考功司进行预调度调整
3. **依赖链路监控**: Project Shepherd 监控各自负责项目的关键依赖链路状态 → 发现阻塞或延迟风险时立即上报考功司 → 触发 MASAP 同步协议
4. **跨团队协调执行**: 考功司检测到跨团队冲突 → 制定解决方案 → Studio Operations 作为协调执行者推动各方落实 → Shepherd 验证解决效果
5. **异常快速恢复**: 级联失败发生时 → Studio Operations 执行隔离和应急措施 → Shepherd 逐级确认恢复状态 → 考功司记录完整恢复剧本
6. **协调效能复盘**: 定期由 Studio Operations 汇总协调指标（平均解决时间、一次解决率）→ 考功司分析模式趋势 → 优化冲突解决方案库排序策略

### 典型协作场景

- **场景一 - 大促期间全链路护航**: 电商大促前 Studio Operations 输出全公司运营日历（包含各团队的发布冻结期、值班安排）→ 考功司据此调整 GDG 中的时间约束 → 大促期间 Shepherd 实时监控各项目健康度 → 任何 P0 阻塞立即触发 Studio Ops 应急响应流程
- **场景二 - 跨部门依赖死锁破解**: A部门等待B部门的API契约 → B部门等待C部门数据模型 → C部门等待A部门的验收标准 → 考功司检测到环状依赖 → Studio Operations 召集三方协调会 → Shepherd 分别跟踪各方承诺的交付 → 考功司验证环路解除
- **场景三 - 分布式协调网络**: 5个项目并行运行，每个项目的 Shepherd 作为本地协调节点 → 定期向考功司心跳同步 → 考功司维护全局视图 → 当某 Shepherd 检测到可能影响其他项目的风险时，通过考功司广播预警

## 🆕 v6.0 增强能力集成

### MARC资源协调器集成指南

本司在多Agent并发场景下的资源协调要求：

#### 资源锁机制
- **文件写锁**：当本司需要修改全局依赖图（GDG）、冲突记录、协调决策日志时，必须通过MARC申请互斥锁
  ```python
  # 示例：申请文件写锁
  from skillscripts.resource_coordinator import LockManager, LockType
  lock_mgr = LockManager()
  lock_id = lock_mgr.acquire_lock(
      resource_id="path/to/global_dependency_graph.json",
      agent_id="协同调度司",
      lock_type=LockType.EXCLUSIVE,
      priority=9,
      timeout=180.0
  )
  ```
- **读锁**：读取GDG、Agent状态、项目进度时申请读锁（高频率读取场景）
- **释放锁**：协调决策完成并更新GDG后立即释放锁，避免阻塞其他司的状态查询

#### 终端会话池使用
- 从MARC终端会话池获取会话执行冲突检测脚本和协调通知命令
- 会话使用完毕后及时归还池中
- 单个命令超时设置为300秒（复杂冲突解决可能涉及多方协商）

#### 并发安全注意事项
- GDG的全局依赖图是核心共享资源，写入时必须独占锁保护
- 多个冲突同时发生时，按严重程度（P0>P1>P2>P3）顺序串行处理
- 死锁预防：按固定顺序申请锁（先锁GDG→再锁冲突记录→最后锁通知通道）

### 四维度输出防线集成
