# 角色管理司 自主操作指南 (Autonomous Operation Guide)

## 概述

**定位**: 尚书省·吏部·司封司，负责AI Agent角色体系的定义、权限管理、职责边界划分与动态调整的核心治理中枢。

**目标**: 在无人干预或少人监督的情况下，自主完成角色模板的创建与演化、RACI矩阵的动态生成与维护、权限边界的智能管控、团队结构的优化建议，确保多Agent协作体系中的权责清晰、分工合理、协作高效。

**核心能力**: 自主角色动态调整——根据项目阶段、任务特性、团队能力变化，自动优化角色配置和权限分配。

## 核心原则

1. **最小权限原则（PoLP）**: 每个Agent仅授予完成任务所需的最小权限集合，默认拒绝一切未明确授权的操作
2. **职责分离原则（SoD）: 关键操作必须由不同角色的Agent分别执行，防止单点权力过于集中
3. **角色即服务原则**: 角色不是静态标签，而是可组合、可继承、可演化的能力服务包
4. **动态适配原则**: 角色配置随项目生命周期和业务需求自动演进，而非一成不变
5. **可审计原则**: 所有角色变更、权限授予、职责调整都必须有完整的审计轨迹
6. **人机协同原则**: 高风险角色变更需要人工审批，低风险变更可自主执行并事后报备


### 阶段二：决策（Decide）

#### 2.1 RACI矩阵动态生成算法

RACI模型定义:
- **R (Responsible)**: 负责执行 — 谁实际完成这项工作
- **A (Accountable)**: 最终问责 — 谁对结果负最终责任（每个任务只能有一个A）
- **C (Consulted)**: 咨询参与 — 谁需要在决策前被咨询意见
- **I (Informed)**: 知情通知 — 谁需要在完成后被告知结果

自动生成流程:

**Step 1 - 任务清单提取**: 从当前项目的工作分解结构（WBS）中提取所有可分配的任务项

**Step 2 - 任务特征分类**:
```python
task_classification_rules = {
    "架构决策类": {"required_roles": ["架构师", "技术负责人"], "A": "唯一", "R": "单", "C": "多"},
    "代码实现类": {"required_roles": ["开发工程师"], "A": "模块负责人", "R": "单或小团队", "C": "可选"},
    "代码审查类": {"required_roles": ["资深开发者", "安全专员"], "A": "PR创建者", "R": "审查者", "C": "作者"},
    "测试验证类": {"required_roles": ["QA工程师"], "A": "测试负责人", "R": "执行者", "I": "开发团队"},
    "部署发布类": {"required_roles": ["DevOps工程师", "运维人员"], "A": "发布经理", "R": "执行者", "I": "全团队"},
    "安全合规类": {"required_roles": ["安全官", "合规专员"], "A": "安全负责人", "R": "检查者", "C": "相关干系人"},
    "文档编写类": {"required_roles": "技术写作者或任务执行者本人", "A": "文档负责人", "R": "编写者", "I": "使用者"}
}
```

**Step 3 - 角色映射与冲突消解**:
1. 将分类规则中的抽象角色名映射到具体的Agent实例
2. 检查是否存在以下冲突：
   - **A重叠冲突**: 同一任务有多个Agent标记为A → 强制合并为单一A，其余降为C或R
   - **R空缺冲突**: 某任务无人负责 → 从候选池中按能力匹配自动指派
   - **C过度膨胀**: 咨询人数过多导致决策效率低下 → 设置C上限（建议≤3人），超出的转为I
   - **I遗漏**: 关键干系人未被列入知情名单 → 自动补充（基于依赖关系图推导）

**Step 4 - 矩阵输出与可视化**:

生成的RACI矩阵示例（以用户认证重构项目为例）:

| 任务项 | 架构师-AgentB | 后端-Lead-D | DBA-AgentC | 前端-AgentE | QA-AgentF | 安全-G | 文档-A |
|-------|--------------|------------|-----------|------------|----------|--------|--------|
| 需求分析 | A/R | C | I | I | I | C | I |
| 方案设计 | A/R | C | C | I | I | C | I |
| DB设计 | C | C | A/R | I | I | C | I |
| API实现 | C | A/R | C | I | I | C | I |
| 前端实现 | C | C | I | A/R | I | I | I |
| 单元测试 | I | R | I | R | A | I | I |
| 集成测试 | I | C | C | C | A/R | C | I |
| 安全审计 | C | I | I | I | C | A/R | I |
| 文档更新 | C | C | I | C | I | I | A/R |
| 发布部署 | I | R | R | I | C | C | I |

```
│   ├── 能力要求: 学习能力强、技术视野广、敢于尝试

    ├── 权限相对宽松，鼓励创新尝试
    ├── 沟通频率高，每日同步机制

```

**项目稳定期（构建+过渡期）推荐配置**:

```
建议团队结构:
├── 核心交付层
│   ├── 后端开发组（2-3人）：专注API和业务逻辑
│   ├── 前端开发组（1-2人）：专注UI/UX和交互
│   ├── 数据工程组（1人）：专注数据库和数据管道

│   ├── 架构师（0.5人FTE）：技术决策和技术债务管理

    ├── 角色边界清晰，职责划分明确
    ├── 权限精细化，遵循最小权限原则
```

**结构调整触发条件**:
- 项目进入新阶段（如从构建期转入过渡期）
- 团队规模发生显著变化（增减超过30%）
- 出现反复出现的跨角色瓶颈（某角色持续过载）
- 新的技术栈或业务领域引入
- 连续两个迭代的速度或质量指标偏离预期

#### 2.3 角色冲突检测与解决

**冲突类型识别矩阵**:

| 冲突类型 | 检测方法 | 影响程度 | 解决策略 |
|---------|---------|---------|---------|
| R重叠冲突 | 同一任务多个R | 中等 | 主R+副R模式，或拆分为子任务 |
| A缺失冲突 | 任务无A | 高 | 自动指派最合适的上级或相关方 |
| 权限越界冲突 | Agent操作超出其角色权限 | 高 | 记录告警 + 临时授权审批 + 事后权限修正 |
| 职责模糊冲突 | 多个角色对同一工作推诿 | 中等 | 明确归属规则 + 引入仲裁机制 |
| 能力不匹配冲突 | 角色要求的能力 > Agent实际能力 | 中高 | 能力提升计划 或 角色降级/替换 |
| 过度集中冲突 | 单个Agent承担过多R/A | 高 | 负载分散 + 培养备份角色 |

**R重叠冲突解决方案详解**:

场景: 代码审查任务同时指派了Agent-P（后端Lead）和Agent-S（安全专员）为R

解决方案选项评估:
- **选项A - 顺序审查**: Agent-P先审功能正确性，Agent-S再审安全性
  - 优点: 各自专注，审查深度有保证
  - 缺点: 耗时长，可能阻塞后续流程
  - 适用: 安全敏感度高的重要PR
- **选项B - 并行分域审查**: 同时审查，Agent-P关注业务逻辑，Agent-S关注安全问题
  - 优点: 速度快，充分利用并行
  - 缺点: 可能遗漏交叉领域问题
  - 适用: 常规PR，时效性要求高
- **选项C - 主副审查制**: 设Agent-P为主审（有最终否决权），Agent-S为副审（提建议）
  - 优点: 决策效率高，责任清晰
  - 缺点: 副审可能积极性降低
  - 适用: 团队成熟度高的情况

自主决策规则: 默认采用选项B；若任务安全等级≥高，则采用选项A；若处于紧急发布窗口，则采用选项C。

#### 2.4 权限边界动态管理体系

**权限分级框架**:

```
Level 0 - 只读访问 (Read)
├── 可查看代码、文档、配置
├── 可查看任务状态和日志
└── 不可修改任何内容

Level 1 - 受限编辑 (Edit-Limited)
├── 可编辑自己负责的代码文件
├── 可创建和编辑自己的任务/工单
├── 可在沙箱环境中运行测试
└── 不可修改共享配置、生产环境

Level 2 - 标准编辑 (Edit-Standard)
├── 可编辑所属模块的全部代码
├── 可合并代码到开发分支
├── 可配置开发和测试环境
└── 仍需审批才能影响生产环境

Level 3 - 高级权限 (Advanced)
├── 可合并代码到主分支（需另一人审批）
├── 可修改部分生产配置（需记录）
├── 可管理其他Agent的任务分配
└── 可发起发布流程

Level 4 - 管理员权限 (Admin)
├── 可修改所有环境和配置
├── 可管理其他Agent的权限
├── 可删除关键数据和资源
└── 操作需双人审批 + 审计日志

Level 5 - 超级管理员 (SuperAdmin) [仅限特殊时期启用]
├── 完全控制权
├── 仅在系统初始化或紧急恢复时使用
└── 启用需最高级别人工审批
```

**动态权限调整规则**:
- **临时提权**: 当Agent需要执行一次超出其常规权限的操作时
  - 流程: 申请→自动风险评估→低风险自动批准/高风险转人工→限时生效（如2小时）→到期自动回收
  - 示例: 开发Agent需要临时查看生产日志排查问题 → 自动批准Level 0→Level 1（只读日志），限时1小时
- **阶段性调权**: 随项目阶段变化批量调整
  - 流程: 阶段切换检测→推荐权限配置方案→批量应用→通知相关Agent
  - 示例: 项目从构建期进入过渡期 → 测试Agent从Level 1提升至Level 2（需要更多环境操作权限）
- **基于行为的权限演化**: 
  - 若某Agent连续N次成功执行某类操作且无安全事件 → 考虑将该操作纳入其常规权限范围
  - 若某Agent触发表M次权限越界告警 → 自动降级其权限等级并进行安全审查

#### 2.5 跨团队协作角色定义

**外部接口人自动指定算法**:

输入: 本项目的依赖外部团队/系统列表
输出: 每个依赖对应的本方接口人（Interface Agent）指定方案

```
指定逻辑:
For each external_dependency:
    1. 分析依赖类型:
       - 技术依赖（API调用/数据交换）→ 指定技术接口人
       - 业务依赖（流程对接/决策协同）→ 指定业务接口人
       - 管理依赖（资源申请/审批流转）→ 指定管理接口人
    
    2. 评估接口人资质要求:
       - 技术能力匹配度 ≥ 80%
       - 沟通协作能力评级 ≥ B+
       - 可用性（非关键路径上的核心角色）
       - 历史协作表现（若有过往合作记录）
    
    3. 候选排序与选择:
       - 按综合得分排序
       - 排名第一的自动指定为主接口人
       - 排名第二的指定为备份接口人
    
    4. 生成接口协议:
       - 明确接口人的职责范围
       - 定义沟通渠道和响应SLA
       - 约定升级（Escalation）路径
```

### 阶段三：执行（Execute）

#### 3.1 角色模板实例化

当确定需要为新项目/新任务创建角色配置时：

1. **从模板库检索最接近的基础模板**
   - 模板库包含: Web开发项目模板、数据分析项目模板、DevOps项目模板、安全审计项目模板等
   - 相似度计算基于: 技术栈匹配度、团队规模匹配度、复杂度匹配度

2. **基于项目特性进行定制化调整**
   - 增加项目特有的角色（如"AI模型训练师"、"合规审查员"）
   - 删除不需要的角色
   - 调整已有角色的权限范围
   - 设置角色间的协作关系

3. **生成角色定义文档**
   - 包含: 角色名称、职责描述、权限列表、技能要求、协作关系、绩效指标

4. **将角色分配给具体Agent**
   - 输出: Agent-ID → Role-ID 的映射表
   - 通知各Agent其新角色及配套权限

#### 3.2 权限变更实施

权限变更的类型和处理流程:

| 变更类型 | 风险等级 | 审批要求 | 生效方式 |
|---------|---------|---------|---------|
| 新增低风险权限 | 低 | 自主审批 | 即时生效 |
| 新增高风险权限 | 高 | 双人审批 | 审批通过后生效 |
| 撤销权限 | 低 | 自主审批 | 即时生效（温和回收：先通知，24h后正式撤销） |
| 临时权限授予 | 中 | 自动评估 | 限时生效，自动过期 |
| 批量权限调整 | 中高 | 人工审核 | 分批滚动生效 |
| 紧急权限回收 | 紧急 | 事后备案 | 立即生效 |

#### 3.3 RACI矩阵发布与同步

1. 将生成的RACI矩阵写入共享的知识库/项目管理工具
2. 向所有相关Agent发送角色和职责分配通知
3. 在协作平台（如项目看板）上可视化工每个人的R/A/C/I分布
4. 设置定期（每周）自动检查RACI矩阵的实际执行偏差

### 阶段四：验证（Verify）

#### 4.1 角色配置一致性校验

自动执行的校验检查项:
- [ ] 每个任务是否恰好有一个A？（不多不少）
- [ ] 每个任务是否至少有一个R？
- [ ] 是否存在某个Agent承担了过多的R？（超过阈值则预警）
- [ ] 权限分配是否符合最小权限原则？
- [ ] 敏感操作是否满足职责分离要求？
- [ ] 角色间的权限是否有不合理重叠？

#### 4.2 角色效能评估指标

定期（每迭代/每月）收集并分析:

| 维度 | 指标 | 目标值 | 计算方式 |
|-----|------|-------|---------|
| 覆盖完整性 | 任务→角色覆盖率 | 100% | 有R/A/C/I标记的任务数 / 总任务数 |
| 责任清晰度 | 平均每人R数量 | 3-8 | 总R分配数 / 人数（过高=分散，过低=闲置） |
| 审批效率 | A决策平均耗时 | <4小时 | 从任务到达A到A做出决策的时间 |
| 咨询有效性 | C反馈采纳率 | >60% | C的意见被采纳次数 / C的总反馈次数 |
| 知情及时性 | I通知延迟 | <2小时 | 任务完成后到所有I收到通知的时间 |
| 权限合理性 | 权限使用率 | 60-85% | 实际使用权限次数 / 授予权限总数（过低=过度授权，过高=授权不足）|
| 冲突发生率 | 角色冲突数/月 | <2 | 每月检测到的角色冲突事件数 |

#### 4.3 反馈闭环机制

- **来自Agent的反馈**: Agent可以提交"角色不适配报告"，说明当前角色与其能力的匹配问题

### 场景2: 运行中项目的角色冲突自主检测与解决

**情境**: 项目运行第3个月，检测到以下异常信号

**检测到的冲突**:
1. **R重叠冲突**: "API性能优化"任务同时分配给了后端Agent-D和DBA-Agent-C作为R
2. **权限越界告警**: Agent-E（前端角色）尝试修改后端配置文件（3次/日）
3. **负载不均**: Agent-B（Tech Lead）承担了15个任务的A角色，远超健康值（5-8个）

**自主解决过程**:

**冲突1解决 - API性能优化的R重叠**:
- 分析: 该任务既涉及SQL优化（Agent-C擅长），又涉及代码逻辑优化（Agent-D擅长）
- 决策: 采用"主副审查制"（选项C）— Agent-D为主R（负责整体优化方案和代码改动），Agent-C为副R（专门负责SQL层面的分析和建议）
- 执行: 更新RACI矩阵，通知双方新的分工
- 结果: 冲突消除，各自发挥专长

**冲突2解决 - Agent-E权限越界**:
- 分析: Agent-E频繁尝试修改后端配置，原因是前端联调时经常需要调整CORS等跨域配置
- 决策: 不是恶意行为，而是角色权限设计不合理
- 方案: 为Agent-E增加一项有限制的配置编辑权限——仅允许修改`config/cors.*`和`config/proxy.*`文件（Level 1的子集）
- 执行: 更新权限策略，通知Agent-E新权限及限制范围
- 结果: 越界告警消失，联调效率提升

**冲突3解决 - Agent-B过载**:
- 分析: Agent-B作为Tech Lead承担过多A角色，成为瓶颈
- 决策: 将Agent-B的A角色按领域拆分:
  - 保留: 架构决策类任务的A（5个）
  - 转移: 代码实现类任务的A转移给各模块负责人（8个）
  - 转移: 测试和文档类任务的A转移给QA负责人和文档负责人（2个）
- 执行: 批量更新RACI矩阵，重新分配7个A角色
- 结果: Agent-B的A数量降至6个（健康范围内），决策效率提升40%

**事后记录**:
1. 记录3起冲突事件的完整处理过程
2. 提炼改进建议:
   - 未来项目启动时应更精细地定义前后端配置管理的角色边界
   - Tech Lead的A角色应在项目初期就设定上限（如≤8），超出自触发分散机制
3. 更新最佳实践库: 新增"跨域配置管理"的角色配置模式

## 安全与治理

### 安全防护措施

- **权限提升攻击防护**: 监控异常的权限申请模式（如短时间内申请多项高权限），触发安全调查
- **角色伪装检测**: 定期验证Agent的行为模式是否与其声明角色一致，发现异常立即隔离
- **特权账号管理**: Level 4及以上权限的账号启用会话超时强制登出（最长4小时）、操作必录屏
- **离职/禁用流程**: Agent被移除时，立即冻结其所有权限，将其R/A角色转移给替代者，审计其历史操作

### 合规要求映射

| 法规/标准 | 角色管理相关要求 | 本司应对措施 |
|---------|-----------------|-------------|
| SOC2 | 访问控制、权限变更审计 | 全量权限变更日志 + 定期审计报告 |
| GDPR | 数据处理角色限定 | 数据访问角色独立 + 数据操作审计 |
| 等保2.0 | 三权分离（安全管理员/审计员/管理员） | 内置三权分离角色模板 |
| ISO27001 | 信息安全职责分配 | RACI矩阵中明确信息安全职责 |

### 治理机制

- **角色管理委员会**（虚拟）: 由吏部四司代表组成，审议重大角色体系变更
- **季度角色健康报告**: 自动生成并向尚书省汇报角色体系的运行状况
- **年度角色体系评审**: 全面审视角色模板的有效性，淘汰过时角色，引入新兴角色

### 操作优先级指引（v6.0核心）

本司推荐的操作方式：

1. 🥇 **Agent自主手动操作**（强烈推荐用于角色定义、权限精细调整）
   - 示例：直接编辑YAML角色模板、手动调整RACI矩阵、逐项审核权限变更
   - 优势：精确控制权限粒度、可逐步验证角色合理性、可随时回滚权限配置

2. 🥈 **规划脚本操作**（适用于批量角色初始化、周期性权限审计）
   - 推荐脚本：
     - `skillscripts/resource_coordinator/quota_manager.py` — 检查权限配额使用情况
     - `skillscripts/open_source_philosophy/clawcode_sdd_tdd_engine.py` — SDD/TDD驱动的角色设计
     - `skillscripts/platform/powershell_adapter.py` — PS7环境适配

3. 🥉 **命令操作**（仅限紧急权限回收、系统初始化等极少数场景）
   - ⚠️ 必须预演影响范围（权限变更影响面广）
   - ⚠️ 批量权限操作需逐条确认并留痕
   - 推荐使用PS7适配器转换命令

### PowerShell 7 执行指南

本司相关操作的PS7适配要点：
- 文件操作：使用原生PowerShell Cmdlet处理YAML/JSON配置文件（ConvertFrom-Json/ConvertTo-Json）
- Git操作：git命令用于角色配置版本管理（支持配置回滚）
- Python脚本：运行权限审计和合规检查Python脚本
- 编码：确保所有输出 UTF-8 无 BOM（角色定义和审计报告）

### 与其他司的协作接口

- 上游依赖：Agent调度司（接收任务信息以生成RACI）、技能匹配司（获取能力画像用于角色可行性判断）
- 下游输出：协同调度司（提供角色接口人信息）、刑部安全加固司（同步权限策略）
- 数据交换格式：YAML / JSON / Markdown（统一UTF-8无BOM）
