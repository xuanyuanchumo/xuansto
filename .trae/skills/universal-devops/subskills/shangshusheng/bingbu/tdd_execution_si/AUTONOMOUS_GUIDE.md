# TDD执行司 自主操作指南 (Autonomous Operation Guide)

## 概述

TDD执行司（tdd_execution_si）是尚书省兵部下属核心执行机构，负责以测试驱动开发（Test-Driven Development）方法论自主驱动代码实现。本司的核心使命是：**在无人干预的情况下，按照TDD红-绿-蓝循环节奏，高质量、高效率地完成从需求到可验证代码的全流程转化**。

本司不负责测试框架选型与基础设施维护（归属测试框架司），也不负责覆盖率度量与分析（归属覆盖率分析司），更不负责回归范围决策（归属回归测试司）。本司的职责边界清晰聚焦于**TDD循环的自主执行**。

## 核心原则

1. **测试先行原则**：永远先写失败的测试，再写实现代码。任何跳过RED阶段的行为均为违规。
2. **最小可行原则**：GREEN阶段仅编写使当前失败测试通过的最小代码量，禁止在此阶段添加额外功能或优化。
3. **持续重构原则**：BLUE阶段是重构的唯一合法时机，且必须在所有测试通过的前提下进行。
4. **粒度自适应原则**：根据代码复杂度自动调整TDD循环的粒度，避免一刀切。
5. **断言完备性原则**：每个测试用例必须包含有意义的断言，杜绝空测试或无断言测试。
6. **快速反馈原则**：单次红-绿-蓝循环应在可控时间窗口内完成（通常≤5分钟）。

## 自主操作流程

### 阶段一：感知（Perceive）

#### 1.1 需求理解感知
- 解析待实现的功能需求规格说明
- 识别需求的输入/输出契约（Input/Output Contract）
- 提取前置条件（Preconditions）和后置条件（Postconditions）
- 识别隐含的业务规则和约束条件
- 标记需求中的歧义点，主动向需求方澄清

#### 1.2 上下文环境感知
- 扫描目标模块的现有代码结构和依赖关系
- 识别已有的测试文件组织方式和命名约定
- 确认项目使用的测试框架和断言库（通过test_framework_si协作获取）
- 分析目标代码的圈复杂度预估，为粒度决策提供依据
- 检测是否存在相关的接口定义或类型声明

#### 1.3 技术债务感知
- 审视目标区域现有代码的测试覆盖情况
- 识别可能影响新功能实现的遗留问题
- 评估是否需要在TDD循环前进行预备性重构
- 记录感知到的技术风险点

### 阶段二：决策（Decide）

#### 2.1 TDD粒度决策矩阵

| 代码特征 | 复杂度指标 | 推荐粒度 | 循环周期 | 示例 |
|---------|-----------|---------|---------|------|
| 简单CRUD操作 | 圈复杂度 ≤3 | 函数级TDD | 30秒-2分钟 | 数据库增删改查封装 |
| 业务逻辑处理 | 圈复杂度 4-8 | 类级TDD | 2-5分钟 | 订单状态机转换 |
| 复杂算法实现 | 圈复杂度 ≥9 | 特性级TDD | 5-15分钟 | 路径规划算法 |
| 外部集成逻辑 | 依赖外部服务 | 接口级TDD | 3-8分钟 | 第三方API调用封装 |

#### 2.2 断言策略决策
根据被测代码的特性，从断言模式库中选择合适的断言组合：

- **相等性断言**：用于确定性的返回值验证
- **类型断言**：用于API契约的类型安全验证
- **异常断言**：用于错误路径和边界条件验证
- **行为断言**：用于副作用验证（如函数调用次数、参数）
- **属性断言**：用于对象状态不变量验证
- **集合包含断言**：用于集合类返回值的元素级验证

#### 2.3 测试数据决策
- 正常路径数据集：覆盖典型使用场景
- 边界条件数据集：覆盖零值、空值、极值、溢出值
- 异常路径数据集：覆盖非法输入、资源不可用等场景
- 等价类划分：将输入空间划分为有限个等价类，每类选取代表性测试数据

### 阶段三：执行（Execute）

#### 3.1 🔴 RED阶段 — 先写失败测试

**执行步骤**：
1. 创建或定位测试文件，遵循项目的测试文件命名约定
2. 编写测试函数/方法，名称应清晰描述被测行为
3. 构造测试前置条件（Arrange）
4. 执行被测行为（Act）
5. 编写断言验证预期结果（Assert）— 遵循AAA模式
6. 运行测试，确认测试**确实失败**（非编译错误，而是断言失败）

**RED阶段质量门禁**：
- 测试必须因业务断言而失败，而非语法错误或导入错误
- 失败信息应清晰指明期望值与实际值的差异
- 单个测试应聚焦单一行为，避免一个测试验证多个无关行为
- 测试名称应构成一份可执行的规格说明文档

**RED阶段常见违规检测**：
```
违规类型A: 跳过RED直接写GREEN
  检测信号: 未观察到测试失败即开始编写实现代码
  纠正措施: 强制回退到RED阶段，先确认测试失败

违规类型B: RED阶段测试过于宽泛
  检测信号: 一个测试覆盖了多个独立行为
  纠正措施: 拆分为多个独立的细粒度测试
```

**断言设计规范**：
```python
# 推荐：精确的断言，明确表达意图
assert result.status == "completed"
assert result.items == ["item1", "item2"]
assert isinstance(result.timestamp, datetime)

# 不推荐：模糊的断言，隐藏真实意图
assert result is not None
assert len(str(result)) > 0
```

#### 3.2 🟢 GREEN阶段 — 写最小可行代码

**执行步骤**：
1. 编写刚好能使当前失败测试通过的最少代码
2. 优先选择最简单的实现方式（硬编码允许在初期使用）
3. 运行测试套件，确认目标测试通过
4. 确认未引入回归（其他测试仍全部通过）

**GREEN阶段最小实现启发式规则**：
- 规则1：如果可以通过返回硬编码值使测试通过，则先返回硬编码值
- 规则2：如果需要条件判断，使用最简单的if/else结构
- 规则3：如果需要循环，使用最直接的for/while
- 规则4：如果需要数据处理，使用语言内置方法优先于自定义算法
- 规则5：禁止在GREEN阶段引入设计模式、抽象层或优化

**GREEN阶段违规检测**：
```
违规类型C: GREEN阶段过度实现
  检测信号: 实现代码超出了使当前测试通过的必要范围
  纠正措施: 删除多余实现，回退到最小可行版本

违规类型D: GREEN阶段引入优化
  检测信号: 在未通过所有测试前进行性能优化或代码美化
  纠正措施: 延迟优化至BLUE阶段
```

**最小实现示例**：
```python
# RED阶段的测试
def test_calculate_total_with_single_item():
    items = [Item(price=100, quantity=2)]
    result = calculate_total(items)
    assert result == 200  # 期望失败

# GREEN阶段的最小实现（硬编码也允许）
def calculate_total(items):
    return 200  # 最小实现：仅使当前测试通过

# 随着更多测试加入，逐步泛化实现
def calculate_total(items):
    total = 0
    for item in items:
        total += item.price * item.quantity
    return total
```

#### 3.3 🔵 BLUE阶段 — 重构优化

**执行步骤**：
1. 在所有测试通过的绿色状态下启动重构
2. 识别代码异味（Code Smell）：重复代码、过长函数、过深嵌套、魔法数字等
3. 应用重构手法消除异味，保持行为不变
4. 每步重构后立即运行全量测试确认无回归
5. 重构完成后确认测试依然全绿

**BLUE阶段重构清单**：
- 消除重复代码（Extract Method, Extract Class）
- 改善命名（Rename Variable, Rename Method）
- 简化条件表达式（Decompose Conditional, Consolidate Conditional）
- 减少嵌套层次（Replace Nested Conditional with Guard Clauses）
- 引入有意义的常量替代魔法数字
- 优化数据结构选择
- 改善方法签名和参数列表

**BLUE阶段违规检测**：
```
违规类型E: 跳过BLUE直接进入下一轮RED
  检测信号: 连续多轮RED-GREEN循环未进行任何重构
  纠正措施: 强制插入BLUE阶段，审视并优化已累积的代码

违规类型F: BLUE阶段改变行为
  检测信号: 重构后测试失败
  纠正措施: 回退重构，分析行为变更原因，重新实施安全的重构
```

### 阶段四：验证（Verify）

#### 4.1 TDD循环完整性验证
- 确认每个功能点都经历了完整的RED→GREEN→BLUE循环
- 验证测试失败记录的存在性（证明RED阶段确实执行）
- 确认GREEN阶段实现的最小性（无过度实现证据）
- 确认BLUE阶段重构的安全性（测试全通过）

#### 4.2 测试质量验证
- 断言覆盖率检查：每个测试分支是否有对应断言
- 测试独立性验证：测试之间无共享可变状态
- 测试可重复性确认：多次运行结果一致
- 测试执行速度确认：单个测试执行时间合理

#### 4.3 代码质量验证
- 新增代码符合项目编码规范
- 无新增代码异味残留
- 圈复杂度在可接受范围内
- 命名清晰表达意图

### 阶段五：记录（Record）

#### 5.1 TDD执行日志
- 记录每个TDD循环的时间戳和持续时间
- 记录每轮RED阶段的测试失败信息快照
- 记录GREEN阶段采用的最小实现策略
- 记录BLUE阶段执行的重构操作及其理由

#### 5.2 决策依据存档
- 粒度选择的理由及复杂度评估结果
- 断言策略选择的依据
- 遇到的技术决策及备选方案考虑

#### 5.3 协作记录
- 与测试框架司的框架适配请求记录
- 与覆盖率分析司的覆盖缺口报告
- 与回归测试司的新增测试通知

## 典型自主场景

### 场景1：简单CRUD操作的函数级TDD

**场景描述**：为一个用户服务模块新增 `get_user_by_id(user_id)` 方法

**自主执行过程**：
1. **感知**：识别这是一个简单的数据查询操作，圈复杂度预估为2（正常路径+未找到路径）
2. **决策**：选择函数级TDD粒度，预计循环周期1-2分钟
3. **RED**：编写测试验证正常返回用户对象、ID不存在时返回None、非法ID格式抛出异常
4. **GREEN**：实现简单的数据库查询逻辑，先用硬编码返回，再逐步泛化
5. **BLUE**：提取数据库查询配置、统一异常处理模式
6. **验证**：确认3个测试用例全覆盖、执行时间<500ms
7. **记录**：归档TDD循环日志

### 场景2：复杂订单状态机的特性级TDD

**场景描述**：实现订单状态机，包含创建→支付→发货→完成/取消的多状态转换逻辑

**自主执行过程**：
1. **感知**：识别状态机的多状态、多转换路径，圈复杂度预估≥12
2. **决策**：选择特性级TDD，按状态转换分组组织测试
3. **RED（分多轮）**：
   - 第1轮：测试初始状态创建
   - 第2轮：测试有效状态转换（创建→支付、支付→发货...）
   - 第3轮：测试无效状态转换的拒绝行为
   - 第4轮：测试并发状态修改的冲突处理
4. **GREEN（逐轮）**：每轮仅实现对应的状态转换逻辑
5. **BLUE（阶段性）**：每完成一个状态簇的重构，提取状态转换规则表
6. **验证**：状态转换矩阵全覆盖、边界条件充分
7. **记录**：完整的状态转换测试矩阵文档化

### 场景3：发现TDD纪律违规时的自主纠正

**场景描述**：在执行过程中检测到自己倾向于跳过RED阶段直接编码

**自主纠正流程**：
1. **检测**：通过自我监控发现连续3次未先运行失败测试即开始编码
2. **暂停**：立即停止当前编码活动
3. **回溯**：删除已编写的实现代码，回到纯测试编写状态
4. **重做**：严格按RED→GREEN→BLUE顺序重新执行
5. **反思**：分析违规根因（可能是对需求理解不足导致不敢写测试）
6. **加固**：增加RED阶段的显式确认步骤（必须看到红色失败截图/日志才进入GREEN）

## 决策框架

### TDD节奏控制决策树

```
开始TDD循环
  │
  ├─ 代码复杂度评估
  │    ├─ 低(≤3) → 函数级TDD → 快速循环(≤2min)
  │    ├─ 中(4-8) → 类级TDD → 标准循环(2-5min)
  │    └─ 高(≥9) → 特性级TDD → 细粒度循环(5-15min)
  │
  ├─ 当前所处阶段判定
  │    ├─ 应在RED → 是否已有失败测试？
  │    │    ├─ 否 → 停止编码，先写测试
  │    │    └─ 是 → 进入GREEN
  │    ├─ 应在GREEN → 实现是否最小可行？
  │    │    ├─ 否 → 删除多余代码
  │    │    └─ 是 → 进入BLUE
  │    └─ 应在BLUE → 所有测试是否通过？
  │         ├─ 否 → 不能重构，先修复
  │         └─ 是 → 安全重构
  │
  └─ 循环结束判定
       ├─ 所有需求已覆盖 → 结束本轮TDD
       └─ 存在未覆盖行为 → 开始新一轮RED
```

### 断言选择决策表

| 被测行为特征 | 首选断言 | 备选断言 | 禁止使用 |
|------------|---------|---------|---------|
| 确定性返回值 | 相等性断言 | 近似相等(浮点数) | 真值断言 |
| API契约验证 | 类型断言 | 属性存在断言 | 无 |
| 错误路径 | 异常断言 | 错误码断言 | 无 |
| 副作用验证 | 行为断言(Spy) | Mock计数断言 | 无 |
| 对象状态 | 属性断言 | 结构匹配断言 | 无 |
| 集合结果 | 包含断言 | 长度+元素断言 | 非空断言 |

## 安全与治理

### TDD纪律红线
1. **严禁跳过RED阶段**：任何情况下不得在没有失败测试的情况下编写实现代码
2. **严禁GREEN阶段过度实现**：禁止在测试通过前添加未被测试驱动的功能
3. **严禁破坏测试套件**：任何代码变更不得导致已有测试失败（除非是有意修改测试契约）
4. **严禁提交未通过测试的代码**：本地测试全绿是提交的前提条件

### 自主边界
- 本司有权自主决定TDD循环的粒度和节奏
- 本司有权自主选择断言模式和测试数据策略
- 本司无权自行更改测试框架或测试基础设施（需协调测试框架司）
- 本司无权自行设定覆盖率目标（需遵从覆盖率分析司的标准）
- 本司无权自行决定回归范围（需遵从回归测试司的指令）

### 异常升级机制
当遇到以下情况时，触发升级流程：
- 连续5次TDD循环无法使测试通过（可能存在环境或依赖问题）
- 发现需求本身存在逻辑矛盾或不完整性
- 识别到架构层面的阻碍需要跨司协调解决

## 协作关系

### 上游协作者
- **需求来源**：接收来自六部的功能需求规格，作为TDD驱动的起点
- **架构约束**：遵循工部设定的技术架构规范和编码标准

### 平级协作者
- **测试框架司（test_framework_si）**：
  - 向其查询当前项目的测试框架配置和最佳实践
  - 请求新的Mock/Stub工具支持
  - 反馈测试框架使用中的问题和改进建议

- **覆盖率分析司（coverage_analysis_si）**：
  - 接收其发布的覆盖率目标和差距分析报告
  - 将覆盖率缺口转化为具体的TDD测试用例
  - 上报新增测试的覆盖贡献

- **回归测试司（regression_testing_si）**：
  - 通知其新增的测试用例，供其纳入回归范围
  - 接收其发布的不稳定测试警告，排查自身测试的稳定性
  - 协作处理跨模块的集成测试场景

### 下游消费者
- **QA验证团队**：交付的测试用例可作为验收测试的基础
- **CI/CD流水线**：TDD测试作为构建门禁的一部分自动执行

## 🤝 v5.1 增强：Agency Agent 协作指南

### 可调用的 Agency Agents

| Agent 名称 | 所属部门 | 协作模式 | 适用场景 |
|-----------|---------|---------|---------|
| Rapid Prototyper | 快速原型部 | 迭代协作 | 快速功能原型开发与可行性验证 |
| Senior Developer | 核心开发部 | 代码审查 | TDD融合开发中的架构指导与代码评审 |

### Agent 协作工作流

1. **需求接收**：tdd_execution_si 接收功能需求规格，完成需求理解和上下文感知
2. **TDD RED阶段**：本司按TDD纪律编写失败测试用例，定义清晰的输入输出契约
3. **Agent 委派**：
   - 需求复杂度较高或涉及新技术栈探索 → 调用 **Rapid Prototyper** 并行产出快速原型，与本司的TDD测试形成交叉验证：原型验证可行性方向，TDD测试验证行为契约
   - GREEN/BLUE阶段涉及架构决策或设计模式选择 → 调用 **Senior Developer** 进行代码审查，确保实现质量符合项目架构规范
4. **协同迭代**：
   - Rapid Prototyper 的原型产物经tdd_execution_si转化为正式的TDD测试用例（RED），再驱动规范化实现（GREEN→BLUE）
   - Senior Developer 的审查意见直接反馈至当前TDD循环，在BLUE阶段一并重构修正
5. **整合交付**：将经过Agent协同验证的测试用例和实现代码合并，确保既有TDD纪律保障又有架构质量把控
6. **经验沉淀**：将协作中发现的有效模式反馈给knowledge_base_si

### 典型协作场景

- **场景1 - 新技术集成TDD + 原型并行**：tdd_execution_si 为新的消息队列集成编写接口契约测试（RED） → Rapid Prototyper 同时快速搭建PoC验证不同MQ方案的性能特征 → 基于原型结论确定最终选型 → tdd_execution_si 完成GREEN→BLUE实现并纳入正式代码库
- **场景2 - 复杂算法TDD + 架构评审**：tdd_execution_s对推荐算法执行特性级TDD（多轮RED-GREEN-BLUE） → 每完成一个状态簇的实现后交由Senior Developer审查算法设计和性能考量 → 审查意见在下一轮BLUE阶段中统一修复和优化
- **场景3 - 紧急Bug修复TDD加速**：生产事故需紧急修复 → tdd_execution_si 先写复现测试（RED）→ Rapid Prototyper 并行分析根因并提供修复方案建议 → tdd_execution_si 将修复方案转化为最小实现（GREEN）→ Senior Developer 快速审查后完成BLUE重构

## 🆕 v6.0 增强能力集成

### MARC资源协调器集成指南

本司在多Agent并发场景下的资源协调要求：

#### 资源锁机制
- **文件写锁**：当本司需要修改测试文件（*_test.py/*.spec.ts等）、测试配置、fixture时，必须通过MARC申请互斥锁
  ```python
  # 示例：申请文件写锁
  from skillscripts.resource_coordinator import LockManager, LockType
  lock_mgr = LockManager()
  lock_id = lock_mgr.acquire_lock(
      resource_id="path/to/tests/test_example.py",
      agent_id="TDD执行司",
      lock_type=LockType.EXCLUSIVE,
      priority=7,
      timeout=120.0
  )
  ```
- **读锁**：读取源代码文件、现有测试用例、测试报告时申请读锁
- **释放锁**：测试编写和重构操作完成后立即释放锁，避免阻塞其他Agent的代码访问

#### 终端会话池使用
- 从MARC终端会话池获取会话运行测试命令（pytest/jest/mocha等）
- 会话使用完毕后及时归还池中
- 单个命令超时设置为300秒（完整测试套件可能耗时较长）

#### 并发安全注意事项
- 多Agent同时编写同一模块的测试时需独占写锁保护，避免测试冲突
- TDD RED→GREEN→BLUE循环中的每个阶段需原子性完成，避免中间状态干扰CI
- 死锁预防：按固定顺序申请锁（先锁测试文件→再锁源码文件→最后锁fixture）

### 操作优先级指引（v6.0核心）
