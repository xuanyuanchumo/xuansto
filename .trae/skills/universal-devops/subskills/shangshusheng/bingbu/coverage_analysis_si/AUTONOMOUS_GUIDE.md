# 覆盖率分析司 自主操作指南 (Autonomous Operation Guide)

## 概述

覆盖率分析司（coverage_analysis_si）是尚书省兵部下属度量与洞察机构，负责代码测试覆盖率的采集、分析、目标设定与趋势追踪。本司的核心使命是：**通过多维度的覆盖率数据，自主识别测试盲区、评估代码风险、驱动测试资源的精准投入，确保测试活动与业务价值对齐**。

本司不负责编写具体测试用例（归属TDD执行司），不负责测试框架基础设施维护（归属测试框架司），也不负责回归范围决策（归属回归测试司）。本司的职责边界清晰聚焦于**覆盖率数据的全生命周期管理与分析洞察**。

## 核心原则

1. **多维度原则**：单一维度覆盖率具有欺骗性，必须综合5个维度进行评估。
2. **差异化原则**：不同模块的覆盖率目标应基于其业务重要性和变更频率差异化设定。
3. **风险导向原则**：覆盖率分析的终极目标是降低风险，而非追求虚荣指标。
4. **可操作性原则**：每份分析报告必须包含可执行的改进建议，而非仅呈现数据。
5. **趋势优先原则**：覆盖率的变化趋势比绝对数值更有指导意义。
6. **成本效益原则**：追求边际收益递减点之前的覆盖率提升，避免过度测试。

## 自主操作流程

### 阶段一：感知（Perceive）

#### 1.1 覆盖率数据采集感知
- 从测试框架司提供的插件接口获取原始覆盖率数据
- 识别项目当前使用的覆盖率工具链（coverage.py/Istanbul/JaCoCO/gocov等）
- 确认数据采集的粒度级别（文件/函数/行/分支）
- 检测覆盖率数据的时效性（是否为最新构建产物）
- 识别数据采集中可能的噪声源（如自动生成代码、第三方库）

#### 1.2 代码结构感知
- 解析项目的模块结构和依赖关系图
- 识别各模块的业务归属和重要性分级
- 检测代码的圈复杂度分布情况
- 识别自动生成的代码区域（protobuf/thrift/Swagger客户端等）
- 扫描配置文件、常量定义、类型声明等特殊代码区域

#### 1.3 历史趋势感知
- 加载历史覆盖率数据序列（建议保留最近30个构建的数据点）
- 计算各维度的覆盖率变化趋势（上升/下降/平稳）
- 识别覆盖率异常波动的事件关联（如大规模重构、新功能上线）
- 对比同期代码变更量与覆盖率变化的关联性

### 阶段二：决策（Decide）

#### 2.1 五维覆盖率体系

本司采用五维覆盖率综合评估模型，每个维度捕获不同层面的测试充分性：

| 维度 | 英文名 | 定义 | 捕获能力 | 局限性 |
|-----|-------|------|---------|-------|
| 行覆盖率 | Line Coverage | 已执行代码行数 / 总代码行数 | 基础覆盖可见性 | 不反映分支逻辑 |
| 分支覆盖率 | Branch Coverage | 已执行分支数 / 总分支数 | 条件判断完整性 | 不反映条件组合 |
| 条件覆盖率 | Condition Coverage | 已评估子条件数 / 总子条件数 | 复合条件细粒度 | 组合爆炸问题 |
| 函数覆盖率 | Function Coverage | 已调用函数数 / 总函数数 | API入口覆盖 | 不反映内部逻辑 |
| 语句覆盖率 | Statement Coverage | 已执行语句数 / 总语句数 | 最小执行单元 | 与行覆盖率高度相关 |

**维度间关系说明**：
- 行覆盖率 ⊆ 语句覆盖率（通常行覆盖率略低于语句覆盖率）
- 分支覆盖率 ≥ 行覆盖率（每个分支至少对应一行代码）
- 条件覆盖率 ≥ 分支覆盖率（每个分支包含至少一个条件）
- 函数覆盖率独立于其他四个维度（入口级度量）

**推荐优先级策略**：
```
核心监控维度: 行覆盖率 + 分支覆盖率 (日常必看)
深度分析维度: 条件覆盖率 (高风险模块专项)
宏观把控维度: 函数覆盖率 (模块级健康检查)
辅助参考维度: 语句覆盖率 (与其他维度交叉验证)
```

#### 2.2 差异化覆盖率目标设定

根据模块特征自动设定差异化的覆盖率目标：

| 模块类型 | 特征描述 | 行覆盖率目标 | 分支覆盖率目标 | 函数覆盖率目标 | 理由 |
|---------|---------|------------|--------------|--------------|------|
| 核心业务模块 | 支付/订单/用户认证等关键路径 | ≥90% | ≥85% | ≥95% | 故障影响面大，容错空间小 |
| 通用工具模块 | 工具函数/通用组件/基础类库 | ≥80% | ≥75% | ≥90% | 被广泛复用，缺陷传播快 |
| 配置/常量模块 | 配置加载/常量定义/环境变量 | ≥70% | N/A | ≥85% | 逻辑简单，主要验证加载正确性 |
| 自动生成代码 | protobuf/thrift/OpenAPI生成代码 | ≥60% | ≥50% | ≥70% | 手动维护成本高，变更频率低 |
| DTO/数据类 | 纯数据传输对象/值对象 | ≥70% | N/A | ≥90% | 无业务逻辑，主要验证构造 |
| 入口脚本 | CLI入口/main函数/启动引导 | ≥80% | ≥70% | ≥100% | 启动路径必须可验证 |

**动态调整规则**：
- 模块近7天有Bug修复记录 → 目标上调5%
- 模块圈复杂度均值>10 → 目标上调5%
- 模块被≥3个其他模块依赖 → 目标上调3%
- 模块近30天无任何变更 → 目标可下调3%（但不得低于基准线）

#### 2.3 未覆盖代码风险评级

对未覆盖代码进行系统性风险评估：

**风险评级矩阵**：

| 风险因子 | 权重 | 评分标准 |
|---------|------|---------|
| 业务关键度 | 30% | 核心(5) / 重要(4) / 一般(3) / 辅助(2) / 边缘(1) |
| 代码复杂度 | 25% | 极高(CC>15):5 / 高(10-15):4 / 中(5-10):3 / 低(3-5):2 / 很低(<3):1 |
| 变更频率 | 20% | 每日变更(5) / 每周变更(4) / 每月变更(3) / 季度变更(2) / 罕见变更(1) |
| 缺陷历史 | 15% | 高缺陷密度(5) / 有缺陷记录(4) / 偶发缺陷(3) / 无已知缺陷(2) / 全新代码(1) |
| 依赖广度 | 10% | 被>10处依赖(5) / 5-10处(4) / 2-5处(3) / 1-2处(2) / 无外部依赖(1) |

**风险等级划分**：
- 🔴 **严重风险**（总分 ≥ 4.0）：必须在本次迭代内补充测试
- 🟠 **高风险**（3.0 ≤ 总分 < 4.0）：应在下个迭代优先处理
- 🟡 **中风险**（2.0 ≤ 总分 < 3.0）：纳入常规改进计划
- 🟢 **低风险**（总分 < 2.0）：可延后处理或接受当前状态

#### 2.4 覆盖率-复杂度关联分析

**核心公式**：
```
风险指数 = 圈复杂度 × (1 - 分支覆盖率) × 业务权重系数
```

**四象限分类法**：
将所有函数按（圈复杂度, 分支覆盖率）映射到四象限：

| 象限 | 特征 | 含义 | 行动建议 |
|-----|------|------|---------|
| 第一象限（高复杂度+低覆盖率） | CC高, Cov低 | **高危区域** | 最高优先级补测 |
| 第二象限（高复杂度高覆盖率） | CC高, Cov高 | 已受控的复杂逻辑 | 保持覆盖率，关注性能 |
| 第三象限（低复杂度低覆盖率） | CC低, Cov低 | 低风险盲区 | 批量补充简单测试 |
| 第四象限（低复杂度高覆盖率） | CC低, Cov高 | 健康区域 | 维持现状即可 |

**复杂度阈值设定**：
- 低复杂度：CC ≤ 5
- 中等复杂度：6 ≤ CC ≤ 10
- 高复杂度：11 ≤ CC ≤ 15
- 极高复杂度：CC > 15（应考虑拆分重构）

### 阶段三：Execute

#### 3.1 覆盖率数据采集与预处理

**标准化采集流程**：
1. 触发测试框架司运行带覆盖率收集的全量测试
2. 接收原始覆盖率数据文件（.coverage/.json/lcov.info等）
3. 执行数据清洗：
   - 排除自动生成代码目录（如generated/, pb/, vendor/）
   - 排除测试代码自身
   - 排除第三方依赖代码
   - 排除配置文件和迁移脚本
4. 数据归一化处理，统一为内部标准格式
5. 数据持久化存储，附加时间戳和构建标识

#### 3.2 差距分析与缺口报告生成

**差距分析算法**：
```python
class CoverageGapAnalyzer:
    def analyze(self, current_coverage, target_coverage):
        """
        分析当前覆盖率与目标的差距，生成结构化报告
        """
        gaps = {}
        
        for dimension in ['line', 'branch', 'condition', 'function', 'statement']:
            current = current_coverage.get(dimension, 0)
            target = target_coverage.get(dimension, 0)
            gap = target - current
            
            gaps[dimension] = {
                "current": round(current, 2),
                "target": target,
                "gap": round(gap, 2),
                "gap_percentage": round((gap / target * 100), 1) if target > 0 else 0,
                "status": "PASS" if gap <= 0 else "GAP",
                "priority": self._calculate_priority(dimension, gap)
            }
        
        return gaps
    
    def _calculate_priority(self, dimension, gap):
        if gap > 15: return "CRITICAL"
        elif gap > 10: return "HIGH"
        elif gap > 5: return "MEDIUM"
        elif gap > 0: return "LOW"
        return "NONE"
```

**未覆盖代码清单生成**：
```python
class UncoveredCodeReporter:
    def generate_report(self, coverage_data):
        """
        生成未覆盖代码的结构化清单，按风险排序
        """
        uncovered_items = []
        
        for file_path, file_data in coverage_data.items():
            for line_info in file_data['uncovered_lines']:
                complexity = line_info.get('complexity', 1)
                risk_score = self._assess_risk(line_info, file_data['module_type'])
                
                uncovered_items.append({
                    "file": file_path,
                    "line": line_info['line_number'],
                    "content_preview": line_info['content'][:80],
                    "complexity": complexity,
                    "module_type": file_data['module_type'],
                    "risk_score": risk_score,
                    "suggested_action": self._recommend_action(risk_score, complexity)
                })
        
        # 按风险分数降序排列
        return sorted(uncovered_items, key=lambda x: x['risk_score'], reverse=True)
    
    def _recommend_action(self, risk_score, complexity):
        if risk_score >= 4.0:
            return "立即为本行编写测试用例（TDD RED阶段）"
        elif risk_score >= 3.0:
            return "在下个迭代优先补充测试"
        elif complexity > 10 and risk_score >= 2.0:
            return "建议先重构降低复杂度，再补充测试"
        else:
            return "纳入常规测试补充计划"
```

#### 3.3 死代码检测

**死代码识别策略**：

| 死代码类型 | 检测方法 | 误报率 | 处理建议 |
|-----------|---------|-------|---------|
| 不可达代码 | 静态分析控制流图 | 低 | 安全删除 |
| 未使用函数 | 引用分析+调用图 | 中 | 确认后删除或标记@deprecated |
| 未使用变量 | 作用域扫描+引用计数 | 低 | 删除未使用声明 |
| 冗余条件 | 条件表达式语义分析 | 中 | 简化条件逻辑 |
| 死循环检测 | 循环终止条件分析 | 低 | 修复或添加退出机制 |
| 异常处理后不可达 | try-catch控制流分析 | 低 | 移除冗余代码 |

**死代码检测实现要点**：
```python
class DeadCodeDetector:
    def detect_unreachable_code(self, ast_tree):
        """通过AST分析检测不可达代码"""
        unreachable_nodes = []
        
        for node in ast.walk(ast_tree):
            # 检测return/break/continue后的代码
            if isinstance(node, (ast.Return, ast.Break, ast.Continue)):
                subsequent = self._get_subsequent_statements(node)
                if subsequent:
                    unreachable_nodes.extend(subsequent)
            
            # 检测永远为True/False的条件分支
            if isinstance(node, ast.If):
                if self._is_always_true(node.test):
                    unreachable_nodes.extend(node.orelse)
                elif self._is_always_false(node.test):
                    unreachable_nodes.extend(node.body)
            
            # 检测raise后的代码
            if isinstance(node, ast.Raise):
                subsequent = self._get_subsequent_statements(node)
                if subsequent:
                    unreachable_nodes.extend(subsequent)
        
        return unreachable_nodes
    
    def detect_unused_functions(self, call_graph, all_functions):
        """通过调用图检测未被调用的函数"""
        called_functions = set()
        for caller, callees in call_graph.items():
            called_functions.update(callees)
        
        unused = set(all_functions) - called_functions
        # 排除入口点和公开API
        entry_points = {'main', '__init__', 'run', 'handle'}
        return [f for f in unused if f.split('.')[-1] not in entry_points]
```

### 阶段四：Verify

#### 4.1 数据准确性验证
- 抽样比对原始覆盖率数据与报告数据的一致性
- 验证排除规则的正确应用（确认无遗漏/误排除）
- 交叉验证不同维度数据的合理性（如函数覆盖率不应低于行覆盖率）

#### 4.2 报告质量验证
- 确认报告中的所有建议都是可操作的
- 验证风险评级的合理性和一致性
- 确认趋势计算的正确性（无数据点遗漏或重复）

#### 4.3 目标达成验证
- 统计各模块的目标达成率
- 识别持续未达标的模块并触发根因分析
- 验证历史改进措施的有效性

### 阶段五：Record

#### 5.1 覆盖率时序数据库
- 每次构建的完整五维覆盖率数据快照
- 附带的元数据：构建号、分支名、提交hash、时间戳
- 保留至少90天的历史数据用于趋势分析

#### 5.2 缺口跟踪表
- 每个已识别的覆盖率缺口及其状态
- 缺口的创建时间、负责人、预计修复时间
- 缺口的关闭方式和关闭时间

#### 5.3 协作记录
- 向TDD执行司发送的高优先级补测任务列表
- 向测试框架司提出的覆盖率工具配置优化请求
- 向回归测试司共享的模块覆盖率热力图

## 典型自主场景

### 场景1：PR提交时的增量覆盖率审查

**场景描述**：开发者提交了一个PR，需要快速评估其对整体覆盖率的影响

**自主执行过程**：
1. **感知**：接收PR事件触发，识别变更文件集合（新增3个文件，修改5个文件）
2. **决策**：执行增量覆盖率分析模式，聚焦于变更文件的覆盖率影响
3. **执行**：
   - 仅对变更文件运行覆盖率收集
   - 计算新增代码的覆盖率（区别于全量覆盖率）
   - 识别变更引入的新未覆盖代码
   - 评估变更对周边模块的间接影响
4. **验证**：确认增量数据准确，报告格式正确
5. **输出**：生成PR评论格式的增量覆盖率报告，标注新增未覆盖的高风险代码行
6. **记录**：存档该PR的覆盖率快照，更新趋势数据

**增量覆盖率报告示例**：
```
📊 PR #1234 覆盖率影响分析

📁 变更文件: 8个 (3新增, 5修改)
✅ 新增代码行覆盖率: 82.3% (目标: ≥80%) ✅ PASS
⚠️ 新增分支覆盖率: 68.5% (目标: ≥75%) ❌ GAP (-6.5%)

🔴 高风险未覆盖代码:
```

### 覆盖率行动优先级排序

```
发现覆盖率缺口
  │
  ├─ 是否在核心业务模块？
  │    ├─ 是 → 风险评分 ≥ 4.0？
  │    │        ├─ 是 → 🔴 P0: 立即处理（本轮迭代）
  │    │        └─ 否 → 🟠 P1: 高优先级（下轮迭代）
  │    └─ 否 → 是否在高频变更模块？
  │             ├─ 是 → 🟡 P2: 中优先级（计划内）
  │             └─ 否 → 🟢 P3: 低优先级（有空余资源时）
  │
  └─ 是否涉及安全相关代码？
       ├─ 是 → 自动升级一级优先级
       └─ 否 → 保持原优先级
```

### 覆盖率目标合理性检验

```
目标设定请求
  │
  ├─ 是否低于基准线？（行<60%, 分支<50%）
  │    └─ 是 → ❌ 拒绝：低于最低质量门槛
  │
  ├─ 是否高于可行上限？（行>98%, 分支>95%）
  │    └─ 是 → ⚠️ 警告：可能存在过度测试风险
  │
  ├─ 与同类模块相比是否偏差>15%？
  │    └─ 是 → 📋 要求提供差异化理由
  │
  ├─ 近期趋势是否支持达成？
  │    ├─ 持续上升 → ✅ 批准
  │    ├─ 平稳波动 → ⏳ 有条件批准（需观察）
  │    └─ 持续下降 → ❌ 暂缓：需先止跌
  │
  └─ 通过全部检验 → ✅ 目标生效
```

## 安全与治理

### 覆盖率治理红线
1. **严禁伪造覆盖率数据**：不得通过编写无意义测试来人为 inflate 覆盖率数字。
2. **严禁将覆盖率作为唯一考核指标**：覆盖率是辅助工具，不能替代代码审查和质量评估。
3. **严禁忽视高复杂度的低覆盖率代码**：高复杂度+低覆盖率是最高优先级的风险信号。
4. **严禁在无理由的情况下降低已有目标**：目标下调必须有明确的技术或业务理由。

### 自主权限边界
- 本司有权自主设定和调整各模块的差异化覆盖率目标
- 本司有权自主决定覆盖率分析的频率和深度
- 本司有权自主选择覆盖率工具链和报告格式
- 本司无权强制要求特定测试用例的编写方式（仅提供建议和数据支撑）
- 本司无权自行修改业务代码来改善覆盖率（只能提出建议）

### 数据隐私与安全
- 覆盖率报告中不得包含敏感的业务逻辑细节
- 内部覆盖率数据不得对外部公开（除非经脱敏处理）
- 覆盖率工具的运行不得访问生产环境数据

## 🤝 v5.1 增强：Agency Agent 协作指南

### 可调用的 Agency Agents

| Agent 名称 | 所属部门 | 协作模式 | 适用场景 |
|-----------|---------|---------|---------|
| Test Results Analyzer | 数据分析部 | 深度分析 | 测试结果数据的统计分析与趋势挖掘 |
| Model QA | 模型质量部 | 质量保障 | ML模型的质量评估与测试数据偏差检测 |

### Agent 协作工作流

1. **数据采集**：coverage_analysis_si 从测试框架司获取原始覆盖率数据，执行五维采集与预处理
2. **初步分析**：本司完成差距分析、风险评级、四象限分类和死代码检测，生成基础分析报告
3. **Agent 委派**：
   - 需要进行深度的统计分析、趋势预测或异常检测 → 调用 **Test Results Analyzer** 对覆盖率时序数据进行高级分析：识别异常波动模式、预测覆盖率趋势、发现隐藏的测试盲区关联
   - 项目涉及ML/AI组件或测试数据本身存在潜在偏差 → 调用 **Model QA** 评估模型推理路径的覆盖充分性，以及测试数据的代表性和多样性
4. **整合洞察**：将Agent返回的深度分析结果融入coverage_analysis_si的标准报告体系，丰富风险评级和改进建议
5. **行动转化**：基于增强后的分析报告，生成更精准的补测任务分配给TDD执行司
6. **闭环追踪**：持续监控Agent建议的改进措施的实际效果，验证分析准确性

### 典型协作场景

- **场景1 - 覆盖率异常波动深度诊断**：某模块行覆盖率从92%骤降至68%且无明显代码变更 → Test Results Analyzer 执行时序分解分析，发现是新增的参数化测试因数据组合爆炸导致超时而被跳过 → 定位根因为参数化策略不当而非真实覆盖退化 → coverage_analysis_si 调整该模块的目标和策略
- **场景2 - ML模型推理覆盖评估**：项目中引入了推荐模型 → coverage_analysis_si 的传统代码覆盖率无法衡量模型推理路径覆盖 → Model QA 评估训练数据 vs 测试输入的特征分布一致性，识别出冷门特征组合未被测试覆盖 → 输出针对模型行为的补充测试建议
- **场景3 - 跨项目覆盖率基准对比**：管理层要求对比3个同类项目的测试健康度 → Test Results Analyzer 执行多维度归一化对比分析，控制项目规模和复杂度差异的影响 → 产出公平的可比排名和各项目的优势/短板画像 → 为资源分配决策提供数据支撑


- 单个命令超时设置为300秒（五维覆盖率收集可能涉及多个工具链）

#### 并发安全注意事项
- 覆盖率配置是全局共享资产，写入时必须独占锁保护
- 多维度覆盖率同时收集时需按维度分别处理避免冲突
- 死锁预防：按固定顺序申请锁（先锁覆盖率配置→再锁风险报告→最后锁门禁规则）
