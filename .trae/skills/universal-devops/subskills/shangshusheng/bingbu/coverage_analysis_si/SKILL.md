# 覆盖分析司 (Coverage Analysis Si)

> 尚书省 · 兵部 · Universal DevOps v4.0

**状态**: 占位符 - 具体内容由后续任务填充

## 🤖 自主化操作指南 (v7.0)

### 推荐操作模式
| 操作场景 | 推荐模式 | 置信度 | 说明 |
|---------|---------|--------|------|
| 覆盖率数据采集 | SCRIPTED_BATCH | 98% | Istanbul/JaCoCo/Cobertura自动采集 |
| 覆盖率报告生成 | SCRIPTED_BATCH | 96% | 模板化报告，高度标准化 |
| 未覆盖代码分析 | HYBRID_ASSISTED | 84% | 工具定位 + 人工判断是否需要测试 |
| 覆盖率目标制定 | AUTONOMOUS_MANUAL | 75% | 需要平衡质量要求和开发成本 |

### 常用工具组合
- **读操作**: Read, SearchCodebase, Grep（读取覆盖率数据、源码、历史基线）
- **写操作**: Write, SearchReplace（生成覆盖率报告、更新阈值配置）
- **批量操作**: 覆盖率采集pipeline、报告生成脚本、趋势分析ETL
- **验证操作**: 覆盖率达标检查器、增量覆盖率计算工具

### 注意事项
- ⚠️ 覆盖率不是目的而是手段：100%覆盖率不代表没有bug，不要为了数字而写无意义测试
- ⚠️ 关注"有效覆盖"：分支覆盖 > 行覆盖，条件覆盖能发现更多边界问题
- ✅ 采用增量覆盖率：PR只关注新增代码的覆盖率，避免旧代码拖累新功能
- ✅ 建立分层覆盖策略：核心业务逻辑要求高覆盖率(>90%)，工具类代码可适当放宽

## 🔗 资源协调要点 (v7.0)

### 常访问资源
| 资源类型 | 典型路径 | 锁策略建议 |
|---------|---------|-----------|
| FILE | /coverage/ (报告输出目录) | OVERWRITE (每次构建覆盖) |
| METRIC | 覆盖率指标(Prometheus) | SHARED (读) |
| CONFIG | 覆盖率配置(.nycrc/jacoco.xml) | EXCLUSIVE (修改) |
| CODEBASE | 被测源码 | SHARED (读) |
| CI/CD | Pipeline覆盖率门禁 | PROTECTED |

### 竞争规避策略
1. **并行采集隔离**: 多个并行任务各自收集覆盖率，最后merge而非同时写入同一文件
2. **报告版本化管理**: 每次构建的覆盖率报告按build number归档，支持历史对比
3. **阈值渐进式提升**: 初始设定较低门槛，每个迭代逐步提高，避免一次性过高导致阻力

## 💡 开源哲学应用 (v7.0)

### OpenCode 透明化
- 覆盖率数据全员可见：每个开发者可查看自己代码的覆盖率情况和团队排名
- 趋势变化透明：覆盖率是上升还是下降、哪些模块在退化，实时展示
- 目标制定过程公开：为什么设定这个覆盖率目标、基于什么数据和考量，清晰记录

### OpenClaude 编排
- 智能缺口分析：自动识别未覆盖的关键路径和边界条件，推荐优先补充的测试用例
- 覆盖率预测模型：基于代码复杂度和历史数据预测达到目标覆盖率所需的工作量
- 伪覆盖检测：识别只追求行覆盖但未真正验证逻辑的"假测试"

### Claw-Code 契约驱动
- 覆盖率硬性门禁：定义最低覆盖率要求（如新增代码>80%），不达标阻止合入
- 分层覆盖率契约：单元测试>集成测试>E2E测试各有不同门槛，综合评估
- 技术债务追踪：将持续低于覆盖率的模块标记为技术债务，纳入清理计划
