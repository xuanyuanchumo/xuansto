## 融合工作流概述

### 核心理念

SDD（Specification-Driven Development，规范驱动开发）与 TDD（Test-Driven Development，测试驱动开发）的融合，构建了"规范→测试→代码"的完整质量保障闭环。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        SDD + TDD 融合闭环                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│    ┌──────────────┐         ┌──────────────┐         ┌──────────────┐       │
│    │     SDD      │ ──────> │     TDD      │ ──────> │    代码      │       │
│    │  规范驱动    │         │  测试驱动    │         │   实现       │       │
│    └──────────────┘         └──────────────┘         └──────────────┘       │
│           │                        │                        │                │
│           │                        │                        │                │
│           ▼                        ▼                        ▼                │
│    ┌──────────────┐         ┌──────────────┐         ┌──────────────┐       │
│    │ 需求规格     │         │ 测试用例     │         │ 功能代码     │       │
│    │ 设计规范     │         │ 验收标准     │         │ 重构优化     │       │
│    │ 接口契约     │         │ 覆盖率要求   │         │ 质量保障     │       │
│    └──────────────┘         └──────────────┘         └──────────────┘       │
│           ▲                        │                        │                │
│           │                        │                        │                │
│           └────────────────────────┴────────────────────────┘                │
│                           反馈验证闭环                                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 融合价值

| 维度 | SDD 贡献 | TDD 贡献 | 融合效果 |
|------|----------|----------|----------|
| 需求质量 | 结构化规范定义 | 可测试性验证 | 需求清晰可验证 |
| 设计质量 | 接口契约先行 | 测试驱动设计 | 设计可落地 |
| 代码质量 | 规范约束代码 | 测试保护重构 | 代码高质量 |
| 追溯能力 | 规范→测试映射 | 测试→代码映射 | 全链路追溯 |

## SDD 到 TDD 的转换规则

### 规范→测试用例映射

#### 映射原则

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        规范→测试映射原则                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  原则1：一对一映射                                                    │   │
│   │  每个功能规范点至少对应一个测试用例                                    │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  原则2：边界覆盖                                                      │   │
│   │  规范中的边界条件必须转化为边界测试用例                                │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  原则3：异常转化                                                      │   │
│   │  规范中的异常处理要求必须转化为异常测试用例                            │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  原则4：场景展开                                                      │   │
│   │  业务场景规范需展开为正向、逆向、边界三类测试                          │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 转换规则详解

##### 规则1：功能规范→单元测试

```
规范描述格式：
┌─────────────────────────────────────────────────────────────────┐
│ 功能名称：[功能名称]                                              │
│ 输入条件：[输入参数及约束]                                        │
│ 输出结果：[预期输出及格式]                                        │
│ 前置条件：[执行前必须满足的条件]                                  │
│ 后置条件：[执行后的状态变化]                                      │
│ 异常处理：[异常情况及处理方式]                                    │
└─────────────────────────────────────────────────────────────────┘

转换规则：
┌─────────────────────────────────────────────────────────────────┐
│ 测试用例 = {                                                     │
│   名称: "test_[功能名]_[场景]_[预期结果]",                       │
│   输入: 规范.输入条件,                                           │
│   预期输出: 规范.输出结果,                                       │
│   前置条件: 规范.前置条件,                                       │
│   验证点: 规范.后置条件                                          │
│ }                                                                │
└─────────────────────────────────────────────────────────────────┘
```

**示例：**

```
规范定义：
┌─────────────────────────────────────────────────────────────────┐
│ 功能名称：用户注册                                               │
│ 输入条件：用户名(6-20字符)、邮箱(有效格式)、密码(≥8位)           │
│ 输出结果：用户对象，包含id、用户名、邮箱、创建时间                │
│ 前置条件：用户名和邮箱未被注册                                    │
│ 后置条件：数据库新增用户记录                                      │
│ 异常处理：                                                       │
│   - 用户名已存在 → 抛出UsernameExistsException                   │
│   - 邮箱已存在 → 抛出EmailExistsException                        │
│   - 参数格式错误 → 抛出ValidationException                       │
└─────────────────────────────────────────────────────────────────┘

转换后的测试用例：
┌─────────────────────────────────────────────────────────────────┐
│ TC-USER-001: test_user_register_with_valid_data_returns_user    │
│ TC-USER-002: test_user_register_with_existing_username_raises   │
│ TC-USER-003: test_user_register_with_existing_email_raises      │
│ TC-USER-004: test_user_register_with_invalid_email_raises       │
│ TC-USER-005: test_user_register_with_short_password_raises      │
│ TC-USER-006: test_user_register_with_short_username_raises      │
│ TC-USER-007: test_user_register_creates_database_record         │
└─────────────────────────────────────────────────────────────────┘
```

##### 规则2：接口规范→集成测试

```
接口规范格式：
┌─────────────────────────────────────────────────────────────────┐
│ 接口路径：[URL路径]                                              │
│ 请求方法：[GET/POST/PUT/DELETE]                                  │
│ 请求参数：[参数名, 类型, 必填, 约束]                              │
│ 响应格式：[状态码, 响应体结构]                                    │
│ 业务规则：[接口处理的业务逻辑]                                    │
│ 权限要求：[访问权限要求]                                          │
└─────────────────────────────────────────────────────────────────┘

转换规则：
┌─────────────────────────────────────────────────────────────────┐
│ 集成测试 = {                                                     │
│   正向测试: 验证正常请求返回预期响应,                             │
│   参数验证: 验证参数缺失/格式错误返回400,                         │
│   权限测试: 验证无权限返回401/403,                                │
│   业务规则测试: 验证业务逻辑正确执行,                             │
│   边界测试: 验证参数边界值处理                                    │
│ }                                                                │
└─────────────────────────────────────────────────────────────────┘
```

##### 规则3：业务流程规范→E2E测试

```
业务流程规范格式：
┌─────────────────────────────────────────────────────────────────┐
│ 流程名称：[业务流程名称]                                          │
│ 参与角色：[涉及的用户角色]                                        │
│ 流程步骤：[步骤序列及条件分支]                                    │
│ 状态变迁：[各步骤的状态变化]                                      │
│ 业务规则：[流程中的业务约束]                                      │
│ 异常流程：[异常情况的处理路径]                                    │
└─────────────────────────────────────────────────────────────────┘

转换规则：
┌─────────────────────────────────────────────────────────────────┐
│ E2E测试 = {                                                      │
│   基本流测试: 验证正常流程完整执行,                               │
│   备选流测试: 验证分支流程正确执行,                               │
│   异常流测试: 验证异常情况正确处理,                               │
│   状态验证: 验证各步骤状态变迁正确,                               │
│   数据验证: 验证流程结束后的数据状态                              │
│ }                                                                │
└─────────────────────────────────────────────────────────────────┘
```

### 转换矩阵

| 规范类型 | 测试类型 | 转换比例 | 负责部门 |
|----------|----------|----------|----------|
| 功能规范 | 单元测试 | 1:N (≥3) | 兵部 |
| 接口规范 | 集成测试 | 1:N (≥5) | 兵部 |
| 业务流程规范 | E2E测试 | 1:N (≥2) | 兵部 |
| 性能规范 | 性能测试 | 1:1 | 兵部 |
| 安全规范 | 安全测试 | 1:N | 兵部 |

## TDD 到 SDD 的反馈机制

### 测试结果→规范验证

#### 反馈闭环

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        TDD→SDD 反馈闭环                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   ┌──────────────┐         ┌──────────────┐         ┌──────────────┐       │
│   │   测试执行   │ ──────> │   结果分析   │ ──────> │   规范更新   │       │
│   └──────────────┘         └──────────────┘         └──────────────┘       │
│          │                        │                        │                │
│          ▼                        ▼                        ▼                │
│   ┌──────────────┐         ┌──────────────┐         ┌──────────────┐       │
│   │ 通过/失败    │         │ 问题分类     │         │ 规范修订     │       │
│   │ 覆盖率报告   │         │ 根因分析     │         │ 版本更新     │       │
│   │ 性能数据     │         │ 影响评估     │         │ 追溯更新     │       │
│   └──────────────┘         └──────────────┘         └──────────────┘       │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 反馈类型与处理

| 反馈类型 | 触发条件 | 处理方式 | 负责部门 |
|----------|----------|----------|----------|
| 测试失败 | 测试用例执行失败 | 分析原因，修正代码或更新规范 | 工部/中书省 |
| 覆盖率不足 | 覆盖率低于阈值 | 补充测试用例，检查规范完整性 | 兵部/中书省 |
| 边界遗漏 | 发现未覆盖边界 | 更新规范边界定义，补充测试 | 中书省/兵部 |
| 异常遗漏 | 发现未处理异常 | 更新规范异常处理，补充测试 | 中书省/兵部 |
| 性能不达标 | 性能测试未通过 | 优化代码或调整性能规范 | 工部/中书省 |

## 步骤4：功能实现（工部，绿灯🟢）

```python
# src/services/auth.py

class AuthService:
    FAILED_ATTEMPTS_LIMIT = 5
    LOCK_DURATION_MINUTES = 30
    
    @staticmethod
    def login(username: str, password: str) -> LoginResult:
        AuthService._validate_credentials(username, password)
        
        user = UserRepository.find_by_username_or_email(username)
        if not user:
            raise UserNotFoundError("用户不存在")
        
        if user.is_locked:
            raise AccountLockedError("账户已锁定")
        
        if not user.verify_password(password):
            AuthService._handle_failed_login(user)
            raise InvalidPasswordError("密码错误")
        
        AuthService._reset_failed_attempts(user)
        token = TokenService.generate_token(user)
        
        LoginLogService.log_success(user.id)
        
        return LoginResult(token=token, user=user)
    
    @staticmethod
    def _validate_credentials(username: str, password: str):
        if not username or len(username) < 3 or len(username) > 50:
            raise ValidationError("用户名长度必须在3-50字符之间")
        if not password or len(password) < 8 or len(password) > 100:
            raise ValidationError("密码长度必须在8-100字符之间")
    
    @staticmethod
    def _handle_failed_login(user: User):
        user.increment_failed_attempts()
        if user.failed_attempts >= AuthService.FAILED_ATTEMPTS_LIMIT:
            user.lock(duration_minutes=AuthService.LOCK_DURATION_MINUTES)
        user.save()
        LoginLogService.log_failure(user.id)
```

## 步骤5：重构优化（刑部，重构🔵）

```python
# 重构后：提取验证器、分离关注点

class CredentialValidator:
    USERNAME_MIN_LENGTH = 3
    USERNAME_MAX_LENGTH = 50
    PASSWORD_MIN_LENGTH = 8
    PASSWORD_MAX_LENGTH = 100
    
    @classmethod
    def validate(cls, username: str, password: str) -> None:
        cls._validate_username(username)
        cls._validate_password(password)
    
    @classmethod
    def _validate_username(cls, username: str) -> None:
        if not username:
            raise ValidationError("用户名不能为空")
        if len(username) < cls.USERNAME_MIN_LENGTH:
            raise ValidationError(f"用户名长度不能小于{cls.USERNAME_MIN_LENGTH}字符")
        if len(username) > cls.USERNAME_MAX_LENGTH:
            raise ValidationError(f"用户名长度不能超过{cls.USERNAME_MAX_LENGTH}字符")
    
    @classmethod
    def _validate_password(cls, password: str) -> None:
        if not password:
            raise ValidationError("密码不能为空")
        if len(password) < cls.PASSWORD_MIN_LENGTH:
            raise ValidationError(f"密码长度不能小于{cls.PASSWORD_MIN_LENGTH}字符")
        if len(password) > cls.PASSWORD_MAX_LENGTH:
            raise ValidationError(f"密码长度不能超过{cls.PASSWORD_MAX_LENGTH}字符")


class AccountLockPolicy:
    FAILED_ATTEMPTS_LIMIT = 5
    LOCK_DURATION_MINUTES = 30
    
    @classmethod
    def should_lock(cls, failed_attempts: int) -> bool:
        return failed_attempts >= cls.FAILED_ATTEMPTS_LIMIT
    
    @classmethod
    def apply_lock(cls, user: User) -> None:
        user.lock(duration_minutes=cls.LOCK_DURATION_MINUTES)


class AuthService:
    def __init__(
        self,
        user_repository: UserRepository,
        token_service: TokenService,
        login_log_service: LoginLogService
    ):
        self.user_repository = user_repository
        self.token_service = token_service
        self.login_log_service = login_log_service
    
    def login(self, username: str, password: str) -> LoginResult:
        CredentialValidator.validate(username, password)
        
        user = self.user_repository.find_by_username_or_email(username)
        if not user:
            raise UserNotFoundError("用户不存在")
        
        if user.is_locked:
            raise AccountLockedError("账户已锁定")
        
        if not user.verify_password(password):
            self._handle_failed_login(user)
            raise InvalidPasswordError("密码错误")
        
        return self._create_success_result(user)
    
    def _handle_failed_login(self, user: User) -> None:
        user.increment_failed_attempts()
        if AccountLockPolicy.should_lock(user.failed_attempts):
            AccountLockPolicy.apply_lock(user)
        user.save()
        self.login_log_service.log_failure(user.id)
    
    def _create_success_result(self, user: User) -> LoginResult:
        user.reset_failed_attempts()
        user.save()
        token = self.token_service.generate_token(user)
        self.login_log_service.log_success(user.id)
        return LoginResult(token=token, user=user)
```

```python
class InterfaceConsistencyChecker:
    """接口一致性检查器"""
    
    def check(self, spec: InterfaceSpec, code: CodeSnapshot) -> ConsistencyReport:
        """
        检查接口实现与规范的一致性
        
        检查项:
        1. 方法签名一致性：参数类型、返回类型、异常声明
        2. 参数约束一致性：必填性、默认值、验证规则
        3. 响应格式一致性：字段名称、字段类型、字段约束
        """
        report = ConsistencyReport(spec_id=spec.id)
        
        code_interface = self.extract_interface_from_code(code)
        
        for param in spec.parameters:
            code_param = code_interface.find_parameter(param.name)
            if not code_param:
                report.add_inconsistency(
                    type="PARAMETER_MISSING",
                    spec_element=param.name,
                    message=f"规范参数 '{param.name}' 在代码中不存在"
                )
            elif code_param.type != param.type:
                report.add_inconsistency(
                    type="PARAMETER_TYPE_MISMATCH",
                    spec_element=param.name,
                    expected=param.type,
                    actual=code_param.type
                )
        
        return report
```

```python
class BehaviorConsistencyChecker:
    """行为一致性检查器"""
    
    def check(self, spec: BehaviorSpec, test_results: TestResults) -> ConsistencyReport:
        """
        检查代码行为与规范的一致性
        
        检查项:
        1. 正常流程一致性：输入输出是否符合规范预期
        2. 异常流程一致性：异常类型和消息是否符合规范

                        type="OUTPUT_MISMATCH",
                        scenario=scenario.name,
                        expected=scenario.expected_output,
                        actual=test_result.actual_output
                    )
```

```python
class ConstraintConsistencyChecker:

    def check(self, spec: ConstraintSpec, code: CodeSnapshot) -> ConsistencyReport:
        """
        检查代码实现与约束规范的一致性
        
        检查项:

        3. 安全约束一致性：权限控制、数据加密

                    type="CONSTRAINT_MISMATCH",
                    constraint=constraint.name,
                    expected=constraint.rule,
                    actual=code_validation.rule
                )
        
        return report
```

## 自动化映射执行器

```python
class SddTddMapper:
    """SDD到TDD的自动化映射器"""
    
    def __init__(self, config_path: str):
        self.config = self.load_config(config_path)
        self.trace_matrix = TraceMatrix()
    
    def map_spec_to_tests(self, spec: Specification) -> List[TestCase]:
        """
        将规范映射为测试用例
        
        流程:
        1. 识别规范类型
        2. 加载对应的映射规则
        3. 生成测试用例骨架
        4. 建立追溯关系
        """
        spec_type = self.identify_spec_type(spec)
        mapping_rules = self.config.get_mapping_rules(spec_type)
        
        test_cases = []
        
        for rule in mapping_rules:
            spec_elements = self.extract_spec_elements(spec, rule.spec_element)
            
            for element in spec_elements:
                test_case = self.generate_test_case(
                    spec=spec,
                    element=element,
                    rule=rule,
                    naming_convention=self.config.naming_conventions
                )
                
                self.trace_matrix.add_trace(
                    spec_id=spec.id,
                    spec_element=element.name,
                    test_id=test_case.id
                )
                
                test_cases.append(test_case)
        
        return test_cases
    
    def generate_test_case(
        self,
        spec: Specification,
        element: SpecElement,
        rule: MappingRule,
        naming_convention: NamingConvention
    ) -> TestCase:
        """生成单个测试用例"""
        
        test_case = TestCase(
            id=self.generate_test_id(spec, element),
            name=self.generate_test_name(spec, element, naming_convention),
            spec_id=spec.id,
            spec_element=element.name,
            test_type=rule.test_types[0],
            status="pending"
        )
        
        test_case.arrange = self.generate_arrange(element)
        test_case.act = self.generate_act(spec, element)
        test_case.assert_ = self.generate_assert(element)
        
        return test_case
```

## 最佳实践建议

### 规范编写建议

1. **可测试性优先**：每个规范点都应该是可测试的
2. **边界明确**：明确定义输入输出的边界条件
3. **异常完整**：覆盖所有可能的异常情况
4. **版本控制**：规范变更需版本管理

### 测试设计建议

1. **全覆盖原则**：确保所有规范点都有对应测试
2. **边界优先**：优先测试边界条件
3. **独立性**：测试用例之间相互独立
4. **可追溯**：每个测试用例关联规范ID

### 追溯维护建议

1. **实时更新**：变更发生时立即更新追溯关系
2. **定期审计**：定期检查追溯完整性
3. **自动化工具**：使用工具自动生成追溯报告
4. **可视化展示**：提供追溯关系的可视化界面

### 协作建议

1. **规范先行**：开发前必须完成规范制定
2. **测试先行**：编码前必须完成测试编写
3. **持续沟通**：规范变更需及时通知相关方
4. **文档同步**：保持规范、测试、代码文档同步

### SDD+TDD融合建议

1. **规范驱动测试**：所有测试用例应源于规范定义
2. **测试验证规范**：测试结果验证规范合规性
3. **重构保持一致**：重构后必须检查规范一致性
4. **追溯双向维护**：保持规范-测试-代码的双向追溯

### Decision Log 系统集成

**核心理念**: 透明化决策链路, 支持效果评估与统计分析。

**数据结构**:
```python
DecisionRecord:
  id: "DEC-YYYYMMDD-NNN"        # 决策ID (例: DEC-20260406-001)
  title: string                  # 决策标题
  content: string                # 决策内容详情
  rationale: List[str]           # 决策依据 (为什么这么做)
  alternatives: List[Dict]       # 备选方案
  selected_option: int           # 选中的方案索引
  impact_scope: List[str]       # 影响范围
  maker: string                  # 决策制定者 (哪个司/局)
  evaluation_plan: string        # 评估计划

EvaluationResult:
  effectiveness_score: float     # 效果评分 0.0 ~ 1.0
  lessons_learned: string        # 经验教训
  would_repeat: bool             # 是否会再做同样的决定
```

**在融合流程中的集成点**:

| 阶段 | 集成点 | 记录内容 |
|------|--------|----------|
| 规范制定(中书省) | 技术选型决策、架构模式决策、ADR记录 | 为什么选择FastAPI而非Flask |
| 规范→测试转换(兵部) | 测试策略决策 | 为什么优先使用pytest+asyncio |
| TDD红-绿-蓝循环 | 实现方案决策、重构策略决策 | 为什么提取CredentialValidator类 |
| 验证反馈(门下省) | 验收标准调整 | 为什么降低覆盖率阈值 |
| 后评估(定期) | evaluate_outcome() | 实际效果评分 + 经验教训 |

**使用示例**:
```python
from skillscripts.core.decision_log import DecisionLog

decisions = DecisionLog(output_dir="docs/logs/decision_logs/")

# 记录技术选型决策
tech_decision = decisions.generate(
    title="API框架选型: FastAPI vs Flask vs DRF",
    rationale=["异步原生支持", "自动OpenAPI文档", "团队熟悉度高"],
    alternatives=[
        {"option": "FastAPI", "pros": ["异步", "自动文档"], "cons": ["较新"]},
        {"option": "Flask", "pros": ["成熟"], "cons": ["需手动配置"]},
    ],
    selected_option=0,
    impact_scope=["backend", "api-design"],
    maker="架构设计局-技术选型司"
)
print(f"已记录: {tech_decision.id}")  # DEC-20260406-001

# 后评估
eval_result = decisions.evaluate_outcome(
    decision_id=tech_decision.id,
    effectiveness_score=0.9,       # 9/10分
    lessons_learned="FastAPI的选择非常正确...",
    would_repeat=True
)

# 查询统计
stats = decisions.get_statistics()
print(f"总决策: {stats['total']}, 已评估: {stats['evaluated_count']}, 平均效果: {stats['avg_effectiveness']:.1%}")
```

### Workflow DSL 引擎集成

**核心理念**: YAML声明式工作流编排, 支持并行/串行/条件/单步四种步骤类型。

**StepType枚举**:
- **PARALLEL**: 并行执行子步骤 (ThreadPoolExecutor)
- **SEQUENTIAL**: 顺序执行子步骤
- **CONDITIONAL**: 条件分支执行 (10种运算符: eq/ne/gt/lt/gte/in/contains/regex/and/or)
- **SINGLE**: 单步执行

**错误处理策略**:
| 策略 | 说明 | 适用场景 |
|------|------|----------|
| `retry_with_backoff` | 指数退避重试 | 网络调用、外部服务 |
| `fail_fast` | 快速失败 | 关键路径、安全相关 |
| `skip_and_continue` | 跳过并继续 | 非关键检查、可选步骤 |
| `escalate_to_human` | 升级人工处理 | 复杂决策、模糊判断 |

**Workflow DSL 执行核心接口**:
```python
from skillscripts.core.workflow_dsl_engine import WorkflowDSLEngine

engine = WorkflowDSLEngine()

# 解析YAML工作流
workflow = engine.parse_workflow(workflow_yaml)

# 验证工作流合法性
validation = engine.validate_workflow(workflow)
if validation.is_valid:
    # 执行完整工作流
    result = engine.execute_workflow(workflow)
    
    for sr in result.step_results:
        print(f"[{sr.status.value}] {sr.name}: {sr.duration_ms}ms")
```

### Clause Extraction 条款提取引擎

详见 [TDD流程](tdd_liucheng.md#v40-更新) 和 [SDD流程](sdd_liucheng.md#v40-更新) 中的详细说明。

**核心能力总结**:
- 从 SDD 规范自动提取 **5大类条款** (功能/API/业务规则/性能/安全)
- 每个条款包含 **前置条件 + 执行步骤 + 预期结果 + 验收标准**
- **ClauseToTestMapper** 自动将条款转化为 TDD 测试骨架 (AAA模式)
- **ClauseCoverageReport** 提供条款级覆盖率统计 (P0/P1/P2/P3)
