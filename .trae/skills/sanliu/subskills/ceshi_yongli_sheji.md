# 测试用例设计

## 测试用例设计方法

### 边界值分析

边界值分析是一种黑盒测试方法，专注于输入和输出边界处的测试。经验表明，大量错误发生在输入范围的边界上，而非内部。

**核心原则：**
- 最小值（Min）
- 最小值+1（Min+）
- 正常值（Nom）
- 最大值-1（Max-）
- 最大值（Max）

**应用场景：**
- 数值范围输入（如年龄0-150）
- 字符串长度限制（如用户名1-20字符）
- 日期范围（如开始日期≤结束日期）
- 数组/列表索引
- 文件大小限制

**示例：**
```
输入条件：年龄输入框，有效范围18-60岁
边界值测试用例：
- 17岁（Min-1，无效边界）
- 18岁（Min，有效边界）
- 19岁（Min+1，有效边界内）
- 39岁（Nom，正常值）
- 59岁（Max-1，有效边界内）
- 60岁（Max，有效边界）
- 61岁（Max+1，无效边界）
```

### 等价类划分

等价类划分将输入数据划分为若干等价类，每个等价类中的数据对于揭露程序错误具有等效作用。

**分类：**
1. **有效等价类**：符合需求规格说明的合理输入集合
2. **无效等价类**：不符合需求规格说明的输入集合

**划分原则：**
- 若输入条件规定了取值范围，可定义一个有效等价类和两个无效等价类
- 若输入条件规定了取值个数，可定义一个有效等价类和两个无效等价类
- 若输入条件规定了值的集合，可定义一个有效等价类和一个无效等价类
- 若输入条件为布尔值，可定义一个有效等价类和一个无效等价类

**示例：**
```
需求：用户名长度为6-20个字符，只能包含字母、数字和下划线

有效等价类：
- E1: 长度6-20，只含字母
- E2: 长度6-20，只含数字
- E3: 长度6-20，只含下划线
- E4: 长度6-20，混合字符

无效等价类：
- I1: 长度<6
- I2: 长度>20
- I3: 包含特殊字符（如@#$%）
- I4: 包含空格
- I5: 包含中文
- I6: 空值
```

### 其他方法

#### 1. 决策表法

适用于多条件组合逻辑的测试场景。

**适用场景：**
- 多个输入条件组合产生不同输出
- 业务规则复杂，条件之间存在依赖关系

**示例：**
```
订单折扣规则：
| VIP会员 | 订单金额>500 | 使用优惠券 | 折扣率 |
|---------|--------------|-----------|--------|
| 是      | 是           | 是        | 30%    |
| 是      | 是           | 否        | 20%    |
| 是      | 否           | 是        | 15%    |
| 是      | 否           | 否        | 10%    |
| 否      | 是           | 是        | 15%    |
| 否      | 是           | 否        | 5%     |
| 否      | 否           | 是        | 10%    |
| 否      | 否           | 否        | 0%     |
```

#### 2. 状态迁移法

适用于测试对象具有明确状态流转的场景。

**适用场景：**
- 订单状态流转（待支付→已支付→发货→完成）
- 工作流审批
- 用户账户状态

**示例：**
```
订单状态迁移测试：
- 待支付 --支付成功--> 已支付
- 待支付 --支付失败--> 待支付
- 待支付 --取消订单--> 已取消
- 已支付 --发货--> 已发货
- 已发货 --确认收货--> 已完成
- 已发货 --申请退货--> 退货中
```

#### 3. 因果图法

用于分析输入条件（因）与输出结果（果）之间的逻辑关系。

**基本符号：**
- 恒等：条件成立则结果成立
- 非：条件成立则结果不成立
- 或：任一条件成立则结果成立
- 与：所有条件成立则结果成立

#### 4. 正交实验法

用于多因素多水平测试，减少测试用例数量同时保证覆盖率。

**适用场景：**
- 配置项组合测试
- 多参数接口测试
- 兼容性测试

**示例：**
```
测试因素：
- 浏览器：Chrome, Firefox, Safari
- 操作系统：Windows, macOS, Linux
- 分辨率：1920x1080, 1366x768

使用正交表L9(3^4)，可从27种组合减少到9种测试组合
```

#### 5. 错误推测法

基于经验和直觉推测可能存在的错误。

**常见错误类型：**
- 空值/null处理
- 特殊字符输入
- 并发操作
- 网络异常
- 数据溢出
- 权限边界

#### 6. 场景法

从用户角度设计端到端的业务流程测试。

**场景类型：**
- 基本流：正常业务流程
- 备选流：分支流程和异常处理

## 测试覆盖率指南

### 代码覆盖率

#### 覆盖率类型

| 类型 | 说明 | 计算方式 |
|------|------|----------|
| 语句覆盖 | 每行代码至少执行一次 | 已执行语句数/总语句数 |
| 分支覆盖 | 每个判断分支至少执行一次 | 已执行分支数/总分支数 |
| 条件覆盖 | 每个条件的真假值至少出现一次 | 已覆盖条件数/总条件数 |
| 分支/条件覆盖 | 同时满足分支覆盖和条件覆盖 | 综合计算 |
| 条件组合覆盖 | 所有条件的真假组合都出现 | 已覆盖组合数/总组合数 |
| 路径覆盖 | 程序中所有可能路径至少执行一次 | 已执行路径数/总路径数 |

#### 覆盖率目标

| 项目类型 | 语句覆盖 | 分支覆盖 | 说明 |
|----------|----------|----------|------|
| 核心业务模块 | ≥90% | ≥85% | 关键功能，高覆盖要求 |
| 一般功能模块 | ≥80% | ≥75% | 常规功能 |
| 工具类/辅助模块 | ≥70% | ≥65% | 非核心功能 |
| 配置/初始化代码 | ≥60% | ≥50% | 启动相关代码 |

### 功能覆盖率

#### 测试需求覆盖

```
覆盖率 = 已覆盖需求数 / 总需求数 × 100%

目标：100%需求覆盖
```

**检查清单：**
- [ ] 所有功能需求都有对应测试用例
- [ ] 所有业务规则都有验证
- [ ] 所有用户场景都有覆盖
- [ ] 所有异常处理都有测试

#### 测试类型覆盖

| 测试类型 | 覆盖范围 | 优先级 |
|----------|----------|--------|
| 单元测试 | 函数/方法级别 | P0 |
| 集成测试 | 模块间交互 | P1 |
| 系统测试 | 端到端功能 | P1 |
| 回归测试 | 已修复缺陷验证 | P1 |
| 验收测试 | 用户需求验证 | P0 |

### 风险覆盖率

#### 基于风险的测试覆盖

| 风险等级 | 覆盖要求 | 测试深度 |
|----------|----------|----------|
| 高风险 | 100%覆盖 | 全面测试（正向+逆向+边界+异常） |
| 中风险 | 80%覆盖 | 主要场景测试（正向+主要异常） |
| 低风险 | 60%覆盖 | 基本功能测试（主要正向场景） |

#### 风险评估维度

```
风险值 = 发生概率 × 影响程度

发生概率：高(3) / 中(2) / 低(1)
影响程度：严重(3) / 一般(2) / 轻微(1)

风险等级：
- 高风险：6-9分
- 中风险：3-5分
- 低风险：1-2分
```

### 兼容性覆盖率

#### 平台兼容性

| 维度 | 覆盖项 |
|------|--------|
| 操作系统 | Windows 10/11, macOS, Linux |
| 浏览器 | Chrome, Firefox, Safari, Edge |
| 移动设备 | iOS, Android（主流版本） |
| 分辨率 | 主流分辨率组合 |

#### 版本兼容性

- 新版本对旧版本数据的兼容
- API接口的向后兼容性
- 数据库迁移兼容性

#### 持续改进

1. **定期评审**：每周评审覆盖率报告
2. **差距分析**：识别未覆盖区域
3. **优先补充**：按风险优先级补充测试
4. **目标设定**：制定阶段性覆盖率目标
5. **流程优化**：改进测试设计和评审流程

### 最佳实践建议

1. **测试先行**：采用TDD方法，先写测试再写代码
2. **分层测试**：金字塔模型，单元测试>集成测试>端到端测试
3. **自动化优先**：核心功能自动化测试覆盖
4. **持续集成**：每次提交触发覆盖率检查
5. **覆盖率门槛**：设置合并代码的覆盖率最低要求
6. **定期清理**：删除无效或重复的测试用例
7. **文档同步**：测试用例与需求文档保持同步更新
