# 代码审查流程

## 审查内容
1. **代码规范**：检查是否符合编码规范
2. **代码质量**：检查代码可读性、可维护性
3. **安全性**：检查潜在安全漏洞
4. **性能**：检查性能问题
5. **测试覆盖**：检查测试覆盖率

## 审查流程
1. 获取待审查代码
2. 进行自动化检查（lint、静态分析）
3. 进行人工审查
4. 记录问题和建议
5. 反馈给开发者

## 详细审查标准

### 1. 代码规范审查
- **命名规范**：
  - 变量名、函数名、类名符合命名约定
  - 避免使用缩写和无意义名称
  - 常量使用大写下划线命名
- **格式规范**：
  - 缩进一致性（空格/Tab）
  - 行长度限制（通常80-120字符）
  - 空行和空格使用规范
  - 大括号风格一致性
- **注释规范**：
  - 函数文档注释完整
  - 复杂逻辑有解释说明
  - 注释与代码保持同步

### 2. 代码质量审查
- **可读性**：
  - 函数长度适中（建议不超过50行）
  - 嵌套深度控制（建议不超过4层）
  - 避免魔法数字和硬编码
- **可维护性**：
  - 单一职责原则
  - 避免重复代码（DRY原则）
  - 合理的模块划分
- **设计原则**：
  - SOLID原则遵循情况
  - 设计模式使用是否恰当
  - 依赖注入使用情况

### 3. 安全性审查
- **输入验证**：
  - 所有外部输入是否验证
  - 验证规则是否完整
- **敏感数据处理**：
  - 密码是否加密存储
  - 敏感信息是否脱敏
  - 日志中是否泄露敏感信息
- **权限控制**：
  - 接口是否有权限校验
  - 越权访问风险检查

### 4. 性能审查
- **算法效率**：
  - 时间复杂度分析
  - 空间复杂度分析
- **资源使用**：
  - 数据库查询优化
  - 内存泄漏风险
  - 文件句柄释放
- **并发处理**：
  - 线程安全问题
  - 死锁风险
  - 资源竞争

### 5. 测试覆盖审查
- **单元测试**：
  - 测试覆盖率是否达标（建议>80%）
  - 边界条件测试
  - 异常情况测试
- **集成测试**：
  - 接口测试覆盖
  - 数据流测试

## 审查工具推荐

| 类型 | 工具 |
|------|------|
| Lint | ESLint, Pylint, Checkstyle |
| 静态分析 | SonarQube, CodeClimate |
| 安全扫描 | SonarQube, Fortify |
| 测试覆盖 | JaCoCo, Coverage.py, Istanbul |

## 问题等级定义

| 等级 | 描述 | 处理方式 |
|------|------|----------|
| 阻塞 | 严重问题，必须修复 | 阻止合并 |
| 重要 | 需要修复的问题 | 本迭代修复 |
| 建议 | 改进建议 | 可选修复 |
| 讨论 | 需要讨论的问题 | 团队讨论 |

## 输出物
- 代码审查报告
- 问题列表（含等级和建议）
- 改进建议
- 审查统计数据

## 最佳实践
1. 审查前确保代码可编译、测试通过
2. 每次审查代码量控制在400行以内
3. 审查意见要具体、建设性
4. 避免主观评价，以规范为准
5. 及时完成审查，不阻塞开发进度
