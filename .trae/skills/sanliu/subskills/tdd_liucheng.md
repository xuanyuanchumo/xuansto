# TDD流程指导

## 红-绿-重构循环

### 循环概述
测试驱动开发（Test-Driven Development，TDD）是一种软件开发方法，其核心是"红-绿-重构"循环。这个循环强调在编写实际代码之前先编写测试，通过测试来驱动代码的设计和实现。TDD的核心思想是：先明确需求（写测试），再实现功能（让测试通过），最后优化代码（重构）。

循环的三个阶段紧密相连，形成一个持续迭代的开发流程。每个循环应该保持短小，通常在几分钟到十几分钟内完成，确保开发节奏稳定且可控。

### 红阶段（Red）- 兵部测试先行

#### 目标
编写一个失败的测试，明确下一步需要实现的功能或修复的问题。此阶段由兵部主导，遵循"测试先行"原则。

#### 详细步骤

1. **理解需求**
   - 明确当前需要实现的具体功能或行为
   - 将需求拆解为最小的可测试单元
   - 思考期望的输入、输出和边界条件
   - 调用 `../../subskills/huanjing_jiance.md` 确保测试环境就绪

2. **设计测试用例**
   - 基于需求规格设计测试场景
   - 应用等价类划分和边界值分析方法
   - 确定测试优先级（P0核心功能/P1重要功能/P2一般功能）
   - 记录测试用例与需求的追溯关系

3. **编写测试代码**
   - 创建测试文件或在现有测试文件中添加测试用例
   - 使用清晰的测试命名，描述测试场景和预期结果
   - 遵循"安排-执行-断言"（Arrange-Act-Assert）模式
   - 只编写必要的测试代码，不要过度设计
   - 确保测试独立于具体实现细节

4. **运行测试确认失败**
   - 执行测试，确认新测试确实失败
   - 检查失败原因是否正确（应该是功能未实现，而非测试代码错误）
   - 确保失败信息清晰明确，能够指导后续开发

5. **验证失败信息**
   - 确保错误消息有意义，能够准确定位问题
   - 如果失败信息不明确，考虑改进测试的断言或错误处理

6. **移交工部**
   - 测试用例评审通过后移交工部开发
   - 提供完整的测试预期和验收标准

#### 兵部测试先行检查清单
```
□ 需求已拆解为最小可测试单元
□ 测试用例覆盖正常路径和异常路径
□ 边界条件已识别并设计测试
□ 测试命名清晰描述行为预期
□ 测试失败原因正确（功能未实现）
□ 失败信息清晰可定位
□ 测试与实现解耦
□ 测试用例已记录追溯关系
```

#### 注意事项
- 测试失败的原因必须是"功能未实现"，而非测试代码本身有问题
- 不要跳过运行测试的步骤，必须确认测试确实失败
- 保持测试简单，一次只测试一个行为或功能点
- 测试应基于需求而非实现细节编写

### 绿阶段（Green）- 工部代码实现

#### 目标
编写最少量的代码，使测试通过。此阶段关注功能实现，不追求代码完美。由工部主导，遵循"最小实现"原则。

#### 详细步骤

1. **分析失败原因**
   - 理解测试失败的具体原因
   - 确定需要实现的最小功能范围
   - 调用 `../../subskills/jiagou_yuanze.md` 获取架构规范指导

2. **加载规范定义**
   - 加载结构化规范定义（SDD）
   - 理解实体定义和接口契约
   - 确认业务规则和约束条件

3. **编写实现代码**
   - 编写刚好能让测试通过的最少代码
   - 不要过度实现，只满足当前测试的需求
   - 可以使用硬编码、简单实现等方式快速通过测试
   - 保持代码可编译、可运行
   - 遵循架构分层原则

4. **架构原则验证**
   - 检查代码是否符合架构规范
   - 验证模块依赖是否合理
   - 确认接口设计是否规范

5. **运行测试确认通过**
   - 执行测试，确认新编写的测试通过
   - 同时确保所有之前的测试仍然通过
   - 如果有测试失败，修改实现代码直到全部通过

6. **规范一致性验证**
   - 验证代码是否符合规范定义
   - 检查实体属性和业务规则实现
   - 确认接口契约遵守

7. **验证功能完整性**
   - 确保实现满足测试描述的行为
   - 检查是否有遗漏的边界情况

#### 工部代码实现检查清单
```
□ 实现代码为最小可行代码
□ 所有测试通过（新测试+旧测试）
□ 代码符合架构分层原则
□ 模块依赖关系合理
□ 规范一致性验证通过
□ 无过度设计
□ 代码可编译可运行
□ 技术决策已记录
```

#### 最小实现原则
```
原则1: 硬编码优先
  - 第一个测试可以用硬编码返回值通过
  - 随着更多测试添加，逐步通用化

原则2: 简单实现优先
  - 选择最简单直接的实现方式
  - 避免引入不必要的抽象

原则3: 重复可接受
  - 绿阶段允许代码重复
  - 重复在重构阶段消除

原则4: 不预先设计
  - 只为当前测试编写代码
  - 不要为未来需求提前实现
```

#### 注意事项
- 代码可以不完美，但必须让测试通过
- 避免在绿阶段进行大规模重构
- 如果发现需要大量代码才能通过测试，考虑拆分测试或重新设计
- 记录技术选型和异常处理决策

### 重构阶段（Refactor）- 刑部重构优化

#### 目标
在测试保护下优化代码结构，提高代码质量，消除重复，改善设计。此阶段由刑部主导，遵循"行为不变"原则。

#### 详细步骤

1. **识别重构机会**
   - 检查代码中是否存在重复代码
   - 评估代码的可读性和可维护性
   - 识别违反设计原则的地方（如单一职责、开闭原则等）
   - 查找可以简化的复杂逻辑
   - 调用 `../../subskills/jiagou_yuanze.md` 进行架构原则检查

2. **选择重构手法**
   - 提取方法：将重复代码或复杂逻辑提取为独立方法
   - 重命名：使用更有意义的变量、方法、类名
   - 移动方法：将方法移动到更合适的类中
   - 简化条件表达式：使用策略模式、状态模式等
   - 消除魔法数字：使用常量或枚举
   - 提取接口：解耦依赖关系

3. **小步重构**
   - 每次只进行一个小的重构操作
   - 重构后立即运行测试，确保测试仍然通过
   - 如果测试失败，立即回退或修复问题
   - 使用版本控制，方便随时回退

4. **运行测试验证**
   - 每次重构后运行完整测试套件
   - 确保所有测试通过，功能行为不变
   - 如果有测试失败，分析原因并修复

5. **质量度量验证**
   - 检查圈复杂度是否降低
   - 检查代码重复率是否降低
   - 检查测试覆盖率是否保持
   - 检查代码可读性是否提升

6. **规范一致性验证**
   - 验证重构后代码仍符合规范定义
   - 调用 `../../resources/guifan_yizhixing_yanzheng.md` 进行验证
   - 记录重构决策与规范依据

7. **提交代码**
   - 重构完成后，确保代码处于可提交状态
   - 提交时附带清晰的提交信息

#### 刑部重构优化检查清单
```
□ 所有测试仍然通过
□ 功能行为未改变
□ 代码重复已消除
□ 命名更加清晰
□ 复杂度已降低
□ 代码可读性提升
□ 规范一致性保持
□ 重构决策已记录
□ 质量指标有提升
```

#### 重构策略与模式

```
策略1: 提取方法
  适用场景: 代码重复、方法过长、逻辑复杂
  操作步骤:
    1. 识别需要提取的代码块
    2. 创建新方法并命名
    3. 将代码移动到新方法
    4. 替换原位置为方法调用
    5. 运行测试验证

策略2: 以多态取代条件
  适用场景: 复杂的switch/if-else逻辑
  操作步骤:
    1. 识别条件分支
    2. 创建策略接口
    3. 为每个分支创建策略类
    4. 使用工厂创建策略实例
    5. 运行测试验证

策略3: 提取接口
  适用场景: 依赖具体实现、耦合过紧
  操作步骤:
    1. 识别依赖的方法
    2. 定义接口
    3. 让实现类实现接口
    4. 修改依赖为接口类型
    5. 运行测试验证

策略4: 移动方法
  适用场景: 方法在错误的类中
  操作步骤:
    1. 识别目标类
    2. 复制方法到目标类
    3. 调整访问权限
    4. 删除原方法
    5. 运行测试验证
```

#### 质量度量标准

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 圈复杂度 | < 10 | 函数复杂度应保持在较低水平 |
| 认知复杂度 | < 15 | 代码理解难度应易于理解 |
| 代码重复率 | < 3% | 重复代码比例应很低 |
| 方法长度 | < 20行 | 单个方法不宜过长 |
| 类长度 | < 200行 | 单个类不宜过大 |
| 参数数量 | < 4个 | 方法参数不宜过多 |
| 嵌套深度 | < 3层 | 代码嵌套不宜过深 |

#### 注意事项
- 重构不应改变代码的外部行为
- 始终保持测试通过状态
- 不要在重构阶段添加新功能
- 如果发现需要新功能，先回到红阶段
- 每次重构后立即运行测试
- 使用版本控制便于回退

## TDD最佳实践

### 测试编写原则

1. **FIRST原则**
   - Fast（快速）：测试应该快速执行，便于频繁运行
   - Independent（独立）：测试之间不应有依赖关系
   - Repeatable（可重复）：测试在任何环境下都应该产生相同结果
   - Self-validating（自验证）：测试应该自动判断通过或失败
   - Timely（及时）：测试应该在编写实现代码之前编写

2. **单一职责**
   - 每个测试只验证一个行为或功能点
   - 测试名称应清晰描述测试场景和预期结果
   - 避免在一个测试中使用多个断言验证不相关的行为

3. **测试命名规范**
   - 使用描述性命名，如 `test_should_return_error_when_input_is_empty`
   - 遵循"given_when_then"或"should_xxx_when_xxx"模式
   - 命名应让测试失败时能快速理解问题

4. **AAA模式**
   - Arrange（安排）：准备测试数据和前置条件
   - Act（执行）：执行被测试的代码
   - Assert（断言）：验证执行结果是否符合预期
   - 在测试代码中使用注释或空行分隔这三个部分

### 循环控制

1. **保持循环短小**
   - 每个红-绿-重构循环应在几分钟内完成
   - 如果循环时间过长，考虑拆分任务
   - 避免一次性编写大量测试或实现代码

2. **小步前进**
   - 每次只添加一个测试
   - 每次只编写最少的实现代码
   - 重构时每次只做一个小的改动

3. **频繁运行测试**
   - 在每个阶段结束后运行测试
   - 重构过程中频繁运行测试
   - 保持测试执行时间足够短

### 代码质量

1. **消除重复**
   - 使用DRY原则（Don't Repeat Yourself）
   - 在重构阶段主动识别和消除重复代码
   - 测试代码也需要避免重复，使用测试辅助方法

2. **保持简单**
   - 遵循KISS原则（Keep It Simple, Stupid）
   - 避免过度设计和不必要的复杂性
   - 优先选择简单直接的实现方式

3. **持续集成**
   - 将TDD与持续集成结合使用
   - 确保每次提交前所有测试通过
   - 使用自动化测试工具

### 测试覆盖

1. **关注行为而非实现**
   - 测试公共接口和可见行为
   - 避免过度测试私有方法或实现细节
   - 测试应该能够指导API设计

2. **边界条件测试**
   - 测试正常情况
   - 测试边界值和极端情况
   - 测试错误处理和异常情况

3. **测试金字塔**
   - 单元测试：数量最多，执行最快
   - 集成测试：适量，验证模块间交互
   - 端到端测试：少量，验证关键业务流程

## 常见问题和解决方案

### 问题1：不知道该写什么测试

**问题描述**：刚开始使用TDD时，不清楚应该从哪个测试开始编写。

**解决方案**：
- 从需求列表开始，将每个需求转化为一个或多个测试
- 使用"待办事项列表"（Todo List）记录需要实现的测试
- 从最简单、最明显的测试开始
- 思考"如果这个功能已经实现，我期望它做什么？"
- 使用用户故事或验收标准作为测试的来源

### 问题2：测试太难编写

**问题描述**：发现编写测试比实现功能更困难，测试代码复杂且难以维护。

**解决方案**：
- 可能是代码设计存在问题，考虑重构以提高可测试性
- 使用依赖注入解耦外部依赖
- 使用Mock或Stub隔离外部系统（数据库、网络等）
- 将复杂逻辑拆分为更小的、可独立测试的单元
- 检查是否违反了单一职责原则

### 问题3：测试运行太慢

**问题描述**：测试套件执行时间过长，影响开发效率。

**解决方案**：
- 识别并优化慢速测试，特别是涉及数据库、网络的测试
- 使用内存数据库或Mock替代真实数据库
- 将集成测试和单元测试分离，单元测试保持快速
- 并行执行测试
- 定期审查测试性能，移除不必要的测试

### 问题4：测试代码难以维护

**问题描述**：测试代码变得混乱、重复，难以理解和修改。

**解决方案**：
- 像对待生产代码一样对待测试代码，保持整洁
- 使用测试辅助方法（Helper Methods）消除重复
- 使用测试数据构建器（Builder Pattern）创建测试数据
- 定期重构测试代码
- 保持测试简单，避免测试中的复杂逻辑

### 问题5：重构时破坏了功能

**问题描述**：在重构阶段修改代码后，发现功能行为发生了变化。

**解决方案**：
- 确保测试覆盖足够全面，能够捕获行为变化
- 每次只做一个小的重构操作
- 重构后立即运行测试
- 使用版本控制，方便回退
- 如果发现测试不足，先补充测试再继续重构

### 问题6：过度依赖Mock

**问题描述**：测试中大量使用Mock，导致测试脆弱且难以理解。

**解决方案**：
- 只Mock真正需要隔离的外部依赖
- 优先使用真实对象而非Mock
- 考虑使用Fake实现而非Mock
- 定期审查Mock的使用，移除不必要的Mock
- 关注交互测试和状态测试的平衡

### 问题7：测试不够全面

**问题描述**：测试通过了，但生产环境中仍然出现Bug。

**解决方案**：
- 审查测试覆盖的边界情况
- 添加负面测试和异常处理测试
- 使用代码覆盖率工具识别未覆盖的代码路径
- 进行代码审查，让他人帮助发现遗漏的测试场景
- 结合探索性测试发现更多问题

### 问题8：团队不采用TDD

**问题描述**：团队成员对TDD持怀疑态度，不愿意采用。

**解决方案**：
- 从小范围试点开始，选择合适的项目或模块
- 展示TDD带来的实际收益，如更少的Bug、更好的设计
- 提供培训和指导，帮助团队成员掌握TDD
- 分享成功案例和经验教训
- 保持耐心，TDD需要时间适应和掌握

### 问题9：遗留代码难以使用TDD

**问题描述**：现有代码没有测试，难以应用TDD进行修改。

**解决方案**：
- 使用" characterization tests"（特征测试）先记录现有行为
- 在修改遗留代码前，先为相关代码添加测试
- 使用"Sprout Method"技术，新功能通过TDD方式添加
- 逐步重构，提高代码的可测试性
- 参考Michael Feathers的《修改代码的艺术》

### 问题10：测试与实现耦合过紧

**问题描述**：测试过度依赖实现细节，导致重构困难。

**解决方案**：
- 测试公共接口和行为，而非实现细节
- 避免直接测试私有方法
- 使用黑盒测试思维，关注输入输出
- 重构时如果测试阻碍修改，考虑重构测试本身
- 保持测试的抽象层次与被测代码匹配

## 循环节奏指南

### 循环时间控制

#### 时间盒建议

| 阶段 | 建议时间 | 最大时间 | 说明 |

### 循环节奏控制

#### 节奏原则

```
原则1: 保持短循环
  - 单个循环不宜过长
  - 超时则拆分任务
  - 避免一次性大改动

原则2: 频繁提交
  - 每个完整循环后提交
  - 提交粒度小而频繁
  - 便于回退和追踪

原则3: 稳定节奏
  - 保持一致的循环速度
  - 避免忽快忽慢
  - 形成肌肉记忆

原则4: 适时休息
  - 连续工作50分钟休息5-10分钟
  - 避免疲劳导致质量下降
  - 保持专注力
```

#### 循环中断处理

```
中断类型1: 时间超限
  触发条件: 单阶段超过最大时间
  处理方式:
    1. 暂停当前工作
    2. 分析超限原因
    3. 拆分任务或寻求帮助
    4. 调整预期后继续

中断类型2: 测试失败
  触发条件: 绿阶段或重构阶段测试失败
  处理方式:
    1. 立即停止
    2. 分析失败原因
    3. 回退到稳定状态
    4. 重新开始循环

中断类型3: 需求变更
  触发条件: 开发过程中需求发生变化
  处理方式:
    1. 完成当前循环
    2. 提交当前进度
    3. 更新测试用例
    4. 开始新循环
```

## v4.0 更新

### 📋 可执行条款提取与Claw-Code契约驱动

v4.0 在传统 TDD 红-绿-蓝循环基础上，增加了 **可执行条款提取 (Clause Extraction)** 阶段，借鉴 Claw-Code 的 SDD 契约驱动理念，实现从 SDD 规范到 TDD 测试的自动化转化。

#### 增强后的TDD流程

```
v4.0 增强版 TDD 流程
═════════════════════

  传统流程:   SDD规范 → [红🔴] → [绿🟢] → [蓝🔵]

  v4.0流程:   SDD规范 → 条款提取 → [红🔴] → [绿🟢] → [蓝🔵]
                   │                                    │
                   ▼                                    ▼
              可执行条款集                    四维防线质量保障
         (前置条件+步骤+预期+验收)          (每层输出检查)
```

#### 条款数据结构

```python
@dataclass
class ExecutableClause:
    """可执行条款 - SDD规范的最小可执行单元"""
    clause_id: str                    # CL-{spec_id}-{NNN}
    spec_ref: str                     # 关联的SDD规范ID
    source_section: str               # 来源章节

    # 条款核心内容
    preconditions: List[str]          # 前置条件列表
    steps: List[ClauseStep]           # 执行步骤
    expected_results: List[str]       # 预期结果
    acceptance_criteria: List[str]    # 验收标准

    # 元数据
    priority: str                     # P0/P1/P2/P3
    complexity: str                   # LOW/MEDIUM/HIGH
    estimated_time: int               # 预估时间(分钟)
    dependencies: List[str]           # 依赖的其他条款ID
    tags: List[str]                  # 标签(正向/边界/异常/性能/安全)

@dataclass
class ClauseStep:
    """条款执行步骤"""
    step_number: int
    action: str                       # 动作描述
    input_data: Dict                  # 输入数据
    expected_output: Any              # 预期输出
    verification_method: str          # 验证方式(assert/log/mock)
```

#### 条款类型分类体系

```
条款类型层次结构
═══════════════

ExecutableClause (可执行条款基线)
├── FunctionalClause (功能条款)
│   ├── PositiveClause (正向条款) - P0 核心 happy path
│   ├── BoundaryClause (边界条款) - P1 边界值处理
│   └── ExceptionClause (异常条款) - P1 异常处理
│
├── ApiClause (接口条款)
│   ├── ParamValidationClause (参数验证条款)
│   ├── PermissionClause (权限验证条款)
│   └── ResponseFormatClause (响应格式条款)
│
├── BusinessRuleClause (业务规则条款)
│   ├── TriggerClause (规则触发条款)
│   ├── CalculationClause (计算规则条款)
│   └── TransitionClause (状态流转条款)
│
├── PerformanceClause (性能条款) - P2
└── SecurityClause (安全条款) - P0/P1
```

#### 条款提取流程（红阶段增强）

```
v4.0 红阶段 (兵部主导, Clause-Driven)
═════════════════════════════════════

  Step 1: SDD规范加载
      │
      ▼
  Step 2: 可执行条款提取 (ClauseExtractor)
      │  • 功能规范 → 正向/边界/异常条款
      │  • 接口规范 → 参数/权限/业务规则条款
      │  • 流程规范 → 基本/备选/异常流条款
      │
      ▼
  Step 3: 条款→测试转化 (ClauseToTestMapper)
      │  • 每个条款 → 1~N 个测试骨架
      │  • 自动建立追溯关系 (clause_id ↔ test_id)
      │  • AAA模式填充
      │
      ▼
  Step 4: 测试代码编写 (基于条款骨架)
      │  • 测试数据构建
      │  • Mock/Stub隔离
      │
      ▼
  Step 5: 测试执行确认红灯 🔴
      │  • 所有新测试必须失败
      │  • 失败原因 = "功能未实现"
      │  • 记录条款覆盖率
      │
      ▼
  Step 6: ★ 四维防线L1检查 ★
      PromptLayer: 测试意图是否明确?
      │
      ▼
  Step 7: 移交工部 (带条款追溯矩阵)
```

#### 条款→TDD测试自动转化规则

| 条款类型 | 转化规则 | 生成的测试模式 |
|----------|----------|---------------|
| **正向条款(P0)** | preconditions→Arrange, steps→Act, expected→Assert | `test_{spec}_positive_happy_path` |
| **边界条款(P1)** | boundary.value→Arrange(边界值), expected_behavior→Assert | `test_{spec}_boundary_{param}_{bound_name}` |
| **异常条款(P1)** | trigger_conditions→Arrange(触发条件), exception_type→Assert | `test_{spec}_exception_{exc_type}` |
| **API参数条款** | param.invalid_example→Arrange, HTTP 400→Assert | `test_api_{endpoint}_{param}_invalid` |
| **业务规则条款** | conditions→Arrange, actions→Act, success_criteria→Assert | `test_rule_{rule_id}_trigger` |

#### 条款覆盖率统计

```python
@dataclass
class ClauseCoverageReport:
    """条款覆盖率报告"""
    total_clauses: int
    covered_clauses: int
    coverage_percent: float

    by_priority: Dict[str, CoverageByPriority]  # P0/P1/P2/P3 各自覆盖情况
    by_tag: Dict[str, CoverageByTag]             # 按标签分类覆盖
    missing_clauses: List[ExecutableClause]      # 未覆盖的条款

    def is_acceptable(self, threshold=0.95) -> bool:
        return self.coverage_percent >= threshold

    def to_markdown(self) -> str:
        """生成Markdown格式覆盖率报告"""
```

#### 与四维防线的集成

```
TDD循环 + 四维防线集成点
═════════════════════════

  红阶段结束 ──→ 四维防线检查
    ├─ L1 PromptLayer:     测试意图是否明确? 条件是否完备?
    ├─ L2 CapabilityLayer: 测试工具是否就绪? Mock框架可用?
    ├─ L3 RuleValidation:  测试命名/结构/AAA是否符合规范?
    └─ L4 FallbackRecovery: 不通过时如何处理? 回滚到哪个版本?

  绿阶段结束 ──→ 四维防线检查
    ├─ L3: 代码规范(Lint/安全扫描/性能基线)
    └─ L4: 质量评分(完整性/准确性/安全性 ≥ 3.5/5)

  蓝阶段结束 ──→ 四维防线检查
    ├─ L3: 重构后规范一致性 + 复杂度指标
    └─ L4: 重构效果评分 + 兜底恢复策略
```

#### 完整使用示例：用户认证模块

```python
from skillscripts.core.four_d_defense import FourDimensionalDefense
from skillscripts.core.resource_coordinator import ResourceCoordinator, LockType
from skillscripts.core.decision_log import DecisionLog

# === 初始化 ===
marc = ResourceCoordinator()
defense = FourDimensionalDefense()
decisions = DecisionLog(output_dir="docs/logs/decision_logs/")

# === Step 1: 定义SDD规范 (中书省输出) ===
auth_spec = {
    "id": "AUTH-001",
    "name": "用户登录",
    "functions": [{
        "id": "login",
        "inputs": [
            {"name": "username", "type": "str", "constraints": "3-50字符"},
            {"name": "password", "type": "str", "constraints": "8-100字符"}
        ],
        "outputs": ["返回LoginResult含token"],
        "exceptions": [
            {"type": "UserNotFoundError", "trigger": "用户不存在"},
            {"type": "InvalidPasswordError", "trigger": "密码错误"},
            {"type": "AccountLockedError", "trigger": "账户锁定5次失败"}
        ],
        "bounds": [
            {"name": "用户名最小长度", "value": "ab", "expected": "应拒绝"},
            {"name": "密码最小长度", "value": "1234567", "expected": "应拒绝"}
        ]
    }]
}

# === Step 2: 条款提取 (MARC协调) ===
with marc.acquire_context("specs", "bingbu-tdd-zhixingsi", LockType.EXCLUSIVE):
    clauses = extract_clauses_from_spec(auth_spec)

    print(f"提取条款数: {len(clauses)}")
    for c in clauses[:5]:
        print(f"  [{c.priority}] {c['id']}: {c['tags']}")

    # 输出:
    # 提取条款数: 9
    #   [P0] CL-AUTH-001-001: ['positive', 'happy-path']
    #   [P1] CL-AUTH-001-002: ['boundary', 'username']
    #   [P1] CL-AUTH-001-003: ['boundary', 'password']
    #   [P1] CL-AUTH-001-004: ['exception', 'UserNotFound']
    #   [P1] CL-AUTH-001-005: ['exception', 'InvalidPassword']

# === Step 3: 条款→测试骨架转化 ===
test_skeletons = []
for clause in clauses:
    skeleton = {
        "test_name": f"test_auth_login_{'_'.join(clause['tags'][:2])}",
        "clause_id": clause["id"],
        "arrange": f"# 前置条件: {'; '.join(clause['preconditions'])}",
        "act": f"# 执行: {clause['steps'][0]['action'] if clause['steps'] else 'login()'}",
        "assertions": [f"assert {r}" for r in clause["expected_results"]]
    }
    test_skeletons.append(skeleton)

# === Step 4: 确认红灯 🔴 + 四维防线L1 ===
defense_result_red = defense.run_full_check({
    "phase": "red",
    "clauses": clauses,
    "tests": test_skeletons,
    "intent": "auth_module_test_generation"
})
print(f"红线四维防线: {defense_result_red.overall_status}")

if defense_result_red.passed:
    pytest_results = run_tests()
    assert pytest_results.failed == len(test_skeletons), "所有新测试应失败(红灯)"

# === Step 5: 记录决策 ===
tdd_decision = decisions.generate(
    title="AUTH模块采用Clause-Driven TDD",
    content="从SDD提取9个可执行条款，生成对应测试骨架",
    rationale=["条款驱动确保需求全覆盖", "自动追溯关系保证可维护性"],
    maker="兵部-TDD执行司"
)

# === Step 6: 绿阶段 (工部) ===
with marc.acquire_context("src/auth", "gongbu-daima-shengchengsi", LockType.EXCLUSIVE):
    # 最小实现...
    pass

# === Step 7: 蓝阶段 (刑部 + 四维防线L4兜底) ===
with marc.acquire_context("src/auth", "xingbu-ziyanhuasi", LockType.EXCLUSIVE):
    final_check = defense.run_full_check({"phase": "blue", "module": "auth"})
    if not final_check.passed:
        apply_fallback(final_check.fallback_strategy)

# 后评估
decisions.evaluate_outcome(
    decision_id=tdd_decision.id,
    effectiveness_score=0.88,
    lessons_learned="条款驱动TDD使测试覆盖率从82%提升到96%",
    would_repeat=True
)
```
