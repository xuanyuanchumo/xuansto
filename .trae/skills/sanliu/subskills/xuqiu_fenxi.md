# 需求分析流程

## 概述
需求分析是软件开发的关键环节，直接影响项目的成功与否。本子技能提供系统化的需求分析方法，帮助准确理解和记录用户需求。

## 工作步骤

### 1. 需求收集
与用户/产品经理访谈，收集功能与非功能需求。

**访谈技巧：**
- 使用开放式问题引导用户表达
- 关注"为什么"而非仅"做什么"
- 记录用户的实际工作场景
- 识别隐性需求和潜在需求

**需求来源：**
- 用户访谈和问卷
- 竞品分析
- 业务流程分析
- 现有系统问题反馈
- 法规和合规要求

### 2. 需求建模
使用用例图、用户故事描述功能。

#### 用例图示例

```
+------------------+
|    用户管理系统    |
+------------------+
|                  |
|  +--------+      |
|  | 用户   |------|-----> 登录系统
|  +--------+      |
|       |          |
|       +--------->-----> 修改密码
|                  |
|  +--------+      |
|  | 管理员 |------|-----> 用户管理
|  +--------+      |
|       |          |
|       +--------->-----> 权限分配
+------------------+
```

**用例图要素：**
- 参与者（Actor）：与系统交互的外部实体
- 用例（Use Case）：系统提供的功能单元
- 关系：关联、包含、扩展、泛化

#### 用户故事模板

```markdown
## 用户故事：[故事名称]

**作为** [用户角色]
**我想要** [完成的目标]
**以便于** [获得的价值]

### 验收标准
- [ ] 给定 [前置条件]
- [ ] 当 [触发动作]
- [ ] 那么 [预期结果]

### 优先级
- MoSCoW: [Must/Should/Could/Won't]
- 业务价值: [高/中/低]
- 技术复杂度: [高/中/低]

### 备注
- 相关依赖：
- 风险提示：
```

**用户故事示例：**

```markdown
## 用户故事：用户登录

**作为** 注册用户
**我想要** 使用账号密码登录系统
**以便于** 访问我的个人数据和功能

### 验收标准
- [ ] 给定 用户已注册账号
- [ ] 当 用户输入正确的账号密码并点击登录
- [ ] 那么 系统验证成功并跳转到首页

- [ ] 给定 用户输入错误密码
- [ ] 当 用户点击登录
- [ ] 那么 系统显示错误提示"账号或密码错误"

- [ ] 给定 用户连续5次输入错误密码
- [ ] 当 用户再次尝试登录
- [ ] 那么 账号被锁定15分钟

### 优先级
- MoSCoW: Must
- 业务价值: 高
- 技术复杂度: 低
```

### 3. 需求优先级划分

#### MoSCoW 方法

| 优先级 | 含义 | 说明 |
|--------|------|------|
| Must | 必须有 | 核心功能，缺失则产品无价值 |
| Should | 应该有 | 重要但非关键，可延期 |
| Could | 可以有 | 锦上添花，资源允许时实现 |
| Won't | 暂不做 | 本次迭代不做，可能后续考虑 |

#### Kano 模型分类

```
满意度
  ^
  |         /\
  |        /  \  兴奋型需求
  |       /    \
  |------/------\------> 实现程度
  |     /        \
  |    / 期望型需求\
  |   /            \
  |  / 基本型需求   \
  | /                \
  +------------------->
```

**需求类型：**
- 基本型需求：必须满足，否则用户不满意
- 期望型需求：满足程度与满意度成正比
- 兴奋型需求：超出期望，带来惊喜
- 无差异需求：用户不在意
- 反向需求：满足反而降低满意度

#### 优先级评估矩阵

|              | 高业务价值 | 中业务价值 | 低业务价值 |
|--------------|-----------|-----------|-----------|
| 低技术复杂度 | 优先实现   | 计划实现   | 考虑实现   |
| 中技术复杂度 | 计划实现   | 考虑实现   | 暂缓       |
| 高技术复杂度 | 评估决策   | 暂缓       | 不做       |

### 4. 输出需求规格说明书

撰写 SRS 文档，包含以下内容：

```markdown
# 需求规格说明书（SRS）

## 1. 引言
### 1.1 项目背景
### 1.2 项目目标
### 1.3 术语定义
### 1.4 参考资料

## 2. 总体描述
### 2.1 产品视角
### 2.2 用户特征
### 2.3 约束条件
### 2.4 假设与依赖

## 3. 功能需求
### 3.1 功能列表
### 3.2 用例描述
### 3.3 业务规则

## 4. 非功能需求
### 4.1 性能需求
### 4.2 安全需求
### 4.3 可用性需求
### 4.4 兼容性需求

## 5. 接口需求
### 5.1 用户接口
### 5.2 硬件接口
### 5.3 软件接口
### 5.4 通信接口

## 6. 附录
```

### 5. 需求评审
提交门下省审议，确保需求质量。

**评审检查点：**
- 需求完整性：是否覆盖所有业务场景
- 需求一致性：是否存在矛盾或冲突
- 需求可行性：技术实现是否可行
- 需求可验证性：是否可以测试验证
- 需求可追溯性：是否可追溯到来源

## 需求分析方法论

### 结构化分析方法
1. 数据流图（DFD）：描述数据在系统中的流动
2. 数据字典：定义数据元素的含义
3. 状态转换图：描述系统状态变化

### 面向对象分析方法
1. 用例建模：识别参与者和用例
2. 类图建模：识别类和关系
3. 顺序图建模：描述对象交互

### 敏捷需求方法
1. 用户故事地图：可视化用户旅程
2. 产品待办列表：优先级排序的需求池
3. 迭代规划：按迭代交付价值

## 常见问题与解决方案

| 问题 | 解决方案 |
|------|----------|
| 需求模糊 | 使用原型验证，获取明确反馈 |
| 需求频繁变更 | 建立变更控制流程，评估影响 |
| 需求遗漏 | 使用检查清单，多维度审查 |
| 需求冲突 | 组织协调会议，明确优先级 |
| 过度设计 | 聚焦MVP，迭代演进 |

## 输出物
- 需求规格说明书（SRS）
- 用例图
- 用户故事列表
- 原型图（可选）
- 需求追踪矩阵
