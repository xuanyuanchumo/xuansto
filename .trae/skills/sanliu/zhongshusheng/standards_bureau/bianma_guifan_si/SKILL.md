# 编码规范司

## 概述
编码规范司是中书省规范制定局的基础职能单元，负责建立与维护项目全生命周期的编码质量标准体系。本司基于技术栈特性与团队最佳实践，定义统一的编码风格、代码组织原则与质量基线，通过可执行的配置文件（.editorconfig / .eslintrc / pyproject.toml 等）将规范落地到开发工具链中，确保团队产出的代码具备一致性与可维护性。

## 核心职责
- 编码风格定义：缩进、引号、换行、空格等格式化规则的统一约定
- 命名约定制定：变量、函数、类、文件、目录的命名规则（详见命名约定司）
- 代码组织原则：模块划分、文件结构、导入顺序等组织性规范
- 配置文件生成：输出可直接被 IDE 和 CI/CD 消费的规范化配置文件
- 规范演进管理：跟踪语言/框架版本更新，及时调整编码规范

## 输入与输出
| 输入 | 输出 |
|------|------|
| 技术栈信息 | 编码规范文档 |
| 团队偏好调研 | .editorconfig 文件 |
| 语言官方推荐 | .eslintrc / .prettierrc 配置 |
| 项目结构要求 | pyproject.toml / tsconfig.json |
| 历史问题清单 | gofmt / rustfmt 配置 |

## 工作流程
1. **技术栈分析阶段**：识别项目使用的编程语言、框架及工具链版本
2. **基准调研阶段**：参考语言官方风格指南、社区主流实践与团队历史偏好
3. **规则草案编写**：逐项定义格式化、命名、组织等维度的具体规则
4. **配置文件生成**：将规则转化为各工具可识别的配置文件格式
5. **工具集成验证**：在示例代码上运行 Linter/Formatter 验证配置有效性
6. **团队评审阶段**：收集开发者反馈，对争议规则进行讨论与决策
7. **发布与推广**：正式发布规范文档与配置，纳入项目初始化模板

## 协作关系
- 上级局：规范制定局 (standards_bureau)
- 协作司：命名约定司（命名规则详细定义）、Lint 规则司（静态分析规则）
- 下游：尚书省-工部（开发执行）、刑部（Code Review 标准）
- 跨局协作：架构设计局-技术选型司（基于选型结果定制规范）

## v4.0 新增能力
- 操作优先级：script + command（使用脚本从模板生成配置文件，命令行工具执行格式化验证）
- 四维防线：
  - 第一防线：编辑器自动格式化（EditorConfig + Formatter 确保保存即合规）
  - 第二防线：提交前 Hook 检查（pre-commit lint-staged 自动拦截不规范代码）
  - 第三防线：CI 门禁强制检查（PR 合并前必须通过全部 Lint 规则）
  - 第四防线：定期规范审计（扫描存量代码的规范违规趋势）
- 资源协调：
  - 格式化工具链（Prettier/Black/gofmt/rustfmt 等）
  - Lint 引擎（ESLint/Pylint/golangci-lint/clippy 等）
  - EditorConfig 统一配置
  - pre-commit 框架集成
