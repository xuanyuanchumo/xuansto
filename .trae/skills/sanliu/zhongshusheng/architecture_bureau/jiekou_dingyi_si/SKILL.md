# 接口定义司

## 概述
接口定义司负责建立系统内外部交互的契约规范，是保障系统集成质量与服务稳定性的关键职能单元。本司通过标准化的 API 设计方法与数据模型规范，确保前后端协作、服务间调用、第三方集成均有清晰明确的接口约定，减少集成阶段的沟通成本与联调返工。

## 核心职责
- API 契约定义：采用 OpenAPI/Swagger 规范设计 RESTful / GraphQL / gRPC 接口
- 数据模型设计：定义请求/响应的数据结构、字段语义与校验规则
- 接口版本管理：制定 API 版本策略（URL/Header/Media Type），管理版本演进
- 错误码体系设计：统一错误响应格式与分类编码体系
- 接口Mock服务提供：基于契约生成 Mock 服务，支持并行开发

## 输入与输出
| 输入 | 输出 |
|------|------|
| 架构设计文档 | OpenAPI 规范文件（YAML/JSON） |
| 业务规则说明 | 数据字典文档 |
| 领域模型定义 | 接口版本管理策略 |
| 错误处理需求 | 统一错误码清单 |
| 前端页面原型 | Mock 服务配置 |

## 工作流程
1. **需求梳理阶段**：从 PRD 和架构设计中提取所有需要暴露的接口需求
2. **资源识别阶段**：按照 RESTful 或 GraphQL 最佳实践设计资源路径与操作
3. **数据模型设计**：定义每个接口的请求体、响应体、错误响应的数据结构
4. **规范编写阶段**：使用 OpenAPI Specification 编写完整的接口描述文件
5. **版本策略制定**：确定版本号规则、兼容性承诺与废弃流程
6. **评审确认阶段**：组织前后端、集成方共同评审接口契约
7. **Mock 发布阶段**：基于契约生成 Mock 服务，供消费方提前对接

## 协作关系
- 上级局：架构设计局 (architecture_bureau)
- 协作司：系统架构司（架构边界对齐）、技术选型司（协议选型参考）
- 下游：尚书省-工部（后端实现）、礼部（接口测试）
- 跨局协作：规范制定局-命名约定司（API 端点命名规范）

## v4.0 新增能力
- 操作优先级：script + command（使用代码生成工具从 OpenAPI 规范自动生成 Client SDK / Server Stub / Mock）
- 四维防线：
  - 第一防线：OpenAPI 规范校验（自动检测规范文件的语法与语义正确性）
  - 第二防线：命名规范一致性（自动检查端点/字段符合命名约定）
  - 第三防线：Breaking Change 检测（版本升级时自动识别不兼容变更）
  - 第四防线：契约测试门禁（发布前自动运行 Pact/Consumer Contract 测试）
- 资源协调：
  - API 设计平台（Stoplight/Apimatic/Swagger Hub）
  - 代码生成工具链（openapi-generator/swagger-codegen）
  - 契约测试框架（Pact/Spring Cloud Contract）
