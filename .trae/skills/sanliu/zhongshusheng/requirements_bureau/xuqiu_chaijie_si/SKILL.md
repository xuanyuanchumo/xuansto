# 需求拆解司

## 概述
需求拆解司负责将高层次的业务需求和用户故事转化为可执行、可追踪的结构化任务单元。本司运用系统化的分解方法，将复杂的 Epic 拆解为独立的 Story 和 Task，同时分析任务间的依赖关系与技术可行性，确保每个需求单元都具备清晰的完成定义（Definition of Done）和可估量的工作量。

## 核心职责
- Epic 拆解：将大型业务需求（Epic）按照业务边界和技术架构进行合理拆分
- Story 分解：将 User Story 进一步细化为包含明确验收标准的开发任务
- 依赖关系分析：识别任务间的前置依赖、并行可能性与关键路径
- 技术可行性评估：从技术实现角度评估需求的可行性与复杂度
- 工作量估算辅助：提供估算所需的技术信息与历史数据参考

## 输入与输出
| 输入 | 输出 |
|------|------|
| PRD 或用户故事 | 结构化需求树 |
| 架构设计约束 | 任务依赖图 |
| 技术栈信息 | 可行性评估报告 |
| 历史项目数据 | Story 拆分清单 |
| 团队产能数据 | 估算参考基准 |

## 工作流程
1. **需求接收阶段**：获取 PRD 或用户研究司产出的用户故事列表，理解业务上下文
2. **Epic 识别阶段**：按业务领域或功能模块将需求分组，形成 Epic 层级
3. **Story 拆分阶段**：遵循 INVEST 原则将 Epic 拆分为独立可交付的 Story
4. **Task 细化阶段**：将 Story 分解为具体的技术任务，明确技术实现要点
5. **依赖分析阶段**：绘制任务依赖关系图，识别关键路径与并行机会
6. **可行性验证阶段**：评估每个任务的技术复杂度与风险等级
7. **输出整合阶段**：生成完整的需求树结构与依赖图，移交下游

## 协作关系
- 上级局：需求分析局 (requirements_bureau)
- 协作司：用户研究司（需求来源）、验收标准司（AC 定义）、优先级排序司（优先级输入）
- 下游：尚书省-工部（开发实施）、礼部（测试验证）
- 跨局协作：架构设计局-系统架构司（架构约束对齐）

## v4.0 新增能力

- 四维防线：
  - 第一防线：拆解完整性检查（确保无遗漏需求项）
  - 第二防线：INVEST 原则校验（自动检测 Story 质量）
  - 第三防线：依赖环检测（自动识别循环依赖）
- 资源协调：
  - 项目管理工具集成（Jira/Linear/GitHub Projects）
  - 架构约束文档访问权限
  - 历史项目数据库（用于估算参考）
