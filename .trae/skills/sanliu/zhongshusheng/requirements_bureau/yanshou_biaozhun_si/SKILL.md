# 验收标准司

## 概述
验收标准司负责为每一个需求单元定义清晰、可度量、可验证的验收条件（Acceptance Criteria）。本司通过系统化的方法识别功能的正常路径、边界条件和异常场景，确保开发团队有明确的完成标准，测试团队有完整的验证依据，从而减少需求歧义导致的返工与争议。

## 核心职责
- 验收标准定义（AC）：为每个 Story 编写 Given-When-Then 格式的验收条件
- 边界条件识别：分析输入输出的边界值、极限情况与特殊状态
- 异常场景覆盖：识别并定义错误处理、降级策略、容错机制等异常流程
- 完成定义维护：维护项目的 Definition of Done（DoD）标准清单
- 测试用例对齐：确保验收标准可直接转化为可执行的测试用例

## 输入与输出
| 输入 | 输出 |
|------|------|
| 需求规格说明书 | 完整验收标准矩阵 |
| 用户故事 | AC 清单（Given-When-Then格式） |
| 业务规则文档 | 边界条件清单 |
| 接口契约定义 | 异常场景矩阵 |
| DoD 标准 | 更新的 DoD 文档 |

## 工作流程
1. **需求解析阶段**：深入理解需求的功能目标、业务规则与非功能要求
2. **正常路径定义**：编写主要用户场景的验收标准（Happy Path）
3. **边界条件分析**：识别数值边界、时间边界、权限边界等边界场景
4. **异常场景梳理**：列举可能的错误输入、服务不可用、并发冲突等情况
5. **AC 编写阶段**：采用 Given-When-Then 格式规范化编写所有验收条件
6. **矩阵组装阶段**：将 AC 按需求单元组织成结构化的验收标准矩阵
7. **评审完善阶段**：与开发、测试团队评审 AC 的完整性与可测试性

## 协作关系
- 上级局：需求分析局 (requirements_bureau)
- 协作司：需求拆解司（Story 输入）、用户研究司（用户场景验证）
- 下游：尚书省-礼部（测试用例设计）、刑部（QA 审查）
- 跨局协作：规范制定局-编码规范司（代码质量标准对齐）

## v4.0 新增能力
- 操作优先级：script（可使用脚本生成 AC 模板并进行覆盖率分析）
- 四维防线：
  - 第一防线：AC 完整性检查（确保每个 Story 至少有 1 个 AC）
  - 第二防线：边界条件覆盖率统计（自动计算边界场景覆盖比例）
  - 第三防线：GWT 格式合规性校验（自动检测 Given-When-Then 格式正确性）
  - 第四防线：DoD 门禁（发布前自动验证 DoD 全部条目）
- 资源协调：
  - BDD 框架支持（Cucumber/SpecFlow 等）
  - 测试管理平台集成
  - 业务规则引擎访问（用于复杂逻辑验证）
