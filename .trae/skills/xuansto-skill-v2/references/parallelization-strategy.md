## 1. 并行化架构概述

Xuansto Skill v2 参照 ECC（Emergent Coding Collective）的并行化模式，通过多Agent协同和资源隔离实现高效并行执行。

### 1.1 并行化层级

| 层级 | 并行方式 | 适用场景 | 最大并行度 |
|------|----------|----------|-----------|
| L1 | Git Worktree | 多Agent修改不同文件/模块 | 4 |
| L2 | Fork对话 | 独立任务并行执行 | 3 |
| L3 | 子代理协作 | 上下文协商与迭代检索 | 2 |
| L4 | 内部并行 | Agent内部多步骤并行 | 不限 |

### 1.2 并行化决策矩阵

| 任务特征 | 串行 | L1 Worktree | L2 Fork | L3 子代理 |
|----------|------|-------------|---------|----------|
| 单文件修改 | ✓ | | | |
| 多文件独立修改 | | ✓ | | |
| 多模块独立任务 | | ✓ | ✓ | |
| 需要上下文协商 | | | | ✓ |
| 有依赖关系的任务 | ✓ | | | |
| 需要共享状态的任务 | | | ✓ | ✓ |

## 2. Git Worktree并行

### 2.1 基本原理

多Agent并行修改不同文件时使用 git worktree 隔离工作区，每个Agent在独立的工作树中操作，避免文件级冲突。

### 2.2 Worktree创建与销毁

**创建Worktree**：

```bash
git worktree add ../agent-a-worktree feature-branch-a
git worktree add ../agent-b-worktree feature-branch-b
```

**销毁Worktree并合并**：

```bash
git worktree remove ../agent-a-worktree
git merge feature-branch-a
```

### 2.3 Worktree命名规范

| Agent角色 | Worktree路径 | 分支命名 |
|-----------|-------------|----------|
| Architect | ../architect-worktree | feat/arch-{task-id} |
| Coder | ../coder-worktree | feat/coder-{task-id} |
| Reviewer | ../reviewer-worktree | feat/review-{task-id} |
| Security | ../security-worktree | feat/sec-{task-id} |

### 2.4 Worktree生命周期

| 阶段 | 操作 | 说明 |
|------|------|------|
| 创建 | git worktree add | Phase 4开始时创建 |
| 使用 | Agent在worktree中工作 | 独立提交、独立测试 |
| 合并 | git merge --no-ff | Phase 4结束时合并 |
| 清理 | git worktree remove | 合并完成后清理 |
| 回滚 | git reset --hard | 合并冲突无法解决时回滚 |

### 2.5 Worktree使用约束

- 每个Worktree仅分配给一个Agent，不共享
- Worktree中的提交必须通过质量门禁后才能合并
- 合并顺序按Agent优先级：Security > Reviewer > Coder > Architect
- Worktree数量不超过4个，超出则排队等待
- Worktree创建前必须检查磁盘空间（预留1GB/Worktree）

## 3. 子代理上下文协商

### 3.1 协商流程

Orchestrator评估子代理返回结果，必要时发起追问（最多3轮）。传递目标上下文而非仅查询，确保子代理理解完整意图。

```
Orchestrator → 子代理: 发送任务 + 完整上下文
子代理 → Orchestrator: 返回结果
Orchestrator: 评估结果质量
  ↓ 不满足
Orchestrator → 子代理: 追问 + 补充上下文 (第2轮)
子代理 → Orchestrator: 返回改进结果
Orchestrator: 再次评估
  ↓ 仍不满足
Orchestrator → 子代理: 最终追问 + 明确指引 (第3轮)
子代理 → Orchestrator: 返回最终结果
Orchestrator: 接受结果或标记为需人工介入
```

### 3.2 上下文传递规范

| 传递内容 | 格式 | 必需性 |
|----------|------|--------|
| 任务描述 | 自然语言 | 必需 |
| 目标上下文 | 结构化JSON | 必需 |
| 约束条件 | YAML/JSON | 必需 |
| 参考文档 | 文件路径列表 | 可选 |
| 历史决策 | decision_log条目 | 可选 |
| 质量标准 | 门禁列表 | 可选 |

### 3.3 追问策略

| 追问轮次 | 上下文补充 | 期望改进 |
|----------|-----------|----------|
| 第1轮 | 完整目标上下文 | 基础结果 |
| 第2轮 | 补充缺失约束 + 具体示例 | 精确结果 |
| 第3轮 | 明确指引 + 评估标准 | 最终结果 |

### 3.4 协商超时处理

| 追问轮次 | 超时时间 | 超时处理 |
|----------|----------|----------|
| 第1轮 | 30秒 | 继续追问 |
| 第2轮 | 45秒 | 继续追问 |
| 第3轮 | 60秒 | 标记为需人工介入 |

## 4. 迭代检索模式

### 4.1 基本原理

子代理返回不足时，Orchestrator提供更多上下文后重新检索，逐步逼近目标结果。

### 4.2 迭代检索流程

```
初始查询 → 子代理检索 → 结果评估
  ↓ 不足
补充上下文 + 细化查询 → 子代理检索 → 结果评估
  ↓ 仍不足
进一步细化 + 约束限定 → 子代理检索 → 结果评估
  ↓ 满足或达到最大迭代
返回最终结果
```

### 4.3 迭代检索参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| max_iterations | 3 | 最大迭代次数 |
| context_enrichment | 渐进式 | 每轮补充更多上下文 |
| relevance_threshold | 0.7 | 结果相关性阈值 |
| timeout_per_iteration | 30秒 | 每轮超时时间 |

### 4.4 上下文渐进补充策略

| 迭代轮次 | 补充内容 | 查询细化方式 |
|----------|----------|-------------|
| 第1轮 | 基础任务描述 | 原始查询 |
| 第2轮 | 添加领域约束 + 代码示例 | 增加限定词 |
| 第3轮 | 添加具体实现要求 + 参考链接 | 精确匹配 |

## 5. Fork对话

### 5.1 基本原理

独立任务使用Fork并行执行，避免串行等待。每个Fork拥有独立上下文，完成后由Orchestrator合并结果。

### 5.2 Fork创建与合并

**创建Fork**：

```
Orchestrator: 识别可并行任务
  → Fork A: 任务1 (独立上下文)
  → Fork B: 任务2 (独立上下文)
  → Fork C: 任务3 (独立上下文)
```

**合并Fork结果**：

```
Fork A → 结果A ─┐
Fork B → 结果B ─┤→ Orchestrator合并 → 最终结果
Fork C → 结果C ─┘
```

### 5.3 Fork使用约束

| 约束 | 说明 |
|------|------|
| 最大Fork数 | 3个 |
| 上下文隔离 | 每个Fork拥有独立上下文，不共享状态 |
| 结果格式 | 统一JSON格式，便于合并 |
| 超时处理 | 单个Fork超时不影响其他Fork |
| 错误隔离 | 单个Fork失败不影响其他Fork执行 |

### 5.4 Fork适用场景

| 场景 | Fork数 | 说明 |
|------|--------|------|
| 多语言实现 | 2-3 | 不同语言版本并行实现 |
| 多方案探索 | 2-3 | 不同技术方案并行探索 |
| 多模块开发 | 2-4 | 独立模块并行开发 |
| 多平台适配 | 2-3 | Web/Desktop/Mobile并行适配 |

## 6. 并行执行规则

### 6.1 核心规则

1. 每个Agent获得一个清晰输入，产生一个清晰输出
2. 输出成为下一阶段的输入
3. 不跳过阶段
4. 独立任务间使用Fork并行
5. 重叠任务间使用git worktree隔离

### 6.2 最小并行原则

以最少并行量完成最多工作。新增终端应出于真正需要，而非为了并行而并行。

**判定标准**：

| 条件 | 决策 |
|------|------|
| 任务间无依赖且无文件重叠 | 允许并行 |
| 任务间无依赖但有文件重叠 | 使用Worktree隔离后并行 |
| 任务间有依赖关系 | 串行执行 |
| 并行收益 < 上下文切换成本 | 串行执行 |

### 6.3 并行收益评估

```
并行收益 = 串行耗时 - max(各并行任务耗时) - 协调开销
```

| 并行收益 | 决策 |
|----------|------|
| > 30% | 强烈建议并行 |
| 10-30% | 建议并行 |
| 0-10% | 可选并行 |
| < 0% | 串行执行 |

## 7. 并行调度算法

### 7.1 任务依赖图构建

```
1. 解析所有任务的输入输出依赖
2. 构建有向无环图(DAG)
3. 拓扑排序确定执行层级
4. 同层任务可并行执行
```

### 7.2 调度策略

| 策略 | 适用场景 | 说明 |
|------|----------|------|
| 宽度优先 | 任务间依赖少 | 最大化并行度 |
| 深度优先 | 任务间依赖多 | 减少上下文切换 |
| 优先级调度 | 任务有不同优先级 | 高优先级任务优先分配资源 |
| 自适应调度 | 混合场景 | 根据运行时状态动态调整 |

### 7.3 调度伪代码

```
function schedule_parallel(tasks: List[Task]) -> ExecutionPlan:
    dag = build_dag(tasks)
    layers = topological_sort(dag)
    plan = ExecutionPlan()
    
    for layer in layers:
        parallel_group = []
        for task in layer:
            if can_parallelize(task, parallel_group):
                parallel_group.append(task)
            else:
                plan.add_sequential(task)
        
        if len(parallel_group) > 1:
            plan.add_parallel(parallel_group)
        else:
            plan.add_sequential(parallel_group)
    
    return plan

function can_parallelize(task: Task, group: List[Task]) -> bool:
    for existing in group:
        if files_overlap(task, existing):
            return false
        if has_dependency(task, existing):
            return false
    return true
```

## 8. 冲突检测与解决

### 8.1 冲突类型

| 冲突类型 | 检测方式 | 解决策略 |
|----------|----------|----------|
| 文件级冲突 | 文件路径交集检测 | Worktree隔离或串行执行 |
| 逻辑冲突 | 语义分析 | 人工审核 |
| 合并冲突 | git merge检测 | 三方合并或人工解决 |
| 资源冲突 | 资源占用检测 | 排队等待或资源替换 |

### 8.2 冲突解决优先级

| 优先级 | 冲突类型 | 解决方式 | 最大等待时间 |
|--------|----------|----------|-------------|
| P0 | 合并冲突 | 自动三方合并 | 5分钟 |
| P1 | 文件级冲突 | Worktree隔离 | 即时 |
| P2 | 资源冲突 | 排队等待 | 10分钟 |
| P3 | 逻辑冲突 | 人工审核 | 不限 |

### 8.3 合并冲突解决流程

```
检测合并冲突
  ↓
尝试自动三方合并
  ↓ 成功
合并完成
  ↓ 失败
标记冲突区域
  ↓
按优先级选择一方修改保留
  ↓
另一方修改以注释形式保留
  ↓
标记为需人工审核
```

## 9. 资源隔离机制

### 9.1 隔离层级

| 隔离层级 | 隔离方式 | 隔离范围 |
|----------|----------|----------|
| L1 文件隔离 | Git Worktree | 文件系统 |
| L2 进程隔离 | 独立终端/进程 | 计算资源 |
| L3 上下文隔离 | 独立会话上下文 | LLM上下文 |
| L4 状态隔离 | 独立状态文件 | 运行时状态 |

### 9.2 资源分配

| Agent角色 | 最大CPU占用 | 最大内存占用 | 最大磁盘占用 |
|-----------|-----------|-------------|-------------|
| Architect | 25% | 512MB | 500MB |
| Coder | 50% | 1GB | 2GB |
| Reviewer | 25% | 512MB | 500MB |
| Security | 30% | 768MB | 1GB |

### 9.3 资源争用处理

| 争用场景 | 处理策略 |
|----------|----------|
| CPU争用 | 按Agent优先级分配时间片 |
| 内存争用 | 触发上下文压缩，释放非活跃上下文 |
| 磁盘争用 | 触发临时文件清理，压缩历史日志 |
| 网络争用 | 按MCP工具优先级排队 |

## 10. 并行化度量指标

### 10.1 核心指标

| 指标 | 计算方式 | 目标值 |
|------|----------|--------|
| 并行度 | 同时执行的任务数 / 总任务数 | ≥ 0.3 |
| 加速比 | 串行耗时 / 并行耗时 | ≥ 1.5 |
| 并行效率 | 加速比 / 并行任务数 | ≥ 0.6 |
| 冲突率 | 冲突次数 / 并行任务对数 | ≤ 0.1 |
| 协调开销 | 协调耗时 / 总耗时 | ≤ 0.2 |

### 10.2 并行化健康度

| 健康等级 | 加速比 | 冲突率 | 建议 |
|----------|--------|--------|------|
| 优秀 | ≥ 2.0 | ≤ 0.05 | 维持当前策略 |
| 良好 | 1.5-2.0 | 0.05-0.1 | 优化冲突检测 |
| 一般 | 1.0-1.5 | 0.1-0.2 | 减少并行度 |
| 差 | < 1.0 | > 0.2 | 回退到串行执行 |
