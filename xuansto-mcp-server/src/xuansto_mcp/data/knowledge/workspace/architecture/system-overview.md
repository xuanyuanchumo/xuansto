# 系统架构概览

## 系统概述

本项目采用前后端分离的微服务架构，通过 API Gateway 统一入口，后端按业务领域拆分为独立服务。系统整体分为四层：接入层、服务层、数据层和基础设施层。

## 模块职责

| 模块 | 职责 | 技术选型 | 负责团队 |
|------|------|----------|----------|
| API Gateway | 请求路由、限流、鉴权、日志 | Nginx + Kong | 基础架构组 |
| 用户服务 | 注册、登录、权限管理、用户画像 | FastAPI + PostgreSQL | 用户组 |
| 订单服务 | 下单、订单流转、退款、库存扣减 | FastAPI + PostgreSQL | 交易组 |
| 商品服务 | 商品管理、分类、搜索、库存 | FastAPI + MongoDB | 商品组 |
| 支付服务 | 支付渠道对接、对账、结算 | FastAPI + PostgreSQL | 支付组 |
| 消息总线 | 异步通信、事件驱动、削峰填谷 | RabbitMQ | 基础架构组 |

## 关键架构决策

### ADR-001: 选择微服务而非单体架构

- **背景**: 系统需支持多团队并行开发，各业务模块独立演进
- **决策**: 采用微服务架构，按业务领域拆分服务
- **原因**: 团队规模超过 20 人，业务模块耦合度低，需要独立部署和扩展
- **代价**: 运维复杂度增加，需引入服务发现、链路追踪等基础设施

### ADR-002: 选择 FastAPI 作为后端框架

- **背景**: 需要高性能异步 API 服务，同时保持开发效率
- **决策**: 采用 FastAPI + Pydantic + SQLAlchemy 技术栈
- **原因**: 原生 async/await 支持、自动 OpenAPI 文档生成、类型安全
- **代价**: 生态较 Django 成熟度略低，部分场景需自行实现中间件

### ADR-003: 读写分离与缓存策略

- **背景**: 读多写少场景下数据库压力较大
- **决策**: PostgreSQL 主从复制 + Redis 缓存热点数据
- **原因**: 查询 QPS 超过 5000 时单库无法支撑，缓存命中率可达 85% 以上
- **代价**: 需要处理缓存一致性，引入 Cache-Aside 模式
